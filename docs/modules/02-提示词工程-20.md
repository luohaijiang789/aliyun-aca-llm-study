## 三、提示词七要素 ⭐（官方明确列举，必背）

> 官方原文：**"掌握如何说明目标、背景、角色、约束、示例、输出格式和评价标准。"**
> 这七个词是官方给的标准清单，**顺序、措辞都按官方背**，场景题里"这份提示词缺什么"就在这七项里找答案。

### 3.0 七要素总览

| # | 要素 | 回答模型的哪个疑问 | 一句话写法 | 不写会怎样 |
|:---:|---|---|---|---|
| 1 | **目标** | 你要我做什么？ | "把下面的用户反馈按四类打标" | 模型自由发挥，答非所问 |
| 2 | **背景** | 我为什么要做、场景是什么？ | "这些是大促期间的售后评价，用于定位物流问题" | 按默认理解作答，踩错业务口径 |
| 3 | **角色** | 我以什么身份说？ | "你是一名有 10 年经验的电商售后质检员" | 语气/视角/专业度不对 |
| 4 | **约束** | 什么能做、什么不能做？ | "仅依据以下资料作答，资料未提及请回答'未提及'" | 编造、越界引用外部信息 |
| 5 | **示例** | 好答案长什么样？ | 2~5 条"输入 → 正确输出"样例 | 口径不一致、格式照模型习惯来 |
| 6 | **输出格式** | 交付成什么形态？ | "以 JSON 数组输出，字段为……，除此之外不要输出任何内容" | 一会儿 JSON 一会儿散文，下游解析失败 |
| 7 | **评价标准** | 什么样算好？ | "三条以内、每条不超过 30 字、必须指向可执行动作；能被业务方直接采纳算合格" | 好坏全凭感觉，无法取舍和复制 |

> 🧠 **记忆锚点**：**目的（目标）+ 来龙去脉（背景）+ 谁在说（角色）→ 规矩（约束）+ 样板（示例）+ 长相（输出格式）→ 打分尺子（评价标准）。**
> 前六个管"让模型做对"，第七个管"让你能判断它对没对"。**本库此前缺的就是这把尺子。**

### 3.1 要素①目标（M2-K02）🟢`[A]`

**写什么**
- 一句动词开头的任务描述：**做什么**（"把…按…分类" / "从…中提取…" / "把…改写成…"）。
- 交付物的定义：交出来的是什么（一份 300 字摘要？一张三列表格？一个判定结论？）。
- 明确边界：这件事做到为止，后续谁接手。

**不写会怎样**：模型只能猜你的意图，用"最常见"的那种理解作答 → 泛泛而谈、答非所问、长度失控。

**示例**
```
✅ 目标：把下面的用户反馈逐条判定问题类型，输出一张「编号 / 问题类型 / 紧急度」的表格。
❌ 目标：帮我分析一下这些反馈。
```

---

### 3.2 要素②背景（M2-K03）🟢`[A]`

**写什么**
- 资料来源与时间范围（"来自 2026 年 Q2 的客服工单"）。
- 业务口径（"这里的'投诉'仅指已升级到主管的工单"）。
- 用途与下游环节（"结果将用于月度物流复盘报告"）。

**不写会怎样**：模型按训练语料里的"默认世界"理解 → 行业黑话理解错、口径踩偏、给出不符合场景的建议。

**示例**
```
✅ 背景：这批文本来自我们平台 618 大促期间的售后工单，"服务态度"与"物流时效"需按公司《投诉分级标准》分开统计，
     结果用于向仓储团队提出改进项。
```

---

### 3.3 要素③角色（M2-K04）🟢`[A]`

**写什么**：**身份 + 领域经验 + 服务对象 + 行为准则**。四件套比"你是一个专家"有效得多。

**不写会怎样**：输出像通用助手写的——面面俱到但没有行业味道；正式/口语尺度不受控。

**示例**
```
✅ 你是一名有 10 年经验的电商售后质检员。你的职责：按公司《售后投诉分级标准》判定投诉紧急度。
   你的准则：只依据用户原话与给定规则判定；不得臆造未出现的情节；无法判定时输出"证据不足"。
❌ 你是一个专家，请帮忙看看。
```

**易错**
- ❌ 叠加一堆互不相关的专家身份（律师+医生+程序员+营销总监…）→ 角色互相打架，输出更飘。
- ❌ 角色与任务错配（让"诗人"写严谨的合规报告）。
- ❌ 认为角色无用——**角色设定是提示词层面的标准手段**，官方把它列入七要素之一。配套题 Q008。

### 3.4 要素④约束（M2-K05）🟢`[A]`

**写什么**：三类条款，缺一不可。
1. **范围约束**：素材来源限定（"仅依据以下【资料】作答，不得引用外部知识"）。
2. **禁止项**：不许做什么（"不得编造数据；不得省略原文中的型号与金额"）。
3. **兜底行为**：**不知道时必须怎么办**（"资料中没有的内容直接输出'未提及'"）。← 最常被漏掉的一条

**不写会怎样**：模型自由补全、用外部知识硬答；只写"不许编造"而不给兜底，模型照样编一个。

**易错**
- ❌ 约束越多越好 → 无关/过度约束会让模型顾此失彼。**原则：强相关且必要。**
- ❌ 用形容词当约束（"写得专业一点"）→ 不可验收，等于没约束。

---

### 3.5 要素⑤示例（M2-K06）🟢`[A]`

**是什么**：按示例数量分 Zero-shot（0 个）/ One-shot（1 个）/ Few-shot（2~N，通常 3~5）。

| 类型 | 数量 | 适用 | 代价 |
|---|:---:|---|---|
| Zero-shot | 0 | 通用成熟任务（翻译、摘要） | 口径/格式不可控 |
| One-shot | 1 | 锚定输出风格或格式 | 占用少量上下文 |
| Few-shot | 2~N | **自定义分类口径、格式模板、行业话术**要严格对齐 | 占用上下文；示例必须高质量且口径一致 |

**不写会怎样**：模型按自己的默认口径分类/排版 → 同类问题今天一个答案明天一个答案。

**示例**
```
请将下列反馈按【物流/服务/商品质量/其他】分类。
示例：
输入：快递丢件了没人管 → 物流
输入：客服回复很及时 → 服务
输入：收到就是坏的 → 商品质量
现在请分类：包装破损但东西没问题 →
```

**易错**：示例自带错误或口径不一致 → 模型会忠实复制错误。**质量 > 数量。** 配套题 Q005。

---

### 3.6 要素⑥输出格式（M2-K07）🟢`[A]`

**写什么**：四类约束（结构化 / 版式 / 字数条数 / 措辞语气）+ **模板** + **负面约束**（"除此之外不要输出任何内容"）+ **空结果行为**（"无结果输出 []"）。

**不写会怎样**：下游解析失败、人工返工；模型在结果前后加"好的，以下是您要的内容…"导致 JSON 解析直接崩。

**示例**
```
请从文本中提取所有金额，仅输出如下 JSON 数组，不要输出其他内容：
[{"item": "项目名称", "amount": 123.45, "currency": "CNY"}]
若没有金额信息，输出 []。
```

**易错**
- ❌ "格式只能靠微调解决" → 错。**先提示词强约束**，反复约束仍不稳定才考虑微调（M5）。这是高频陷阱，配套题 Q007。

---

### 3.7 要素⑦评价标准（M2-K08）🟢`[A]` 🔴 本轮新增

**写什么**：把"好"翻译成**可被检验的条款**，回答三个问题——
1. **看哪些维度？**（准确性 / 完整性 / 可执行性 / 语气 / 长度）
2. **每个维度的尺度是什么？**（"每条不超过 30 字"、"必须包含时间和责任人"、"不得出现未经资料支持的数字"）
3. **谁来判断、怎么判断？**（"由业务负责人对照原文抽检"、"模型输出后先自查一遍再给结论"）

**为什么必须有它**（这是官方把它和前六项并列的原因）
- 没有评价标准，**你分不出三版输出哪一版更好**，只能凭感觉挑；
- 没有评价标准，**迭代没有办法判断"改好了没有"**，测试结果无法对照；
- 没有评价标准，**验收标准也就无从谈起**（见第七章）。
- 写进提示词后，模型会向这个标准对齐输出，有时还可以要求它**交付前先自查一遍**。

**不写会怎样**：收到一堆"看起来都还行"的答案；多人协作时每个人对"好"的定义都不一样；改了三轮也不知道有没有进步。

**示例**
```
✅ 评价标准：
   1. 每条建议必须是可执行动作（含动词、责任人、时限），泛泛而谈的建议视为不合格；
   2. 结论中的每一个数字都必须能在【资料】中找到出处，无法找到的视为不合格；
   3. 交付前请按以上三条自查一遍，剔除不合格条目后再输出最终结果。

❌ 评价标准：写得专业一点，尽量好一些。   ← 不可验收，等于没写
```

**易错**
- ❌ 把评价标准写成形容词（"专业""详细""优质"）→ 不可验收，模型无从对齐。
- ❌ 评价标准脱离任务（要求"语言优美"但这份交付物是数据表格）。
- ❌ 只给标准不给动作 → 建议追加一句"交付前自查一遍"。

### 3.8 七要素速填模板（考前默背）

```
### 目标
一句话动词任务 + 交付物定义
### 背景
资料来源 / 时间范围 / 业务口径 / 下游用途
### 角色
身份 + 领域经验 + 服务对象 + 行为准则
### 输入
<用分隔符包起来的待处理材料>
### 约束
范围限定 + 禁止项 + 不知道时怎么办（兜底）
### 示例
输入 1 → 输出 1；输入 2 → 输出 2（口径必须一致）
### 输出格式
JSON / 表格 / 字数 / 字段清单 + 「除此之外不要输出任何内容」
### 评价标准
判定维度 + 尺度 + 交付前自查
```

> ✅ **答题自检**：题干给一段提示词问"缺什么"时，**按这七项逐项扫一遍**，缺的那一栏就是答案；
> 若发现缺的不止一项，选**官方清单里被点名的那一项**（尤其是"评价标准""约束里的兜底""输出格式"）。

## 四、复杂任务：先列计划和关键信息，确认后再生成 ⭐（M2-K09）🟢`[A]` 🔴 本轮新增

> 官方原文：**"面对复杂任务，先列计划和关键信息，确认后再生成。"**

### 4.1 什么是"复杂任务"

满足以下任一特征的任务，都属于官方所说的复杂任务，**不要一口气让模型出终稿**：

| 特征 | 例子 |
|---|---|
| 需要**多步**才能完成 | 先读 100 页报告 → 摘要 → 提炼数据 → 出大纲 → 翻译 |
| 依赖**未说清的关键信息** | "整理一份管理层报告"，但没说给谁看、看多久、要几个建议 |
| 涉及**多个数据源或口径** | 财报 + 行业报告 + 内部口径同时要用 |
| 结果**会被下游直接使用** | 要入库、要对外发布、要作为决策依据 |
| 错了**返工成本高** | 批量处理 1 万条、跨部门分发 |

### 4.2 标准操作流程（三步走）

```
① 让模型先列「计划」── 这件事准备分几步做？每步的输入输出是什么？需要哪些资料？
        ↓
② 让它列出「关键信息」── 完成这件事它还不清楚的：受众是谁？口径是什么？
                        哪些内容不许改？截止时间？数据范围？**由人来回答/确认**
        ↓
③ 确认计划与关键信息后，再让它按已确认的计划逐步生成 ── 每步产出都可抽检
```

一句话版本：**先对齐"怎么干、依据什么"，再让它干。**

### 4.3 为什么必须这样做（答题时的标准理由）

| 直接生成 | 先列计划再生成 |
|---|---|
| 模型自行假设缺失信息，一步跑偏 → 全篇报废 | 缺口在动手前暴露，关键信息由人补齐 |
| 出错后不知道错在哪一步 | 每步可抽检，定位成本低 |
| 返工要重来一遍 | 只需重做出错的那一小步 |
| 结果可能与业务口径整体跑偏 | 计划阶段就能对齐口径 |

### 4.4 提示词写法示例

```
第一步（先不要生成报告正文）：
背景：我要向公司管理层汇报近三年产品战略复盘。
请你先输出两样东西：
1. 完成这份报告的计划：分几步、每步做什么、需要我提供什么资料；
2. 你还不清楚的关键信息清单：请逐条列出并向我提问。
在我确认之后再进入下一步。
```

### 4.5 易错辨析

| ❌ 错误做法 | ✅ 正解 |
|---|---|
| "复杂任务就该多写几句让模型一次做完" | 写长不等于降耦合；**先列计划 + 确认关键信息**才是官方给的路径 |
| "复杂任务一步到位才显得专业" | 返工成本远高于先确认的成本 |
| "复杂任务必须上 Agent" | 官方路径是**先在输入层面解决**；只有需要模型自主规划并**调用工具**实际执行时，才进入 Agent（M4） |
| "让模型列问题很啰嗦，浪费时间" | 这正是官方点名的做法：把信息缺口在生成前补上 |

> 🧠 **答题口诀**：题干出现「任务复杂 / 需求多步 / 返工成本高 / 不知道该怎么下手」→ 找「**先列出计划与关键信息，确认后再生成**」这个选项。

## 五、翻译·改写·总结·分类：四类任务的补充信息 ⭐（M2-K10）🟢`[A]` 🔴 本轮新增

> 官方原文：**"面对翻译、改写、总结、分类等任务，补充受众、目的、术语和不可改写信息。"**

这四类任务的共同特点是：**输入已经给定了**（待译文本 / 待改写文本 / 待总结文档 / 待分类条目），所以七要素之外，官方额外要求补这四项——它们决定终端"译得像不像、改得对不对、总结到不到位、分得准不准"。

### 5.1 四项补充信息逐条拆解

| 补充项 | 回答什么 | 不写会怎样 | 写法示例 |
|---|---|---|---|
| **受众** | 这份输出给谁看？ | 术语深浅、详略、语气全错：给工程师看的译文塞给客户、给老板看的总结写成流水账 | "面向海外经销商（非技术背景）" / "给公司管理层汇报用" |
| **目的** | 拿来做什么决策或动作？ | 抓错重点：用于"快速扫读"的总结写成了"完整保留细节"的长文 | "用于管理层 5 分钟口头汇报" / "用于售后团队据此派单" |
| **术语** | 专业名词怎么统一？ | 同一个术语前后译法不一致、行话被翻成通用词 | "附术语表：'履约时效'统一译为 fulfillment SLA；'客诉'统一译为 customer complaint" |
| **不可改写信息** 🔴 | **哪些内容一个字都不能动？** | **型号、规格、金额、法务条款、免责声明、专有名词被"优化"掉或改写，后果最严重** | "以下信息保持原文不变，不得翻译、改写、删减或概括：产品型号 XY-200、金额数字、第 5 条免责声明、客户名称" |

### 5.2 四类任务各自的侧重点

| 任务 | 最该补的 | 典型翻车 |
|---|---|---|
| **翻译** | **术语 + 不可改写信息** | 术语前后不一致；型号/数字被本地化改写 |
| **改写** | **不可改写信息 + 受众** | 把不许改的条款也一并润色了；改写后语气与客户不匹配 |
| **总结** | **目的 + 受众**（其次是不可遗漏的关键点） | 平均用力没有重点；漏掉决策所需的关键数据 |
| **分类** | **术语（类别定义）+ 目的**（准确到自己公司的口径） | 按模型的默认理解分类，与业务口径不符 |

### 5.3 完整示例（翻译任务）

```
目标：把这份中文产品说明书改写为英文，供海外经销商阅读（受众）。
背景：用于 Q3 海外渠道推广物料，将由市场部统一印制（目的与用途）。
术语：请统一使用附件术语表；"履约时效"统一译为 fulfillment SLA。
不可改写信息：以下信息保持原样，不得翻译、改写、删减：产品型号 XY-200、全部规格参数与金额数字、
              第 5 条免责声明全文、公司名称与注册商标。
约束：除上述"不可改写信息"外，其余内容可自由润色；不得新增原文没有的性能承诺。
输出格式：保留原文的章节结构与编号，逐节输出。
评价标准：型号/数字/免责声明与原文逐字一致；术语译法全文统一；任一条不符即为不合格。
```

### 5.4 易错辨析

| ❌ 误解 | ✅ 正解 |
|---|---|
| "翻译只要说'翻译成英文'就行" | 官方明确要求**额外**补受众、目的、术语、不可改写信息 |
| "模型和人类翻译一样会保护数字和条款" | 模型按"最可能的续写"生成，**不保证原文照抄**；不写"不可改写信息"就有被改写的风险 |
| "分类任务不需要术语" | 类别名本身就是要对齐的术语，自定义类别必须给定义与示例 |
| "受众和目的是一回事" | 受众是**给谁看**，目的是**拿来干什么**；两者分别影响措辞与取舍，都要写 |

> 🧠 **答题口诀**：题干出现「翻译 / 改写 / 总结 / 分类」→ 优先找含「**受众、目的、术语、不可改写信息**」的选项；
> 若问"最容易漏的是哪一项" → 答「**不可改写信息**」。

## 六、采访模式与深度思考模式（M2-K14 / M2-K15）🔴`[C]` ⚠️ 本轮新增

> ⚠️ **核实声明**：官方「建议掌握的知识」把这两项列入本模块，但**未给出产品名称与交互形态**。
> 以下只记录**概念与作用**——这也是唯一可能被考查的层面。
> **本文件不描述、你也不要去记忆任何按钮位置、开关名称、菜单路径或操作步骤。**

### 6.1 采访模式 🔴`[C]` ⚠️

| 项 | 内容 |
|---|---|
| **是什么** | 不是你单方面把要求说完，而是**让模型反过来向你提问**，通过一轮或多轮问答把需求问清楚 |
| **解决什么** | 你的需求还没想清楚、说不全时，模型知道哪些信息是必要的，由它来问你 |
| **适用** | **需求不清、范围不明、关键信息缺失**的场景（"我要一份市场分析报告"——受众？周期？要几个结论？） |
| **不适用** | 需求已经很清楚的简单任务（直接给七要素即可，先采访反而是浪费） |
| **与七要素的关系** | 它是**补齐七要素的手段**：模型问的正是缺失的目标、背景、约束、评价标准…… |
| **与第四章的关系** | 与"复杂任务先列计划和关键信息"同源：都是**生成前补信息**；差别在于——复杂任务偏"让它列计划"，采访模式偏"让它问你" |

**示例（概念层，不涉及任何产品操作）**
```
我不知道还缺什么信息。请你先向我提问，一次问 3 个最关键的问题，
在我回答之后，再按我们最终确认的需求生成。
```

### 6.2 深度思考模式 🔴`[C]` ⚠️

| 项 | 内容 |
|---|---|
| **是什么** | 让模型**展开更长的推理过程再作答**，而不是立刻给出结论 |
| **解决什么** | 一步到位的答案在多条件判断、多步推算上容易跳步出错 |
| **适用** | **复杂推理 / 多步任务**（多条款比对、多步计算、需要交叉验证的判断） |
| **不适用** | 简单事实问答、格式转换类任务——展开推理只会增加耗时 |
| **与手法层的关系** | 概念上等同"先想后答 / 先列推理过程再给结论"（M2-K17 CoT）的**产品化形态**；两者是同一思路 |
| **注意** | 官方**不考**它是怎么实现的（那属于模型训练/推理细节），只可能考"什么时候该用它" |

**示例（概念层，不涉及任何产品操作）**
```
请先把推理过程完整展开：逐条比对政策条件并说明是否满足，再给出最终结论，最后说明依据的条款编号。
```

### 6.3 两者怎么选（一句话）

| 场景 | 选 |
|---|---|
| **我不知道自己想要什么** / 需求说不清 | **采访模式**（让模型问你） |
| **我知道要什么，但这件事很难想** / 多步推理 | **深度思考模式**（让它慢慢想） |
| 需求清楚又简单 | 都不用，直接按七要素写 |

> ⚠️ 配题 **Q004** 为「待核实」题。若官方课程给出不同的产品名称或更细的定义，**以官方课程为准**，并把修正记录回填到本小节。

## 七、验收标准（M2-K11）🟢`[A]` 🔴 本轮新增

> 官方「建议掌握的知识」原文：**"把任务目标、背景、约束和验收标准讲清楚的方法。"**

### 7.1 它和"评价标准"的关系（必考点）

| 维度 | **评价标准**（M2-K08，写在提示词里） | **验收标准**（M2-K11，写在任务需求里） |
|---|---|---|
| 给谁看 | 给**模型**看：让模型知道好答案长什么样 | 给**人和项目**看：判断这次交付能不能放行 |
| 出现在 | 提示词的一部分 | 任务/需求定义的一部分 |
| 作用时机 | 生成**之前与之中**（对齐输出、自查） | 生成**之后**（抽检、放行/打回） |
| 典型内容 | "每条不超过 30 字，必须含动词和责任人" | "在 20 份测试样本上关键字段准确率 ≥ 95% 才允许上线" |
| 共同点 | **都必须是可量化、可核对的条款**，都不能写成形容词 | |

**一句话**：**评价标准是给模型的尺子，验收标准是给任务的闸门；两把尺子必须同源、口径一致**，否则模型按 A 标准输出、你按 B 标准验收，永远对不齐。

### 7.2 写好验收标准的三条要求

1. **可量化**：有阈值、有样本、有数量（"在 20 份合同上，关键字段漏提 ≤ 1 处"）。
2. **可核对**：别人拿同一份输出能得出同一结论，不依赖主观判断。
3. **有证据**：每条达标与否都能追溯到具体样本或出处（与 M4「自检清单要具体、可核对、有证据」是同一套思路）。

### 7.3 官方四件套的完整写法

```
目标：我们要做什么、交付什么、谁会用    ← M2-K02
背景：资料来源、业务口径、使用场景      ← M2-K03
约束：只能依据什么、不许做什么、不知道怎么办 ← M2-K05
验收标准：达到什么尺度才算完成、由谁用什么方式核对 ← M2-K11
```

> 🧠 **答题口诀**：题干出现「把……讲清楚」「需求该怎么提」「这一版能不能上线」→ 找包含「**目标、背景、约束、验收标准**」这一组的选项。

## 八、输入优化方法：手法层合集（M2-K16 ~ M2-K22）🟡`[B]`

> 这一章是本模块"怎么做"的部分。官方把它们概括为「**输入优化方法**」，下面的招式是对它的展开——**理解 > 背术语**。

### 8.1 Zero-shot / One-shot / Few-shot（M2-K16）

按**提示词里给的示例数量**区分：0 / 1 / 2~N 个。

- 当出现**格式不对、分类口径不一致、话术不像本公司**时，**第一选择是补 Few-shot 示例**，而不是换手段。
- ❌ 误区一：混淆划分维度（这是按**示例数量**分，不是按输出字数或推理步数分）。
- ❌ 误区二：认为 Zero-shot 一定更差（通用任务足够，堆示例是浪费）。
- ❌ 误区三：示例自己有错 → 错误会被忠实复制。**质量 > 数量，口径一致最关键。**

### 8.2 先想后答 / 思维链 CoT（M2-K17）

让模型**把推理过程写出来再给结论**，常见于多步推理、计算、多条款判断。

- 触发写法："先逐条比对条件并说明是否满足，再给出结论，最后说明依据。"
- ❌ CoT **不注入新知识**，只把已有推理能力展开；材料本身不全，写了 CoT 也算不出来。
- ❌ 不要把 CoT 与 Few-shot 混为一谈（CoT 给推理过程，Few-shot 给输入→输出样例；二者可叠加）。
- 📌 **对外交付**时若不宜暴露中间推理，可要求"内部推理，只输出结论要点"（合规要求另见 M6）。
- 🔗 与第六章 **深度思考模式**是同一思路的产品化形态。

### 8.3 任务拆解（M2-K18）

把一个大任务拆成若干**有依赖关系的子步骤**，每步一个提示词，前一步的输出作为后一步的输入。

```
读全文 → 抽摘要 → 提炼要点 → 出大纲 → 翻译成目标语言  ⇒ 5 步 5 个提示词
```

- ❌ 拆解 ≠ 把要求写得更长（写长是堆信息，拆解是**降耦合**）。
- ❌ 简单任务不必拆，判断标准是"单步能否被稳定执行"。
- 🔗 与第四章同源：**复杂任务先列计划**，落地方式常常就是任务拆解。

### 8.4 明确性、具体性与边界约束（M2-K19）

- **明确性**：不用形容词做验收标准 → "使用正式书面语，每段不超过 3 句，不使用夸张修辞"。
- **具体性**：给量化、给对象、给场景 → "面向中小企业主，300 字，突出 3 个卖点"。
- **范围约束**：限定素材来源 → "仅依据以下资料回答，不得使用资料外的信息"。
- **禁止项 + 兜底**：不只说"不许编造"，还要说"资料没有就输出'未提及'"。
- ❌ 约束不是越多越好（**强相关且必要**）；缺兜底条款是最高频的失分项。

### 8.5 常见失败模式与归因（M2-K20）

| 失败模式 | 典型症状 | 提示词层面的改进 | 属本模块？ |
|---|---|---|:---:|
| **指令模糊** | "写得好看点""分析一下" → 泛泛而谈 | 量化要求、明确对象、明写输出格式与评价标准 | ✅ |
| **缺上下文 / 背景** | 答非所问，误解业务口径 | 补背景、补角色、补业务定义 | ✅ |
| **缺输出格式约束** | 一会儿 JSON 一会儿散文 | 明写格式 + 给模板 + 加禁止项 | ✅ |
| **缺评价标准** | 出了几版分不出好坏 | 补"好"的可核对定义 + 要求交付前自查 | ✅ |
| **复杂任务未先对齐** | 一步跑偏全篇报废 | 先列计划与关键信息，确认后再生成 | ✅ |
| **四类任务漏补信息** | 术语不一致、不可改写内容被改 | 补受众 / 目的 / 术语 / 不可改写信息 | ✅ |
| **任务过载** | 一个提示词塞 5 件事，样样稀松 | 任务拆解，分步执行 | ✅ |
| **口径不一致** | 同类样本分类结果前后矛盾 | Few-shot 示例锚定口径 | ✅ |
| **缺知识**（私域 / 最新） | 不知道你家产品、最新政策 | ❌ 提示词解决不了 → **接入知识库 / RAG（M3）** | ❌ |
| **超出能力边界**（实时 / 精确计算 / 业务动作） | 要查今天天气、要算精确账、要发邮件 | ❌ 提示词解决不了 → **调用工具 / Agent（M3/M4）** | ❌ |
| **要长期固定风格且反复约束不稳** | 每次语气都要像同一个人 | 先试提示词 → 不行再**微调（M5）** | ⚠️ 先本模块 |

> 🧠 **归因口诀（已按官方词修订）**：
> **「说不清」优化输入，「不知道」接知识库，「做不了」调工具，「改不了」用微调，「要落地」协作 Agent，风险高保留人工确认。**

### 8.6 优化输入在决策树中的位置（M2-K12）🟢`[A]`

官方给出的手段池是五选一，**顺序就是优先级**：

```
回答不够好
   │
   ├─ 第 1 问：是「它说不清」还是「它不知道 / 做不了」？
   │
   ├─ 表达/理解问题（听得懂，只是答得糙）
   │     → ① 优化输入（提示词）  💰 最低、见效最快  ← 本模块
   │           └─ 还不够好 → 再看缺什么：
   │                 缺私域/最新知识 → ② 接入知识库（M3）
   │                 要实时数据/确定性计算/业务动作 → ③ 调用工具（M3）
   │                 要长期固定行为/格式/风格 → ④ 使用微调（M5）
   │                 要自主规划、多步执行 → ⑤ 协作 Agent（M4）
   │                 高风险场景 → 保留人工确认（M6）
   │
   └─ 知识 / 能力问题 → 直接从 ②~⑤ 里选（但通常仍建议先把话说清楚）
```

> ✅ **答题策略**：题干只说"效果不好 / 不满意"，**第一步永远选"优化输入（提示词）"**，
> 除非题干明确出现了缺知识、缺实时能力、要长期固定风格、要自主多步执行的症状。
> 官方金句之一：**「查知识用 RAG，做动作靠工具，稳行为才考虑微调。」**

### 8.7 提示词迭代循环（M2-K21）

```
① 写（Write）→ 按七要素搭初版，明写评价标准
② 测（Test）→ 用固定的一组测试用例（3~10 条，含边界样本）全跑一遍
③ 分析（Analyze）→ 归因：格式？口径？缺背景？跑题？缺知识？超边界？
④ 改（Revise）→ 针对归因做**一处**改动
⟲ 回到 ②
```

- **固定测试集**是迭代的前提；**一次只改一处**是归因能力的前提；给出版本号便于回滚。
- ❌ "多试几次抽个好的"不是优化，是抽卡；结果不稳定、不可复制。
- ❌ 没跑完循环就换手段（微调/RAG）是考试最爱设的陷阱。

### 8.8 典型业务场景（M2-K22）

| 业务场景 | 提示词设计要点 | 常用组合 |
|---|---|---|
| **批量文本分析**（评论/工单打标） | 统一口径、分隔符隔开逐条输入、明写评价标准 | Few-shot + 输出格式约束 + 类别定义（术语） |
| **信息提取**（姓名/金额/日期/条款） | 字段清单写死、给 JSON 模板、规定"没有就输出 []" | 输出格式约束 + 禁止项 + 兜底 |
| **内容生成**（文案/报告/回复拟稿） | 给受众、目的、字数、语气、卖点数量 | 角色设定 + 量化要求 + 评价标准 |
| **翻译 / 改写** | 给术语表、**标明不可改写信息**、说明受众与目的 | 七要素 + 第五章四件套 |
| **总结** | 给受众与用途、限定字数、点明不可遗漏的关键点 | 目的 + 受众 + 输出格式 + 评价标准 |
| **分类** | 给类别定义（术语）与每条类别的示例 | Few-shot + 术语定义 + 评价标准 |

> 💡 **通用判断顺序**：先问"模型本身能不能做"（能 → 在提示词层面想办法），
> 再问"要不要外部知识或工具"（要 → 转到别的模块）。

## 九、一页纸工作流与边界

### 9.1 六把"武器"速查（按使用频率）

| # | 武器 | 什么时候先想到它 |
|:---:|---|---|
| 1 | **七要素自检** | 拿到任何任务先扫一遍：目标/背景/角色/约束/示例/输出格式/评价标准缺哪项 |
| 2 | **明确与量化**（含评价标准） | 输出跑偏、太泛、分不出好坏 |
| 3 | **Few-shot 示例** | 格式不对、分类口径不一致、话术不像本公司 |
| 4 | **输出格式约束** | 需要机器解析、需要表格/JSON、字数不可控 |
| 5 | **先列计划 + 任务拆解** | 任务复杂、多步、返工成本高 |
| 6 | **四类任务补四件套** | 翻译 / 改写 / 总结 / 分类 |

### 9.2 一条好提示词的检查清单（考前默背）

- [ ] **目标**：一句话动词任务 + 交付物定义
- [ ] **背景**：来龙去脉、业务口径、下游用途
- [ ] **角色**：身份 + 领域经验 + 服务对象 + 行为准则
- [ ] **输入**：给了材料，并用**分隔符**圈起来
- [ ] **约束**：范围限定 + 禁止项 + **"不知道时怎么办"的兜底**
- [ ] **示例**：口径要对齐时至少 1~3 条（口径一致 > 数量多）
- [ ] **输出格式**：JSON/表格/字数/条数 + 模板 + 「除此之外不要输出任何内容」
- [ ] **评价标准**：可核对的维度与尺度，必要时要求交付前自查
- [ ] **复杂任务**：先列计划与关键信息，**确认后再生成**
- [ ] **翻译/改写/总结/分类**：补**受众、目的、术语、不可改写信息**
- [ ] **验收**：有固定测试集与可量化的验收标准，一次只改一处
