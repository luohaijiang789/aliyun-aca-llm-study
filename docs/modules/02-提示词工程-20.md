## 三、逐考点详解

### M2-K01 提示词的构成要素 🟡`[B]`

**是什么**
一个高质量的提示词，通常由四部分拼装而成：

| 要素 | 回答模型哪个疑问 | 举例 |
|---|---|---|
| **指令（Instruction）** | 你要我做什么？ | "把下面的用户反馈分类" |
| **上下文（Context）** | 我为什么要做、背景是什么？ | "这些是电商大促期间的售后反馈，用于定位物流问题" |
| **输入数据（Input Data）** | 我基于什么做？ | 用分隔符包起来的待处理原文 |
| **输出格式（Output Indicator）** | 我交付成什么样？ | "输出 JSON，字段：类别、紧急度、原文摘录" |

**怎么用**：把四要素按固定顺序排进提示词，并用**分隔符**（`###`、`<>…</>`、``` """```）把它们隔开，让模型清楚"哪段是背景、哪段是要处理的材料、哪段是规则"。这就是常说的"结构化提示词 / 提示词框架"。

**易错点**
- ❌ 以为"指令写得长 = 提示词好"。真正的短板通常是**没给输入数据**或**没说输出格式**。
- ❌ 把"质的提升"寄托在换模型、调参数上，而没检查四要素是否齐全。

**示例**

```
### 上下文
你是某电商平台的售后质检助手，下面的文本来自大促期间的用户评价。
### 任务（指令）
请判断每条评价反映的问题类型。
### 输入数据
<评价>
1. 物流太慢了，等了七天
2. 客服态度很好，问题当场解决
</评价>
### 输出要求
以 JSON 数组输出，每条一个对象，字段为：编号、问题类型（物流/服务/商品质量/其他）、紧急度（高/中/低）。
不要输出除 JSON 以外的任何内容。
```

### M2-K02 角色设定与系统角色提示词 🟡`[B]`

**是什么**
- **系统角色提示词（System Prompt）**：对话开始前设定模型"人格"与"行为准则"的那段话，对整个会话持续生效。
- **角色设定（Persona）**：告诉模型"你是谁"——身份、专业背景、服务对象、行事准则。

**怎么用**：角色 = **身份 + 领域经验 + 任务职责 + 行为约束**。不要只写"你是一个专家"（太虚），要写"你是一名有 10 年经验的电商售后质检员，负责按公司标准判定投诉等级"。

**易错点**
- ❌ 认为"提示词里写角色没有作用，角色是训练出来的" —— 这是常见误解，设置角色是提示词层面的标准做法。
- ❌ 一次性叠加十几个互不相关的专家身份（"你是律师+医生+程序员+营销总监…"），角色会互相打架，输出反而更飘。
- ❌ 角色设定与实际任务不匹配（让"诗人"去写严谨的合规报告）。

**示例**
```
你是一名资深电商售后质检员，有 10 年经验。
你的职责：按公司《售后投诉分级标准》判定投诉紧急度。
你的准则：只能依据用户原话和给定规则判定；不得臆造未出现的情节；无法判定时输出"证据不足"。
```

### M2-K03 Zero-shot / One-shot / Few-shot 🟡`[B]`

**是什么**：按**提示词里给的示例数量**区分。

| 类型 | 示例数量 | 适用场景 | 代价 |
|---|:---:|---|---|
| **Zero-shot（零样本）** | 0 个 | 通用的、模型预训练里很熟的任务（翻译、摘要） | 格式/口径不可控 |
| **One-shot（单样本）** | 1 个 | 想锚定输出风格或格式 | 占用少量上下文 |
| **Few-shot（少样本）** | 2~N 个（通常 3~5） | **分类口径、格式模板、行业话术**需要严格对齐 | 占用上下文，示例本身要高质量且具代表性 |

**怎么用**：当模型"格式不对""分类口径不统一""话术不像我们公司的"时，**第一选择是补 Few-shot 示例**，而不是换手段。

**易错点**
- ❌ 混淆"示例数量"与其他维度：这不是按"输出字数"或"推理步数"划分的。
- ❌ Few-shot 示例自己有错/口径不一致 → 模型会忠实地把错误学过去。**示例质量 > 示例数量**。
- ❌ 认为 Zero-shot 一定比 Few-shot 差：任务简单时 Zero-shot 足够，堆示例是浪费。

**示例（Few-shot 分类）**
```
请将下列反馈按【物流/服务/商品质量/其他】分类。
示例：
输入：快递丢件了没人管 → 物流
输入：客服回复很及时 → 服务
输入：收到就是坏的 → 商品质量
现在请分类：包装破损但东西没问题 →
```

### M2-K04 思维链 CoT 🟡`[B]`

**是什么**：Chain-of-Thought，让模型**把推理过程写出来再给结论**，而不是直接蹦答案。最常见的一句触发语是 "让我们一步一步思考 / 请先列出推理步骤，再给出最终结论"。

**怎么用**：适用于**多步推理、计算、需要交叉验证的判断**（如"根据以下条款判断该投诉是否成立"）。
可以要求它"先列步骤 → 再给结论 → 最后自查一遍"。解题正确率通常显著高于直接要答案。

**易错点**
- ❌ 以为 CoT 是在给模型"注入知识" —— 它不改变模型知道什么，只是**让已有的推理能力被完整展开**。模型算不清的账，写了 CoT 也可能算不清。
- ❌ 混淆 CoT 与 Few-shot：CoT 是"给推理过程"，Few-shot 是"给输入→输出样例"。二者可以叠加（ Few-shot CoT：示例里同时给出推理过程）。
- ❌ 对外暴露中间推理过程可能有安全/合规风险 —— 合规要求高的场景可要求"内部推理、只输出结论要点"（相关内容见 M6）。

**示例**
```
请根据以下退货政策，判断该订单是否可退货。
要求：先逐条比对政策条件并说明是否满足，再给出最终结论（可退/不可退），最后说明依据的政策条款编号。
```

### M2-K05 任务拆解 🟡`[B]`

**是什么**：把一个复杂的大任务拆成若干个**顺序执行的子任务**，每个子任务一个提示词，前一步的输出作为后一步的输入。

**怎么用**
> 读全文 → 抽摘要 → 提炼要点 → 按要点写大纲 → 把大纲翻译成目标语言 ⇒ **5 步 5 个提示词**

好处：每一步的输出都可人工抽检；错在哪一步一目了然；单步上下文更短，模型注意力更集中。

**易错点**
- ❌ 把"任务拆解"等同于"把要求写得更长"。写长是堆信息，拆解是**降耦合**。
- ❌ 认为拆解一定比一次完成更好：简单任务拆开反而多做无用功。**判断标准是"单步是否还能被稳定执行"**。
- ❌ 混淆"任务拆解"与"Agent"：多步、需要自主规划和调用外部工具执行 → M4 Agent；**纯提示词层面的分步串联**（人工串，不引入外部工具） → 本模块的做法。

**示例**
```
第 1 步：请阅读以下合同全文，输出不超过 300 字的摘要。
（人工确认后）
第 2 步：基于上面的摘要，列出所有涉及付款时间的条款，以表格输出。
（人工确认后）
第 3 步：将表格内容翻译为英文，保持术语一致。
```

### M2-K06 输出格式约束 🟡`[B]`

**是什么**：在提示词里**事前规定**交付物的形态，常见有四类约束：

| 约束类型 | 写法示例 |
|---|---|
| **结构化** | "仅输出 JSON，字段为：name / date / amount，不要输出多余文字" |
| **版式** | "以 Markdown 表格输出，三列：问题、原因、建议" |
| **字数/条数** | "控制在 200 字以内" / "列出不超过 5 条" |
| **措辞/语气** | "使用正式书面语，避免感叹号" |

**怎么用**：给**格式示例（模板）+ 负面约束（"除此之外不要输出任何内容"）**，双保险。JSON 场景可在提示词里直接写出字段结构。

**易错点**
- ❌ 认为"格式问题应该靠后处理/正则去兜" —— 提示词里说清楚的成本远低于事后解析。
- ❌ 以为"输出格式只能靠微调解决" —— **先提示词强约束**，反复约束仍不稳定才考虑微调（M5）。这是高频陷阱。
- ❌ 只给正面要求不给禁止项，模型容易在 JSON 前后加"好的，以下是结果…"导致解析失败。

**示例**
```
请从文本中提取所有金额信息，仅输出如下 JSON 数组，不要输出其他内容：
[{"item": "项目名称", "amount": 123.45, "currency": "CNY"}]
若文本中没有金额信息，输出 []。
```

### M2-K07 明确性、具体性与边界约束 🟡`[B]`

**是什么**：把"模型的自由度"收到任务需要的范围内。

- **明确性**：不用形容词做验收标准。"写得专业一点" → "使用正式书面语，每段不超过 3 句，不使用夸张修辞"。
- **具体性**：给量化、给对象、给场景。"写得好" → "面向中小企业主，300 字，突出 3 个卖点"。
- **范围约束**：限定素材来源，如"**仅依据以下资料回答**，不得使用资料外的信息"。
- **禁止项**：明确不许做什么，如"不得编造数据；资料未提及的内容请回答'未提及'"。

**怎么用**：把约束写成**可验收**的条款（能量化就量化，能举例就举例）。

**易错点**
- ❌ "约束越多越好" —— 过度、无关的约束会让模型顾此失彼。**约束应与任务强相关且必要**。
- ❌ 缺兜底条款：只说"不许编造"，没说"不知道时怎么办"，模型仍会硬答。**必须给"不知道时的默认行为"**（如输出"未提及"）。

**示例**
```
仅依据【资料】中的内容回答问题，不得引用任何外部知识。
若【资料】中没有答案，直接输出"未提及"，不要猜测。
回答控制在 100 字以内，面向非技术用户，不使用专业术语。
```

### M2-K08 常见失败模式与归因 🟡`[B]`

| 失败模式 | 典型症状 | 提示词层面的改进 | 是否属本模块 |
|---|---|---|:---:|
| **指令模糊** | "写得好看点""分析一下" → 输出泛泛而谈 | 量化要求、给对象、给字数 | ✅ |
| **缺上下文/背景** | 答非所问，误解业务口径 | 补背景、补角色、补业务定义 | ✅ |
| **缺输出格式约束** | 一会儿 JSON 一会儿散文 | 明写格式 + 给模板 + 加禁止项 | ✅ |
| **任务过载** | 一个大提示词塞 5 件事，样样稀松 | 任务拆解，分步执行 | ✅ |
| **口径不一致** | 同类样本分类结果前后矛盾 | Few-shot 示例锚定口径 | ✅ |
| **缺知识**（私域/最新） | 模型不知道你家产品/最新政策 | ❌ 提示词解决不了 → **RAG（M3）** | ❌ |
| **超出能力边界**（实时/计算/操作） | 要查今天天气、要算精确账、要发邮件 | ❌ 提示词解决不了 → **插件/Agent（M3/M4）** | ❌ |
| **要固定风格且长期稳定** | 每次语气都像同一个人、格式从不出错 | 先试提示词，**不行再微调（M5）** | ⚠️ 先本模块 |

> 🧠 **归因口诀**：**"说不清"归提示词，"不知道"归检索，"做不了"归插件，"改不了的习惯"归微调。**

### M2-K09 提示词迭代优化方法论 🟡`[B]`

**是什么**：提示词不是写一次就完事的，而是一个**四步循环**。

```
   ① 写（Write）── 按四要素搭初版，明确你要的"好"是什么
        ↓
   ② 测（Test）── 用固定的一组测试用例跑，覆盖典型 + 边界样本
        ↓
   ③ 分析（Analyze）── 归类失败原因：格式？口径？缺上下文？跑题？幻觉？
        ↓
   ④ 改（Revise）── 针对归因做**一处**改动
        ↓
      回到 ② ──────────── 循环 ────────────
```

**怎么用**
- **必须有固定测试集**：3~10 条典型样本（含 1~2 条刁钻边界），每次改动后重跑同一批，才能对比。
- **一次只改一处**：同时改三处，效果变好你不知道是哪处起作用，变差也不知道该回滚哪个。
- **记录版本**：给提示词编版本号，附上"这版改了什么、为什么改、结果如何"。
- **效果退化时**：对比新旧版本的输出 diff，定位是哪条约束/示例引入的回退，再针对性回改。

**易错点**
- ❌ "多次重试直到抽到一个满意答案" —— 这不是优化，是抽卡；抽样得到的满意不具有稳定性。
- ❌ 效果不好就直接换手段（微调/RAG）—— **没跑完迭代循环就想升级手段，是考试最爱设的陷阱**。
- ❌ 只测一条样本就下结论 —— 样本量太小，结论不可靠。

### M2-K10 提示词在决策树中的位置 🟢`[A]`

**是什么**：官方课时 3 的核心主张——**通过优化输入来提升回答质量**，是所有优化手段里**成本最低、见效最快**的一个。

```
回答不够好
   │
   ├─ 第 1 问：是「它说不清」还是「它不知道」？
   │
   ├─ 表达/理解问题（模型听得懂，只是答得糙）→ ① 优化提示词  💰 最低 ← 本模块
   │       └─ 还不够好 → 再看缺什么：
   │             缺私域/最新知识 → ② RAG（M3）
   │             需固定格式/风格 → ③ 微调（M5）
   │             任务复杂多步/要调工具 → ④ Agent（M4）
   │             能力边界不足（联网/计算/操作） → ⑤ 插件（M3）
   │
   └─ 知识/能力问题 → 直接从 ②~⑤ 里选（但通常仍建议先把提示词写清楚）
```

**怎么用（答题口诀）**：**"只要题干说'效果不好/回答不满意'，第一步永远选"优化提示词"，除非题干明确说了缺知识、缺能力、要多步执行、要固定风格。**

**易错点**
- ❌ 跳过提示词直接选微调/RAG —— 顺序不能跳，成本递增。
- ❌ 把"模型缺少公司私有数据"当成"提示词没写好" —— 这题答案必须是别的手段。

### M2-K11 典型业务场景应用 🟡`[B]`

| 业务场景 | 提示词设计要点 | 常用组合技巧 |
|---|---|---|
| **批量文本分析**（评论/工单批量打标） | 统一口径、批量输入用分隔符隔开、要求逐条输出 | Few-shot + 输出格式约束 + 明确类别枚举 |

## 四、提示词优化方法论（一页纸工作流）

### 4.1 标准四步循环

| 步骤 | 关键动作 | 产出物 |
|---|---|---|
| **① 写** | 按"指令 / 上下文 / 输入数据 / 输出格式"搭初版；能加角色就加 | 提示词 v1 |
| **② 测** | 准备 3~10 条固定测试样本（含边界），全部跑一遍 | 输出记录表 |
| **③ 分析** | 给每条失败分类归因：格式 / 口径 / 缺上下文 / 跑题 / 缺知识 / 超边界 | 归因清单 |
| **④ 改** | 按归因做**一处**针对性修改（加示例 / 加约束 / 拆任务 / 加 CoT） | 提示词 v2 |
| ⟲ | 回到 ②，直到在测试集上稳定达标 | 提示词 vN |

### 4.2 六种"武器"速查（按使用频率排序）

| # | 武器 | 什么时候先想到它 |
|:---:|---|---|
| 1 | **明确与量化** | 输出跑偏、太泛、不符合预期口径 |
| 2 | **角色设定** | 语气不专业、不懂行业语境 |
| 3 | **Few-shot 示例** | 格式不对、分类口径不一致、话术不像本公司 |
| 4 | **输出格式约束** | 需要机器解析、需要表格/JSON、字数不可控 |
| 5 | **思维链 CoT** | 多步推理、计算、需要依据材料下判断 |
| 6 | **任务拆解** | 一个大提示词里塞了多件事 |

### 4.3 归因决策表（"这一步该用哪个武器 / 该不该换模块"）

| 观察到的症状 | 首选动作 | 无效后的下一步 |
|---|---|---|
| 输出太泛、跑题 | 明确与量化 + 角色设定 | Few-shot |
| 格式不稳定 / 无法解析 | 输出格式约束 + 模板 + 禁止项 | 长期仍不稳 → 考虑微调（M5） |
| 分类口径前后不一致 | Few-shot 示例 | 示例加到 3~5 条仍不行 → 微调（M5） |
| 多步题答错、算错 | CoT | CoT + Few-shot（示例里给推理过程） |
| 一件事做不好因为塞了五件事 | 任务拆解 | 需要自主调度与工具 → Agent（M4） |
| 不知道我司私有内容 | 提示词**无效** | → RAG / 知识库（M3） |
| 要查实时数据 / 精确计算 / 实际操作 | 提示词**无效** | → 插件 / Agent（M3/M4） |

### 4.4 一条好提示词的检查清单（考前默背）

- [ ] **指令**：一句话说清"做什么"，动词明确
- [ ] **上下文**：交代背景、业务口径、目标对象
- [ ] **输入数据**：给了材料，并用**分隔符**圈起来
- [ ] **输出格式**：JSON/表格/字数/条数，并附了模板
- [ ] **角色**：身份 + 领域经验 + 行为准则（可选但推荐）
- [ ] **示例**：至少 1~3 条（口径要求高时必给）
- [ ] **边界**：范围限定 + 禁止项 + **"不知道时怎么办"的兜底**
- [ ] **验收**：有固定测试集，一次只改一处

## 五、易错辨析表

| # | 常见误解（陷阱） | 正解 | 关联考点 |
|:---:|---|---|---|
| 1 | "提示词越长越好" | ❌ 长度≠质量。**要素齐全 + 约束相关**才有效；无关约束反而有害 | M2-K07 |
| 2 | "输出格式只能靠微调解决" | ❌ **先提示词强约束**，反复仍不稳才考虑微调 | M2-K06 / M5 |
| 3 | "模型缺少我司资料，优化提示词就行" | ❌ 缺知识是检索问题 → **RAG**（提示词无法注入知识） | M2-K08 / M3 |
| 4 | "CoT 能给模型补充推理知识" | ❌ CoT 只是**展开推理过程**，不注入新知识 | M2-K04 |
| 5 | "Few-shot 示例越多越好" | ❌ **质量 > 数量**，示例自带错误会被忠实复制；口径一致最关键 | M2-K03 |
| 6 | "效果不好就重试几次，抽个好的" | ❌ 抽样不是优化；要建测试集、做归因、改提示词 | M2-K09 |
| 7 | "任务拆解 = 把要求写得更详细" | ❌ 拆解是**降耦合为多步**，写详细仍是单步堆叠 | M2-K05 |
| 8 | "提示词里写角色不起作用" | ❌ 角色设定是提示词层的标准做法，且直接影响语气与视角 | M2-K02 |
| 9 | "只要不说'不许编造'就没问题" | ❌ 必须给**兜底行为**（如输出"未提及"），否则模型仍会硬答 | M2-K07 |
| 10 | "多步任务就该上 Agent" | ⚠️ 先看能不能用**提示词 + 任务拆解**搞定；要自主规划/调工具才是 Agent | M2-K05 / M4 |
| 11 | "温度参数调低就能解决输出不稳定" | ❌ 那是 M3 的 API 参数话题，**本模块不考参数**；先做格式约束与示例 | M2-K12 |
| 12 | "Zero-shot 一定比 Few-shot 弱" | ❌ 通用任务 Zero-shot 足够；Few-shot 用于**口径/格式对齐**，不是越强越好 | M2-K03 |
