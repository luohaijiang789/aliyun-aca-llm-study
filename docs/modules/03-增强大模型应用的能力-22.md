```
        场景：模型答不好 / 做不到
                  │
   ① 说不清（表达问题）→ 优化输入（提示词）          ← M2（此类问题的直接办法）
```

### M3-K01　⭐ RAG 的定位：查企业资料用 RAG　🟢`[A]`

**① 一句话定义**：RAG（Retrieval-Augmented Generation，检索增强生成）—— 回答前先去**企业自己的资料库**里检索相关片段，把片段拼进上下文，再让模型基于这些资料生成答案。

**② 是什么**：官方把它定位成「**查企业资料**」的标准手段。它的完整链路是：把企业资料（产品手册、报销制度、合同模板、售后条款、FAQ、历史工单等）接入知识库 → 解析、切分、向量化入库 → 用户提问时检索相关片段 → 片段拼进上下文 → 模型生成答案并可**附出处**。它和「直接问模型」的本质区别是：直接问靠模型**记忆**（训练数据），RAG 靠**查资料**（你喂进去的库）。

**③ 为什么**：官方原话「**模型不是什么都要靠记忆回答……查企业资料用 RAG**」。企业资料有三个致命特征，恰好是模型的短板：① **私域不公开** —— 模型训练数据里根本没有；② **会更新** —— 每隔几个月修订一次；③ **要可追溯** —— 员工要能核实依据。把这三条凑齐，答案只能是 RAG：改文档即刻生效、答案可引用出处、不需要动模型权重。与之相对，官方把「实时数据 / 确定性计算 / 业务动作」划给了工具（见 M3-K03）。

**④ 怎么做 / 怎么用**：某公司的报销制度从未对外公开、每季度修订。员工问「总监级别的差旅住宿标准是多少钱一晚」——**Before**：直接问大模型，它按行业常见值编一个「800 元」，员工信了、财务拒了；**After**：制度文档接入知识库改用 RAG，模型先检索到《差旅管理办法 v3.2》第 4 条，回答「总监级一线城市每晚 900 元上限（来源：差旅管理办法 v3.2 第 4 条）」，员工点开原文即可核验。

**⑤ 易错点**：
- ❌ 常见误解：企业制度几年改一次，干脆**微调**进模型，省得每次检索 → ✅ 正确：**查企业资料用 RAG**。知识进了权重就**不可更新、不可追溯、不可引用出处**，且训完又开始过时。
- ❌ 常见误解：让模型**联网搜索**就能查到公司资料 → ✅ 正确：私域资料**从不公开**，公开网络搜不到；即便搜到相似内容，来源也不可控、不可追溯。

**⑥ 考法提示**：本模块**最高频的题干模板**——「某公司资料只存在于内部系统、从未公开、每隔几个月修订……最合适的做法是？」干扰项固定四个：**微调**（最诱人）、联网工具搜索（判据用错）、把全文写进提示词（上下文窗口 + 成本 + 不可持续）、RAG（正确答案）。看到「**内部 / 私域 / 未公开 / 会更新 / 要可追溯**」任一信号词，直接选 RAG。

**⑦ 记忆锚点**：**「内部资料不用背，翻书答题用 RAG」** —— 类比开卷考试：微调等于把整本书背进脑子（背完还会忘、还不能翻），RAG 等于把书摊在桌上现翻（随时换新版、还能指明第几页）。

### M3-K02　RAG 的定义与解决的三类问题　🟢`[A]`

**① 一句话定义**：RAG = **检索**（从知识库取回相关片段）+ **增强**（把片段塞进上下文）+ **生成**（模型据此作答），让模型「看着资料说话」而不是凭记忆猜。

**② 是什么**：它是一次流程改造：提问进来时**不立刻生成**，而是先做一次检索，把最相关的若干片段与问题拼成一段更长的上下文，再交给模型。因为答案有了**外部依据**，所以能附出处、能核验、能随资料更新而更新。官方把它写进「建议掌握的知识」第一条：「RAG、知识库服务和知识问答系统的基本原理与**质量改进方法**」。

**③ 为什么**：模型本身有三个绕不过去的短板，RAG 一一对应：① **知识缺失**（训练数据里没有你的企业资料）→ 检索补上；② **时效过期**（训练有时间截止点，之后的事不知道）→ 改库即刻生效；③ **幻觉**（没人管得住它编）→ 有依据才答、无依据必须说「未找到」。这也解释了官方那句「模型不是什么都要靠记忆回答」。

**④ 怎么做 / 怎么用**：客服知识问答上线前，用户问「保修期多久」，模型回答「一般一年」（其实是按家电常识猜的，本公司是两年）；接入产品手册做 RAG 后，模型检索到「整机保修 24 个月（人为损坏除外）」，并附上手册页码。**注意**：RAG 是**降低**幻觉，不是**消除**幻觉 —— 生成侧仍可能不老实，所以才需要评测（M3-K08）约束。

**⑤ 易错点**：
- ❌ 常见误解：有了 RAG 就彻底没有幻觉了 → ✅ 正确：RAG **降低**幻觉（减少无依据编造），但不能根除；生成环节仍可能脱离上下文自创，需靠提示词约束「无依据须回答未找到」+ 评测把关。
- ❌ 常见误解：RAG 就是「把资料塞进提示词」 → ✅ 正确：RAG 只喂**检索出来的相关片段**，不是全文；全量塞入会撞上下文窗口上限、成本与延迟都不可接受。

**⑥ 考法提示**：常以「RAG 主要解决什么问题」出**多选**，正确项围绕「补知识 / 时效 / 可追溯 / 抑制幻觉」；干扰项会把「提升模型推理能力」「替代微调改输出格式」「执行业务动作」混进来 —— 这三件事都**不属于 RAG**。

**⑦ 记忆锚点**：**「缺知识找 RAG，缺能力找工具，缺稳定找微调」** —— RAG 只负责「喂什么」，不负责「怎么答」和「怎么干」。

### M3-K03　⭐ 工具的定位：实时数据 / 确定性计算 / 业务动作用工具　🟢`[A]`

**① 一句话定义**：当需求落在「**实时数据**、**确定性计算**、**业务动作**」三条官方判据中的任意一条时，就应该用**工具调用（Tool Calling）**让外部系统去查、去算、去做，而不是让模型自己去答。

**② 是什么**：官方给工具的三条判据，各自对应的病因完全不同：**实时数据**是「数据每分钟都在变，任何入库的瞬间就已成快照」；**确定性计算**是「大模型按概率生成，天然算不准」；**业务动作**是「模型只能输出文字，不会真的去操作系统」。工具的本质是给模型**装上手脚**（可执行能力），而 RAG 是给模型**喂资料**（可参考内容）。

**③ 为什么**：官方原话「**需要实时数据、确定性计算或业务动作时用工具**」。拆开看：
- **判据一 实时数据**：模型训练有截止时间，RAG 知识库也是人工更新写入的静态快照。要「现在的值」，只能去问系统本身。
- **判据二 确定性计算**：模型是逐 token 概率采样，做多位数乘除、多币种换算、折扣税后总额这类要求「一分不差」的活，本质是错配。
- **判据三 业务动作**：模型只能**说**（输出文本），不会**做**（真实写库 / 发信 / 下单）。下单、发邮件、改状态都是**动作**不是**知识**。

**④ 怎么做 / 怎么用**：
- **实时**：「上海仓现在还剩多少台设备」→ Before 用 RAG 查库存清单文档，答的是三小时前的数；After 工具调用库存接口拿当前值，模型只负责把结构化结果说成人话。
- **计算**：「128 件 × 39.9 元，打 8 折再扣 13% 税，应付多少」→ Before 模型心算，几次问出几个数；After 计算 / 结算类接口算出确定值，模型组织语言。
- **动作**：「把周报发给项目组并把任务标记为已完成」→ Before 模型输出一封写好的邮件文本，但发不出去；After 工具对接邮件系统与项目管理系统，真正执行发送与状态变更。

**⑤ 易错点**：
- ❌ 常见误解：「模型算数不准，写个 Chain-of-Thought 提示词让它一步步仔细算」→ ✅ 正确：**确定性计算用工具**。提示词只能规范「怎么答」，不能提供「答得准」。
- ❌ 常见误解：「资料接进知识库了，模型自然能帮我把任务状态改掉」→ ✅ 正确：**RAG 只提供依据，不执行任何动作**；这是 RAG 的能力边界（见 M3-K17）。

**⑥ 考法提示**：本模块**题量最大的考点**（Q002 实时 / Q003 计算 / Q004 动作，各一题）。三条判据**每条都可能单独出题**，切勿只背「实时」一条。干扰项套路：把工具题包装成 RAG 题（B 选项「导出成文档接入知识库」）、包装成微调题（C 选项「用历史数据训练」）、包装成提示词题（D 选项「加更多示例 / 写清楚步骤」）。另外，跨多个系统的多步流程会再往上走一层到 **Agent**（M4），但其中的每一步动作仍靠**工具**。

**⑦ 记忆锚点**：**「要『现在的』、要『算得准的』、要『真的去做的』—— 这三件事都归工具。」** 再配合官方金句：**「查知识用 RAG，做动作靠工具，稳行为才考虑微调。」**

### M3-K04　⭐ RAG 五环节①：解析　🟢`[A]`

**① 一句话定义**：**解析**是把原始资料（PDF / Word / Excel / HTML / 扫描件 / 图片）提取成**干净、可检索的文本**，并尽量保留标题层级、表格行列关系与图表中的有效信息 —— 这是 RAG 的第一道关口。

**② 是什么**：官方把「**解析**」列为 RAG 五环节之首（"理解 RAG 的**解析**、切分、检索、重排序和评测会影响答案质量"）。关键动作包括：格式转换与清洗；**扫描版 PDF / 图片先做 OCR**；**表格按结构提取**而不是拉平成一串字；保留文档元信息（标题、章节、时间、来源）以便引用与过滤。

**③ 为什么**：解析环节是**唯一一个「丢内容就永久丢失」的环节**。后面四个环节（切分、检索、重排、评测）优化的都是「能不能找得准」，而解析决定的是「**库里有没有**」。表格被拉平后「参数名—参数值」的对应关系消失，扫描件未 OCR 则整页变成空内容。再强的 embedding、再大的 top-k，也召不回库里根本没有的东西。

**④ 怎么做 / 怎么用**：某企业把扫描版产品手册入库后，用户问「XX 型号的工作温度范围」总答不上来。排查发现表格被拉平成一串「-20~60℃0.5A24V……」的无结构文本，参数名与参数值彻底脱钩。**Before**：调更大的 chunk、换更强的检索模型，全无效（因为丢了的是结构不是排序）；**After**：改进解析 —— 扫描件补 OCR、表格按行列结构化提取、保留章节标题，重新入库后即正常召回并可精确到单元格。

**⑤ 易错点**：
- ❌ 常见误解：「资料搜不到，肯定是 embedding 模型不行」→ ✅ 正确：先确认**解析有没有把内容提取出来**。前者是「找得不准」，后者是「源头缺失」，两者归因完全不同，混淆必错。
- ❌ 常见误解：「OCR 只是锦上添花，不重要」→ ✅ 正确：扫描件不做 OCR，**整页就是空内容**，属于典型的内容缺失。

**⑥ 考法提示**：高频考法是「现象描述 + 问出在哪个环节」（Q007、Q011）。题干信号词：**扫描版 PDF、表格、行列关系丢失、图片里的文字、OCR**。正确选项必含「改进文件解析后**重新入库**」；干扰项会把你引向换 embedding、调 chunk size、优化提示词。

**⑦ 记忆锚点**：**「解析丢的是命，检索丢的是路。」** —— 命没了，路走得再好也到不了。

### M3-K05　RAG 五环节②：切分　🟢`[A]`

**① 一句话定义**：**切分（chunking）**是把长文档切成便于检索的小片段，并决定**块大小、块间重叠（overlap）与切分依据**。

**② 是什么**：切分要解决的唯一问题是「**每一块自己能不能读懂**」。核心权衡：**chunk 过大** → 上下文完整但噪声多、稀释相关性、挤占上下文窗口；**chunk 过小** → 粒度细但**语义被切断**，前提与结论散落两块。**overlap**（相邻块重复一段文本）用来防止句子 / 表格被从中间切开，代价是存储与检索冗余，适度即可。

**③ 为什么**：检索的基本单位是 chunk。如果一块只包含半个论点，那么无论检索多准，召回的内容都是残缺的，模型拿到手的也是残缺证据 —— 表现为「答案总像缺斤少两」。

**④ 怎么做 / 怎么用**：FAQ / 条目型文档 → **按条目切**（一条问答一块），不要按字数硬切；论述型文档 → 稍大块 + 适当 overlap；表格、代码块、条款清单 → 尽量**整块保留**。判断标准很朴素：把切出来的块单独抽出来读一遍，**看不看标题也能读懂**就 OK。

**⑤ 易错点**：
- ❌ 常见误解：「overlap 越大越好，越大越不怕切断」→ ✅ 正确：overlap 过大带来大量冗余片段，噪声与成本双升，**适度即可**。
- ❌ 常见误解：「答案不完整就把 chunk size 调到最大」→ ✅ 正确：若源头是**表格结构在解析时已被破坏**（M3-K04），块再大也拼不回对应关系。

**⑥ 考法提示**：多以「现象 → 环节 → 改进」匹配题出现（Q011 B 项）。题干信号词：**前提与结论分开、答案只有一半、缺失必要上下文、表格被切开**。干扰项常把「切分」与「重排序」「评测」混写。

**⑦ 记忆锚点**：**「切小了断语义，切大了带噪声；先求单块能读懂，再谈大小。」**

### M3-K06　RAG 五环节③：检索（含向量检索）　🟢`[A]`

**① 一句话定义**：**检索**是根据用户提问，从知识库中找出**相关**的候选片段（粗召回，通常取 top-k）；其中**向量检索**按**语义相似度**召回，能匹配字面不同但含义相近的表述。

**② 是什么**：核心原理三件事：**Embedding（向量化）** —— 用专门的 embedding 模型把文本映射成固定长度的向量，语义相近的文本在向量空间中**距离更近**；**相似度** —— 常用余弦相似度衡量两个向量有多近；**ANN（近似最近邻）** —— 建索引 + 近似搜索，牺牲极小精度换取海量向量上的检索速度。三个易被忽略的事实：① 向量**由专门的 embedding 模型产出**，不是大模型的摘要；② 用户的**提问也要用同一个 embedding 模型**向量化，否则不在同一空间、比较无意义；③ 相似度**高不等于答案对**，还需重排与生成把关。

**③ 为什么**：关键词检索要求**字面必须重合**，遇到「离职手续怎么办」 vs 文档写「员工离司办理流程」就一个词也匹配不上。向量检索突破了这个限制，对同义词、口语化表述更鲁棒。反过来，向量检索**弱于精确**：型号、订单号、专有名词这类需要精确匹配的场景，关键词检索往往更稳 —— 所以工程上常做**混合检索**（关键词 + 向量多路召回后融合）。

**④ 怎么做 / 怎么用**：用户问「离职手续怎么办」→ **Before** 关键词检索命中 0 条，系统答「未找到」；**After** 改用向量检索，成功召回写「员工离司办理流程」的文档，并扩召回 top-k=20 交由重排精挑。优化方向：调优切片、查询改写 / 多路查询、元数据过滤（按时间 / 部门 / 类型先筛）、混合检索、换更适配领域的 embedding 模型、调整 top-k。

**⑤ 易错点**：
- ❌ 常见误解：「向量检索会让大模型先把文档读一遍再凭记忆答」→ ✅ 正确：向量检索依赖**预先构建的索引**做近似查找，既不逐字全文扫描，也不让模型通读全文（那会撞上下文窗口限制，且违背 RAG「只喂相关片段」的思路）。
- ❌ 常见误解：「文档用 A 模型向量化，提问可以直接拿原文去比」→ ✅ 正确：提问必须**同一个 embedding 模型**向量化，两者才在同一空间。

**⑥ 考法提示**：**必考（Q008 单选 + Q009 多选）**。单选往往用一个「字面不匹配但语义匹配」的对照案例，考察你是否知道向量检索的原理；多选则把「同 embedding 模型」「混合检索」「关键词长于精确」与陷阱项（**rerank 能提升召回率**、**调 temperature 提升召回率**）混在一起。

**⑦ 记忆锚点**：**「关键词找字，向量找意思。」** 提问记得用**同一个** embedding 模型 —— 「一把尺子量两边」。

### M3-K07　RAG 五环节④：重排序（rerank）　🟢`[A]`

**① 一句话定义**：**重排序（rerank）**是对粗召回的候选片段，用更精细的方式重新计算「问题 vs 段落」的相关性并**重新打分排序**，取前 n 条进入上下文。

**② 是什么**：检索链路是**两阶段**设计：**粗召回**求「全」且「快」（别漏，允许有噪声）；**重排序**求「准」（别错，把最相关的提到前面）。它处理的对象是**已经召回的候选集**，不是整个知识库。

**③ 为什么**：粗召回为了保证不漏（高召回率），往往用较快但较粗的方式取回几十条候选，其中必然混入噪声。若直接把噪声塞进上下文，会稀释关键信息、增加幻觉来源；而真正相关的片段若排在靠后位置，可能被 top-n 截断或超出上下文窗口而丢失。重排就是在这批候选里做**精挑**。

**④ 怎么做 / 怎么用**：召回 top-50 → rerank 精排 → 取 top-5 进上下文。**Before**（只有召回）：最相关的第 3.2 节排在第 41 位，被截断丢失，答案只能凑合用相近但不准确的条款；**After**（加 rerank）：相关片段提到第 1 位，噪声片段被排到后面，答案准确且能引用出处。

**⑤ 易错点**：
- 🔴 **最经典的陷阱**：「引入 rerank 可以把没召回到的相关片段重新召回，提升召回率」→ ✅ 正确：**rerank 只对「已召回的候选集」重排，不会把没召回的片段变出来**；它提升的是**精确率**，不是**召回率**。召回率不足（相关片段压根没进候选集）必须回到检索 / 切分 / **解析**环节解决。
- ❌ 常见误解：「有了 rerank 就可以不要粗召回」→ ✅ 正确：精排计算代价高，不可能对全库执行，必须先用粗召回把门打开。

**⑥ 考法提示**：几乎每次出 RAG 流程题都会夹一个 rerank 陷阱选项（Q009 D、Q011 C）。看到「提升召回率」「召回更多」「把没找到的找回来」+ rerank，**一律判错**。

**⑦ 记忆锚点**：**「召回负责把门打开，重排负责把人挑出来。」** 门没开，屋里再会挑也没用。

### M3-K08　RAG 五环节⑤：评测　🟢`[A]`

**① 一句话定义**：**评测**是官方点名的 RAG 第五个环节 —— 建立评测集与指标，对**各环节分别打分**，定位答案质量下降到底出在哪一环。

**② 是什么**：评测由两部分组成 —— 一个**有代表性的评测集**（一批带参考答案的真实问题）+ 一组**分层指标**。常见分层：**检索质量**（相关片段有没有进候选集）、**上下文相关性**（召回片段噪声多不多）、**答案忠实度**（答案每句是否有上下文依据）、**答案相关性**（有没有答非所问）。前两项指向检索侧，后两项指向生成侧，这层对应关系是归因的基础。

**③ 为什么**：官方把「评测」与解析、切分、检索、重排序并列列为影响答案质量的环节，用意非常明确：**评测不是为了打分，是为了归因；归因不是为了甩锅，是为了对症下药**。只打总分（如「这套系统 62 分」）无法告诉你该改解析还是改提示词，只能瞎调。

**④ 怎么做 / 怎么用**：先建一个小而**有代表性的评测集**（覆盖高频问题、边界问题、已知易错问题）→ 对每个问题分别在检索层与生成层打分 → 归因（见 M3-K09）→ 对症改 → **回到评测集复测**，形成闭环。**Before**：上线后答案质量差，团队开始凭感觉调 temperature、换模型，两周无改善；**After**：评测集显示 60% 的问题在 top-20 里根本不包含正确的那段 —— 归因到检索侧，改进解析后重入库，命中率翻倍。

**⑤ 易错点**：
- ❌ 常见误解：「评测就是给最终答案打个总分」→ ✅ 正确：只打总分无法定位环节，违背官方把评测列为**独立环节**的用意。
- ❌ 常见误解：「评测是上线后做一次就行的事」→ ✅ 正确：评测是**贯穿全程**的闭环，每次改动后都要回到评测集复测。

**⑥ 考法提示**：常与归因合并出**多选**（Q010、Q011）。陷阱项固定两种：「只打总分即可」（否定归因价值）、「调高 temperature 可以同时解决两侧问题」（混淆检索侧与生成侧）。

**⑦ 记忆锚点**：**「评测是体检报告，不是期末成绩。」** 体检报告要分项目标出异常，才好对症下药；闭环顺序永远是 **建集 → 分环节打分 → 归因 → 改 → 复测**。

### M3-K09　⭐ RAG 评测归因（检索侧 vs 生成侧）　🟢`[A]`

**① 一句话定义**：RAG 答案不好时，**先看检索到的上下文里有没有正确答案**：有却答错 = **生成侧**失败；压根没有 = **检索侧**失败。口诀：**「有而答错是生成，没有可查是检索。」**

**② 是什么**：归因是一刀把链路切成两半：前半条链路（解析 → 切分 → 检索 → 重排）负责「**喂进去**」，后半条（拼上下文 → 生成）负责「**答出来**」。先看上下文，就能立刻排除掉一半的可能性。

**③ 为什么**：因为两侧的对症手段完全不同，**归因错了就是白干**：检索侧要改的是解析、切分、查询改写、混合检索、元数据过滤、embedding、top-k、rerank；生成侧要改的是提示词约束（「仅限上下文，无依据须回答未找到」）、上下文去重压缩、关键片段放首尾、要求带出处、换更强的生成模型、加自检闭环。更重要的是顺序 —— **永远「先检索，后生成」**：检索侧没修好就去调生成参数，等于**对着错误资料优化措辞**，垃圾进、垃圾出。

**④ 怎么做 / 怎么用**：用户问「总监级差旅住宿标准是多少」，系统答「800 元」。Step 1 打开日志看上下文：如果《差旅管理办法 v3.2》第 4 条「900 元」**就在上下文里**而模型答了 800 → **生成侧**（没吃透 / 不老实）→ 优化提示词强约束 + 要求引用出处；如果上下文里**只有 v2.0 的旧条款**甚至完全没有 → **检索侧**（没喂进去）→ 检查该文档是否解析成功、是否最新版、是否被切碎，修好后「900 元」自然出现。

**⑤ 易错点**：
- ❌ 常见误解：「RAG 答错了，先换个更强的生成模型」→ ✅ 正确：**先归因再动手**。如果是检索侧没召回，换再强的模型也无米下锅。
- ❌ 常见误解：「两侧同时优化，一起上线最快」→ ✅ 正确：**先检索、后生成**。检索侧优化成本低、收益明确，且检索侧没通之前，生成侧的调优结论不可信。

**⑥ 考法提示**：本库自编 Q010（多选）与 Q011 用于练习。常见正确项：① 上下文有/无作为分水岭；② 先检索后生成的顺序；③ 检索质量与答案忠实度要**分别**打分。陷阱项：① 调 temperature 能同时解决两侧；② 只打总分；③ 检索侧问题靠微调解决（混淆 RAG 与微调两条链路）。

**⑦ 记忆锚点**：**「先看有没有，再看答没答对。」** 顺序别反：**「先开路（检索），再开车（生成）。」**

### M3-K10　⭐ MCP 的作用与定位　🟢`[A]`

**① 一句话定义**：**MCP** 是一套**标准化的连接协议 / 开放标准**，用来规范「模型或 Agent 如何发现并连接外部的数据源和工具」。它是「**怎么连**」的标准，不是「连上之后能干什么」的工具本身。

**② 是什么**：官方原文「了解 **MCP 的作用，不要求掌握协议细节**」，且「工具调用、MCP 和个人 AI Agent 接入知识库与工具的方法」同属一行 —— 说明官方要你掌握的是**它在其中的角色**：给 Agent / 模型与外部资源之间提供一条**统一对接方式**。

**③ 为什么**：**没有统一标准时**，N 个 AI 应用 × M 个外部工具 / 数据源 = **N×M 个定制集成** —— 每接一个工具都要重新定义一遍描述格式、写一遍对接逻辑，重复建设、无法复用、扩展一个新工具就要改应用。**有了统一标准后**，工具方按标准暴露一次、应用方按标准对接一次，集成量从 N×M 降到 **N+M**，带来**复用、可扩展、生态互通**三个价值。

**④ 怎么做 / 怎么用**：某团队先给 Agent 接了天气工具（自定义对接方式 A），又要接订单系统（对接方式 B）、内部 Wiki（方式 C）。每接一次重学一套写法，且接出来的东西换一个 AI 应用就用不了。改用 MCP 后，工具侧按标准暴露一次，任何支持该标准的应用都能直接发现并使用 —— 「同一个接口标准，什么设备都能插上来用」。

**⑤ 易错点**：
- ❌ 常见误解：「MCP 是一个工具，能查天气查库存」→ ✅ 正确：MCP 是**连接标准**；**被接入的具体工具**才提供查天气、查库存的能力。
- ❌ 常见误解：「有了 MCP，模型就能自己学会使用工具」→ ✅ 正确：标准只解决「接得上、描述得清」；用得好不好仍取决于模型能力与工具描述质量。

**⑥ 考法提示**：本库自编 Q005、Q006 用两种形式练习 MCP：① 直接问 MCP 的作用，正确答案围绕「**标准化连接 / 解决碎片化集成 / 便于复用扩展**」；② 用一句学生的话让你判断对错（「接上 MCP 就能查天气了」）。**官方不要求协议实现细节，仍须看题干问法，不能按词汇机械排除** —— 官方已声明不考协议细节（详见第五章 5.3 考 / 不考清单）。

**⑦ 记忆锚点**：**「MCP ≈ Type-C 接口标准；工具 ≈ 外接设备（U 盘、打印机）。」** 你不会因为插上 Type-C 就说「接口标准帮我打了文件」。

### M3-K11　MCP 与「工具」「Function Calling」的层级关系　🟡`[B]`

**① 一句话定义**：**MCP（连接标准）≠ 工具（能力本体）≠ Function Calling（模型侧调用机制）** —— 三者分处不同层次，通常共存，不存在谁替代谁。

**② 是什么**：从上到下可以排成五层：**L4 Agent**（用这些能力完成任务）→ **L3 MCP**（外部数据源与工具如何被发现、描述、对接）→ **L2 Function Calling**（模型侧把「要调什么、传什么参数」表达成结构化请求）→ **L1 工具**（查天气、查库存、发邮件、改数据库，真正干活的东西）→ **L0 大模型**。另有 **Skill**（作业方法层，属 M4）用来固化重复工作方法，也不是工具。

**③ 为什么**：混淆层级是本模块最典型的丢分点。出题人最喜欢用「有了 X 就不需要 Y」的句式制造替代关系错觉 —— 实际上它们回答的是三个不同的问题：**工具回答「连上后能干什么」；Function Calling 回答「模型怎么表达调用意图」；MCP 回答「怎么被发现、怎么接得上、怎么描述清楚」**。

**④ 怎么做 / 怎么用**：某同学说「我们给 Agent 接上了 MCP，所以它现在能查天气、能查库存了」—— 恰当的评价是：**不正确**。真正提供查天气、查库存能力的是**通过 MCP 接进来的具体工具**；MCP 负责的是让这些工具**接得上、描述得清**。同时它与 Function Calling 不冲突：模型仍需用 Function Calling 表达「我要调用天气工具，参数是杭州」这样的结构化调用意图，只是这个工具的来源与描述是按标准接入的。

**⑤ 易错点**：
- ❌ 常见误解：「有了 MCP 就不需要 Function Calling」→ ✅ 正确：**不同层**，通常共存。
- ❌ 常见误解：「无法判断，取决于 MCP 用哪种传输层协议与报文格式」→ ✅ 正确：**官方明说不要求掌握协议细节**，这类选项不可选。

**⑥ 考法提示**：**Q006**。题干多为「某同学说……最恰当的评价是？」；正确答案必须同时说清「MCP 是连接协议」与「能力来自具体工具」两点。干扰项 C 会直接说反（「MCP 不能连外部系统」），干扰项 D 用协议细节作为判断依据（**已声明不考**）。

**⑦ 记忆锚点**：**「标准不是设备，指挥不是手脚。」** Type-C（MCP）/ 主机发出的调用指令（Function Calling）/ 打印机（工具）/ 干活的人（Agent）。

### M3-K12　知识库服务与知识问答系统的原理与质量改进　🟢`[A]`

**① 一句话定义**：**知识库服务**是把企业资料接入、解析切分、向量化入库并提供检索能力的服务；**知识问答系统**是在它之上，接上模型做「检索 + 生成」并从问答前端呈现给用户的完整应用。

**② 是什么**：官方「建议掌握的知识」原文点名了这条：「RAG、**知识库服务**和**知识问答系统**的**基本原理与质量改进方法**」。基本原理：**企业资料接入 → 解析 → 切分 → 向量化入库 → 用户提问时检索 + 重排 → 片段拼进上下文 → 模型生成 → 附出处**供核验。它和直接问模型的区别一句话：前者靠**查资料**，后者靠**记记忆**。

**③ 为什么**：知识库服务值得做，因为它同时带来三件事：知识**可更新**（改文档即刻生效，不必重训）、答案**可追溯**（可附出处、可核验）、**可抑制幻觉**（有依据才答，无依据须答「未找到」）。这三点恰好命中 M1「幻觉、训练数据时间范围、上下文限制」三大短板。

**④ 怎么做 / 怎么用**：质量改进有且只有一条路径 —— **按官方五环节逐个排查**：解析（别丢内容）→ 切分（别切碎语义）→ 检索（别漏召，必要时混合检索）→ 重排序（把最相关的排前面）→ 评测（先归因再动手）。**Before**：回答不准就换更大的模型；**After**：用评测集归因后发现八成问题在解析与切分，改完之后小模型也能答对。

**⑤ 易错点**：
- ❌ 常见误解：「知识库问答质量不好 = 模型不够强」→ ✅ 正确：**知识库的质量决定答案上限**；资料没解析好，换什么模型都白搭。
- ❌ 常见误解：「知识库就是把文档上传完事了」→ ✅ 正确：上传只是起点，解析、切分、检索、重排、评测五环节才决定答案质量（官方原话）。

**⑥ 考法提示**：多作为**背景题干**渗透在 Q001、Q007、Q011 中，不单独成题。考点落在「原理链路的顺序」和「质量改进该动哪一环」。

**⑦ 记忆锚点**：**「上传不是结束，是开始。」** 五环节逐个查，别一上来就换模型。

### M3-K13　个人 AI Agent 接入知识库与工具的方法　🟢`[A]`

**① 一句话定义**：官方原文「工具调用、MCP 和**个人 AI Agent 接入知识库与工具的方法**」—— 给个人 Agent 接上**知识库**（补知识）与**工具**（补能力），让它从「只能聊天」变成「能查资料、能干活」。

**② 是什么**：两条接入线，一一对应 M3-K01 与 M3-K03 的官方判据：**接入知识库**补的是知识（让 Agent 能回答它本来不知道的企业资料）；**接入工具**补的是能力（让 Agent 能拿实时数据、做确定性计算、执行业务动作）。**通过 MCP 接入**则是提供标准化的连接方式，降低对接与扩展成本。

**③ 为什么**：单有模型的 Agent 既不知道你的企业资料，也没有任何执行能力。官方把它写在本模块的「建议掌握的知识」里，用意是：**Agent 的能力边界 = 它接了什么知识库 + 它能用哪些工具**（这也是 M4 考试内容中「明确目标、资料来源、工具边界」的来源）。

**④ 怎么做 / 怎么用**：给一个「新员工入职助手 Agent」接入：① **知识库** —— 员工手册、考勤制度、报销流程（对应「查企业资料用 RAG」）；② **工具** —— 查询入职当周的工位安排（实时数据）、计算试用期转正日期（确定性计算）、提交 IT 设备申请单（业务动作）；③ 需要时通过 **MCP** 按标准接入这些数据源与工具。三件事**是组合而非三选一**。

**⑤ 易错点**：
- ❌ 常见误解：「Agent 接了知识库就够用了」→ ✅ 正确：知识库只补**知识**；实时数据、确定性计算、业务动作必须靠**工具**。
- ❌ 常见误解：「接入方式和 M3 没关系，那是 M4 的事」→ ✅ 正确：官方把「接入知识库与工具的方法」写在**本模块**（M3），Agent 侧的编排才属 M4。

**⑥ 考法提示**：不作为独立题出现，**渗透在 Q002~Q004 的选型判定里**：凡是「给 Agent 加某项能力」的题干，判据仍是那三条工具判据 + 一条 RAG 判据。

**⑦ 记忆锚点**：**「知识库补脑，工具补手，MCP 统一插口。」**

### M3-K14　官方场景选型手段与选型边界　🟢`[A]`

**① 一句话定义**：官方给出的标准答案池只有六个：**优化输入、接入知识库、调用工具、使用微调、协作 Agent，或保留人工确认**。本模块占据其中两格（接入知识库、调用工具）。

**② 是什么**：见 1.3 决策树。判据与绑定关系：**「说不清」→ 优化输入**；**「查企业资料 / 私域知识」→ 接入知识库（RAG）**；**「实时数据 / 确定性计算 / 业务动作」→ 调用工具**；**「稳行为 / 格式 / 风格 / 分类」→ 微调**；**「从回答问题推进到完成任务」→ 协作 Agent**；**「高风险、需担责」→ 保留人工确认**（贯穿全程，可叠加在任一手段之上）。

**③ 为什么**：官方强调理解大模型**能力边界**并在业务场景中选择合适办法。题干信号词是线索，还要核对数据类型、权限、时效和风险；一道题可要求组合手段。官方金句：**「查知识用 RAG，做动作靠工具，稳行为才考虑微调。」**

**④ 怎么做 / 怎么用**：拿到一道场景题，按三步走：① 是「说不清」还是「做不到」？（前者 → 优化输入）② 若做不到，缺的是**知识**还是**能力**？③ 缺知识 → RAG；缺能力 → 判断是实时 / 计算 / 动作 → 工具；若要多步编排完成任务 → Agent；若高风险 → 叠人工确认。

**⑤ 易错点**：
- ❌ 常见误解：「手段是互斥的，选了一个就不能再选另一个」→ ✅ 正确：**可组合**。例如 RAG 补知识 + 微调定风格 + 工具补能力 + Agent 编排 + 关键动作人工确认，是常见组合。
- ❌ 常见误解：「效果不好就直接上微调 / Agent（越高级越好）」→ ✅ 正确：顺序不能跳。**微调不是万能按钮**，先把低成本的输入优化与 RAG / 工具做透。

**⑥ 考法提示**：**Q001~Q004 每题的底子**。干扰项永远是从相邻手段里挑一个最有迷惑性的（查企业资料给「微调」、确定性计算给「提示词」、跨系统流程给「RAG」）。

**⑦ 记忆锚点**：**「查知识用 RAG，做动作靠工具，稳行为才考虑微调；完成任务上 Agent，高风险留人工确认。」**

### M3-K15　API 关键参数的作用与方向　🟡`[B]`

**① 一句话定义**：调用大模型 API 时，`temperature` / `top_p` 控制输出的**发散程度**，\`max_tokens\` 控制**输出长度上限**；考试**只考作用与方向（调大调小的影响），不考默认数值**。

**② 是什么**：**temperature** —— 控制采样随机性，调大更发散更有创意（也更可能离谱），调小更确定、更保守、更可复现；**top_p** —— 核采样，只从累积概率达到阈值的候选词中选，调大候选更多样，调小更集中稳定；**max_tokens** —— 生成**输出**的长度上限，过小会被截断（答到一半没了），过大则成本与延迟上升。

**③ 为什么**：官方 M3 原文**未提及**这些参数，故本考点为 `[B]` 级了解内容，题主卷出现了批量 API 使用题。理解方向有两个作用：① 能识破「调高 temperature 能提升检索召回率」这类**检索侧 / 生成侧混淆陷阱**（Q009 E、Q010 D）；② 明白**无论怎么调参，模型都无法凭空获得新知识** —— 要补知识请用 RAG。

**④ 怎么做 / 怎么用**：事实问答、RAG 问答、数据抽取 → **调低** temperature（要准确稳定）；创意写作、起名、头脑风暴 → **调高**（要多样性）；输出总被截断 → 调大 max_tokens；想要多次提问结果一致 → 调低 temperature 与 top_p。

**⑤ 易错点**：
- ❌ 常见误解：「调参数能让模型知道训练数据之外的新内容」→ ✅ 正确：**不能**。参数只影响怎么生成，不影响知识范围；补知识走 RAG。
- ❌ 常见误解：「\`max_tokens\` 限制的是输入长度」→ ✅ 正确：它限制的是**输出**。

**⑥ 考法提示**：**不单独出题**。可能以干扰项形态出现（「提高 temperature 以改善检索效果」），看到即判错。

**⑦ 记忆锚点**：**「想要稳就调低，想要花就调高；补知识调参没用，得检索。」**

### M3-K16　批量生成 vs 流式生成　🟡`[B]`

**① 一句话定义**：**批量（一次性返回）**是全部生成完再一次性给结果；**流式（逐段返回）**是边生成边吐片段。判定口诀：**「让人等的用流式，让机器等的用批量。」**

**② 是什么**：**批量**：要等全部完成才有反馈，适合离线批处理、批量摘要、需要拿到**完整结果再做后处理**的场景。**流式**：首字很快出现，等待感低，适合对话式产品与实时交互界面。

**③ 为什么**：官方 M3 原文未提及，属 `[B]` 级了解内容。知道即可，不必深究；它的价值在于识别「这是体验优化，不是能力提升」—— 流式不会让答案更准，批量也不会让答案更聪明。

**④ 怎么做 / 怎么用**：客服对话框（人盯着屏幕）→ **流式**，立刻开始吐字，降低等待感；每晚把当天 5000 条工单批量生成摘要并写入报表 → **批量**，程序拿到完整结果再做后处理。

**⑤ 易错点**：
- ❌ 常见误解：「流式会让答案更准确」→ ✅ 正确：流式只改变**返回方式 / 感知延迟**，不影响生成质量。
- ❌ 常见误解：「批量比流式更省 token」→ ✅ 正确：两者输出内容相同，成本相当；差别在**交付方式**。

**⑥ 考法提示**：**题主卷已经出现批量 API 类题**。若出现，按「人在等 → 流式；程序在等 → 批量」作答。

**⑦ 记忆锚点**：**「人等用流式，机等用批量。」**

### M3-K17　RAG 的局限与不适用边界　🟡`[B]`

**① 一句话定义**：RAG 不是万能的 —— 它**改不了模型的输出风格与格式**、**执行不了任何业务动作**、**受上下文窗口限制**，且**答案质量的上限由知识库质量决定**。

**② 是什么**：四条边界要分清：**① 边界一（动作）** —— RAG 只提供依据，执行动作必须靠工具（Q004）；**② 边界二（形式）** —— 想要稳定输出某种格式 / 语气 / 分类行为，那是**微调**（或先用提示词强约束）的活，往知识库里塞再多示例也解决不了；**③ 边界三（容量）** —— 检索出来的片段要拼进上下文，**上下文窗口有上限**，不是召回越多越好；**④ 边界四（质量）** —— 库里没有 / 被解析丢掉的内容，永远召不回。

**③ 为什么**：理解边界才能正确归因。很多「RAG 效果不好」的抱怨，本质上是把别的问题塞给了 RAG：要它执行动作（边界一）、要它统一格式（边界二）、给它超长上下文（边界三）、喂它没解析好的文档（边界四）。官方五环节的设计，正是让你能逐环节排查而不是一味怪 RAG。

**④ 怎么做 / 怎么用**：用户说「帮我把这笔订单取消掉」→ 这是**动作**，RAG 查再多退货政策也取消不了订单，必须调工具（且按 M4/M6 要求**人工确认**高风险的取消动作）；用户要求「每次都输出固定五段的工单摘要」→ 这是**格式稳定性**，应选提示词强约束 / 微调，而不是往知识库里加更多摘要样本。

**⑤ 易错点**：
- ❌ 常见误解：「RAG 能包治百病，效果不好就是库建得不对」→ ✅ 正确：先判断这是不是**知识问题**。动作、格式、多步编排各有归属。
- ❌ 常见误解：「召回片段越多答案越好」→ ✅ 正确：过多片段会稀释关键信息、挤爆上下文窗口，还会引入噪声增加幻觉；应靠**重排序**取精。

**⑥ 考法提示**：**渗透在 Q004、Q010** 中，多以干扰项（「用 RAG 执行……」）或正确解析的一部分出现。

**⑦ 记忆锚点**：**「RAG 只会翻书，不会动手；只会给你资料，不会替你说话。」**

## 四、⭐⭐ RAG vs 工具：官方选型判据专章（本模块最高频考法）

### 4.1 官方一句话总原则

> **「模型不是什么都要靠记忆回答。」**
> **「查企业资料用 RAG，需要实时数据、确定性计算或业务动作时用工具。」**

这句话可以直接拆成一张判据表 —— **本模块 11 题里至少 4 题是照着这张表出的**（Q001~Q004）。

### 4.2 官方判据对照表（必背）

| | **RAG（接入知识库）** | **工具调用** |
|---|---|---|
| **官方判据** | **查企业资料** | **实时数据** ／ **确定性计算** ／ **业务动作** |
| 本质 | **喂知识**（给模型参考资料） | **装手脚**（给模型可执行能力） |
| 解决的是 | 「模型**不知道**」 | 「模型**做不到 / 拿不到 / 算不准**」 |
| 数据性质 | **静态**的企业资料（产品手册、制度、合同模板、FAQ） | **动态**的外部系统数据（库存、天气、汇率、订单状态） |
| 输出 | 一段有依据、可附出处的**回答** | 一次**查询 / 计算 / 操作**及其结果 |
| 官方归्परिणाम | 回答**内容** | **结果 / 动作已经真实发生** |
| 典型场景 | 报销制度问答、产品手册问答、内部 SOP 检索 | 查实时库存、精确算税、下单、发邮件、改数据库记录 |
| 归属模块 | **M3** | **M3**（编排进流程后是 M4 Agent） |

### 4.3 三条「用工具」判据，逐条拆开看

| 判据 | 官方原词 | 为什么模型自己不行 | 举例 |
|---|---|---|---|
| **判据一** | **实时数据** | 模型训练有截止时间，且知识库入库的瞬间就已成快照 | 「上海仓现在还剩多少台设备」「今天杭州什么天气」「当前汇率多少」 |
| **判据二** | **确定性计算** | 大模型按概率生成，**算得不准**；金额、税率、库存扣减这类要求「一分不差」的计算不能交给它猜 | 「128 件 × 39.9 元，打 8 折再扣 13% 税，应付多少」「这批订单的总额和平均交付时长」 |
| **判据三** | **业务动作** | 模型只能**输出文字**，不会真的去操作系统；下单、发邮件、改数据库都是**动作**，不是**知识** | 「帮我提交请假单」「把这份周报发给项目组」「把该任务标记为已完成」 |

> **一句话记忆：要「现在的」、要「算得准的」、要「真的去做的」—— 这三件事都归工具。**

## 五、⭐ MCP 的作用专章（官方明列在本模块）

### 5.1 MCP 是什么（一句话，背这句就够）

> **MCP 是一套标准化的连接协议 / 开放标准，用来规范「模型或 Agent 如何发现并连接外部的数据源和工具」。**
> **它是「怎么连」的标准，不是「连上之后能干什么」的工具本身。**

> 📜 **官方原文出处**：考试内容 3「了解 **MCP 的作用，不要求掌握协议细节**」；建议掌握的知识「**工具调用、MCP** 和个人 AI Agent 接入知识库与工具的方法」。

### 5.2 它解决什么问题（这是官方要求掌握的全部内容）

**没有统一标准时**：N 个 AI 应用 × M 个外部工具 / 数据源 = **N×M 个定制集成**。每接一个工具都要写一遍对接代码、定义一遍描述格式，重复建设、无法复用。

**有了统一标准后**：工具方按标准暴露一次，应用方按标准对接一次，集成量从 N×M 降到 **N+M**。

| 维度 | 没有 MCP（碎片化集成） | 有 MCP（标准化连接） |
|---|---|---|
| 对接成本 | 每个应用 × 每个工具都要定制 | 各方按同一套标准对接一次 |
| 工具复用 | 为 A 应用写的工具，B 应用用不了 | 按标准实现的工具可被多个应用复用 |
| 扩展新工具 | 要改应用代码 | 按标准接入即可被发现和使用 |
| 生态 | 各自为战 | 工具与应用可自由组合 |

### 5.3 考到什么程度（⚠️ 官方给了明确上限）

> **官方原文：「了解 MCP 的**作用**，**不要求掌握协议细节**。」**

| ✅ 考（掌握作用与定位即可） | ⛔ **不考（官方明说不要）** |
|---|---|
| MCP **解决什么问题**（碎片化集成 / N×M → N+M） | 握手流程、连接建立过程 |
| MCP 的**定位**（标准化连接协议，**不是工具**） | 报文格式、JSON-RPC 等消息格式 |
| 有了 MCP 带来**什么价值**（复用、可扩展、生态互通） | 传输层实现（stdio / SSE / HTTP 之类） |
| MCP 与**工具、Function Calling 的层级区别** | SDK、配置项、服务端开发、注册流程 |
| 「个人 Agent 通过它接入外部数据源与工具」这一用途 | 任何要求写出 / 识别协议字段的内容 |

> **做题提示**：只要选项里出现「传输层」「报文」「握手」「JSON-RPC」「协议字段」这类词，通常不是本模块问“作用”时的正确答案；应看题干问法 —— 官方不考实现细节。

### 5.4 MCP 与「工具」「Function Calling」的层级关系

```
  L4  执行体：Agent（用这些能力去完成任务）
              │
  L3  连接标准：MCP（外部数据源与工具如何被「发现、描述和对接」）
              │
  L2  调用机制：Function Calling（模型侧 —— 把「要调什么、传什么参数」表达成结构化请求）
              │
  L1  能力本体：工具（查天气、查库存、发邮件、改数据库 —— 真正干活的东西）
              │
  L0  大模型
```

| 概念 | 在哪一层 | 回答的问题 | ❌ 常见误解 |
|---|---|---|---|
| **工具** | L1 能力本体 | **连上之后能干什么** | 「MCP 就是一个工具」 |
| **Function Calling** | L2 模型侧机制 | **模型怎么表达调用意图** | 「有了 MCP 就不需要 Function Calling」（不同层，通常共存） |
| **MCP** | L3 连接标准 | **怎么被发现、怎么接得上、怎么描述清楚** | 「MCP 能让模型自己学会用工具」 |
| **Skill**（M4） | 作业方法层 | **重复的工作方法怎么固化下来** | 「Skill 就是工具」 |

> **类比速记：MCP ≈ Type-C 接口标准；工具 ≈ 外接设备（U 盘、打印机）；Function Calling ≈ 系统发出的调用指令；Agent ≈ 用电脑干活的人。**
> 接口标准不是 U 盘本身，但你有了统一的 Type-C，什么设备都能插上来用。

### 5.5 易错判断表

| 说法 | 判断 | 说明 |
|---|:---:|---|
| MCP 是一个可以查天气的工具 | ❌ | MCP 是**连接标准**；查天气是被接入的**具体工具** |
| MCP 解决了模型与外部数据源、工具对接的碎片化问题 | ✅ | 这是官方要求掌握的**作用** |
| 有了 MCP，模型就能自己学会使用工具 | ❌ | 标准只解决「接得上、描述得清」；用得好不好仍取决于模型能力与工具描述质量 |
| MCP 可以替代 RAG | ❌ | 两者完全不同层：RAG 是**补知识**的方法，MCP 是**连接外部资源**的标准；查企业资料仍用 RAG |
| MCP 可以替代 Function Calling | ❌ | 不同层次：**连接侧** vs **模型侧**，通常共存 |

| 个人 Agent 可以通过 MCP 接入知识库与工具 | ✅ | 官方「建议掌握的知识」点名：**工具调用、MCP** 和个人 AI Agent 接入知识库与工具的方法 |

## 六、⭐ RAG 五环节专章（按官方口径重排）

> **官方原文：「理解 RAG 的**解析、切分、检索、重排序和评测**会影响答案质量。」**
> ⚠️ 考试以官方这五个词为准。工程上完整链路还包含「向量化、入库、拼上下文、生成」，但**官方点名的影响环节就是这五个**，多选题按官方口径作答。
> 🎯 **顺序必背：解析 → 切分 → 检索 → 重排序 → 评测**（漏掉「解析」是本模块最常见的丢分项）。

```
┌──────────────── 离线：资料入库（一次做好，反复使用）────────────────┐
│                                                                    │
│   企业资料 → ①解析 → ②切分 → （向量化 → 入库建索引）                 │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────── 在线：查询应答（每次提问都跑一遍）────────────────┐
│                                                                  │
│   提问 → ③检索（粗召回 top-k）→ ④重排序（精排 top-n）→ 拼上下文 → 生成 │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────── 贯穿全程 ────────────────┐
│  ⑤评测：建评测集 → 分环节打分 → 归因 → 对症下药 │
└──────────────────────────────────────────┘
```

### 6.1 ① 解析

| 项目 | 内容 |
|---|---|
| **做什么** | 把原始资料（PDF / Word / Excel / HTML / 扫描件 / 图片）**提取成干净、可检索的文本**，并尽量保留**标题层级、表格的行列关系、图片与图表中的有效信息** |
| **关键动作** | 格式转换与清洗；**扫描版 PDF / 图片需先做 OCR**；表格要按结构提取而不是拉平成一串字；保留文档元信息（标题、章节、时间、来源） |
| **做不好会怎样** | 🔴 **内容在源头就丢了，后面检索再怎么优化也永远召不回**；表格被拉平后「参数名—参数值」的对应关系消失，答非所问；扫描件未 OCR 则整页变成空内容 |
| **优化方向** | 选用更合适的解析方式；扫描件补 OCR；表格 / 清单按结构化提取并保留行列关系；保留标题层级与出处元信息，便于后续引用与过滤。**改完需重新入库** |
| **易错** | 把「解析丢内容」误判成「切分不好」或「embedding 不行」—— 前者是**源头缺失**，后两者只是**找得不准** |

### 6.2 ② 切分

| 项目 | 内容 |
|---|---|
| **做什么** | 把长文档切成便于检索的小片段（chunk），并决定块大小、块间重叠（overlap）与切分依据 |
| **关键权衡** | **chunk 过大**：上下文完整但噪声多、稀释相关性、占用上下文窗口；**chunk 过小**：粒度细但**语义被切断**，前提与结论散落两块 |
| **overlap 的作用** | 相邻块之间保留一段重复文本，**防止一句话 / 一个表格被从中间切开导致两头都不可用**；代价是存储与检索冗余，适度即可 |
| **做不好会怎样** | 召回的片段「只有一半意思」；答案看起来总像缺斤少两 |
| **优化方向** | FAQ / 条目型文档 → **按条目切**，不要按字数硬切；论述型文档 → 稍大块 + 适当 overlap；表格、代码块 → 尽量**整块保留** |
| **一句话** | **先保证「切出来的每一块自己能读懂」，再谈块大小。** |

### 6.3 ③ 检索（含向量检索）

| 项目 | 内容 |
|---|---|
| **做什么** | 根据用户提问，从知识库中找出**相关**的候选片段（粗召回，通常取 top-k） |
| **核心原理** | **Embedding（向量化）**：用专门的 embedding 模型把文本映射成固定长度的向量，语义相近的文本在向量空间中距离更近；**相似度**：常用余弦相似度衡量两个向量有多近；**ANN（近似最近邻）**：建索引 + 近似搜索，牺牲极小精度换取海量向量上的检索速度 |
| **为什么需要向量检索** | 突破关键词检索「**字面必须重合**」的限制：「离职手续怎么办」能召回写「员工离司办理流程」的文档；对同义词、口语化表述更鲁棒 |
| **做不好会怎样** | 相关段落**根本进不了候选集**（检索侧失败）→ 答案只能答「未找到」或开始编 |
| **优化方向** | 调优切片；**查询改写 / 多路查询**；**元数据过滤**（按时间 / 部门 / 类型先筛）；**混合检索**（向量 + 关键词）；更换更适配领域的 embedding 模型；调整 top-k |
| **易错** | ① 向量**不是**大模型生成的摘要，由专门的 embedding 模型产出；② 用户的**提问也要用同一个 embedding 模型**向量化；③ 相似度**高不等于答案对**，还需重排与生成把关 |

> **混合检索结论**：向量检索长于语义、弱于精确；关键词检索长于精确（型号、订单号、专有名词）、弱于语义。**单一路径都有短板，工程上常做「关键词 + 向量」多路召回后融合。**

### 6.4 ④ 重排序（rerank）

| 项目 | 内容 |
|---|---|
| **做什么** | 对粗召回的候选片段，用更精细的方式重新计算「问题 vs 段落」的相关性并**重新打分排序**，取前 n 条进入上下文 |
| **两阶段设计** | **召回求「全」且「快」**（别漏，允许有噪声）；**重排求「准」**（别错，把最相关的提到前面） |
| **做不好会怎样** | 真正相关的片段排在**靠后位置**，被 top-n 截断或超出上下文窗口而丢失；噪声片段混进上下文 → 稀释关键信息、增加幻觉来源 |
| **优化方向** | 引入 rerank 模型；调整候选集大小（k）与进入上下文的条数（n）；关键片段尽量放在上下文首尾 |
| 🔴 **高频陷阱** | **rerank 只对「已召回的候选集」重新排序，不会把没召回到的片段变出来**，因此它**提升的是精确率，不是召回率**。检索侧「压根没召回」必须回到检索 / 切分 / 解析环节解决 |

> **一句话：召回负责把门打开，重排负责把人挑出来。**

### 6.5 ⑤ 评测

| 项目 | 内容 |
|---|---|
| **做什么** | 建立评测集与指标，对 RAG 各环节分别打分，**定位答案质量下降到底出在哪一环** |
| **为什么必须有** | 官方把「评测」列为影响答案质量的五个环节之一 —— **评测不是为了打分，是为了归因；归因不是为了甩锅，是为了对症下药** |
| **常见分层** | **检索质量**（相关片段有没有进候选集）、**上下文相关性**（召回的片段噪声多不多）、**答案忠实度**（答案每句是否有上下文依据）、**答案相关性**（有没有答非所问） |
| **做不好会怎样** | 出问题只能「瞎调」：检索侧没修好就去调生成参数，等于**对着错误资料优化措辞**（垃圾进，垃圾出） |
| **优化方向** | 先建小而有代表性的评测集；分环节打分；先归因（见第七章）再动手；改完**回到评测集复测**，形成闭环 |
| **易错** | 「评测就是给最终答案打个总分」❌ —— 只打总分无法定位环节，违背官方把评测列为独立环节的用意 |

### 6.6 五环节速查表（「症状 → 环节 → 手段」，考前扫一眼）

| 典型症状 | 出问题的环节 | 对症手段 |
|---|---|---|
| 扫描件 / 表格 / 图片里的内容怎么也搜不到 | **解析** | OCR、按结构提取表格、保留标题层级，**重新入库** |
| 答案的前提与结论分家、总言之缺一半 | **切分** | 调整块大小、加 overlap、按条目 / 整块保留 |
| 同义表述（「离职手续」vs「员工离司」）召回不了 | **检索** | 换用 / 加强向量检索、查询改写、混合检索、调 top-k |
| 相关内容被召回但排在很后面，进上下文前被截断 | **重排序** | 引入 rerank 重排候选集 |
| 不知道该改哪一环 / 上线后瞎调 | **评测** | 建评测集、分环节打分、先归因再动手、改完复测 |

## 七、RAG 评测归因专章（检索侧 vs 生成侧）

### 7.1 归因总原则：一句话切断两半

```
                RAG 答案质量不好
                        │
            第 1 步：把「检索到的上下文」拿出来看
                        │
                ┌───────┴───────┐
                ▼               ▼
        上下文里【有】答案     上下文里【没有】答案
                │               │
                ▼               ▼
        【生成侧失败】        【检索侧失败】
          看到了还答错         压根没喂进去
```

> **口诀：有而答错是生成，没有可查是检索。**

### 7.2 两侧对照表（必背）

| | **检索侧失败** | **生成侧失败** |
|---|---|---|
| **现象** | 召回的片段里**根本没有**正确答案 | 正确答案**就在上下文里**，模型还是答错 / 答漏 / 自创 |
| **通俗说法** | 没喂进去 | 喂进去了没吃透 / 不老实 |
| **关注指标** | 召回率 / 命中率（Recall@k）：相关片段有没有进候选集 | **忠实度**：答案是否严格来自上下文；**答案相关性**：是否答非所问 |
| **典型原因** | 解析丢了内容、切片把答案切断、embedding 不适配领域黑话、提问与文档表述不一致、k 太小、未做元数据过滤被相似文档干扰 | 提示词没约束「只依据上下文」、上下文噪声太多稀释关键信息、模型能力不足、上下文过长导致「中间遗忘」、多条片段冲突时模型乱合并 |
| **对症手段** | ① 改进**解析**<br>② 调**切分**策略<br>③ 查询改写 / 多路查询<br>④ 混合关键词检索<br>⑤ 元数据过滤<br>⑥ 换 embedding 模型<br>⑦ 加 rerank、调 top-k | ① 优化提示词（明确「仅限上下文，无依据须回答『未找到』」）<br>② 上下文去重 / 压缩 / 关键片段放首尾<br>③ 要求带引用出处，便于核验<br>④ 换更强的生成模型<br>⑤ 加入自检闭环（核对答案是否有依据） |
| **成本** | 相对低，**先做** | 相对高，**后做** |

### 7.3 归因的正确顺序

> **永远「先检索，后生成」：**
> 检索侧没修好就去调生成参数，等于对着错误资料优化措辞 —— **垃圾进，垃圾出**。
> 只有确认「相关资料稳定能被召回到」之后，再去优化生成侧才有意义。

### 7.4 归因实操四步（背下来，考场直接套）

| 步骤 | 动作 | 目的 |
|:---:|---|---|
| **① 看上下文** | 把这次召回的片段调出来，看正确答案在不在里面 | 一刀切分检索侧 / 生成侧 |
| **② 定环节** | 若在检索侧，继续往前追：解析丢了？切碎了？检索漏了？排序错了？ | 精确定位到五环节某一环 |
| **③ 对症改** | 按 6.6 速查表选择手段 | 避免瞎调 |
| **④ 回评测集复测** | 改动后重跑评测集，确认指标确实提升 | 形成闭环，防止顾此失彼 |

## 八、知识库服务 / 知识问答系统 / 个人 AI Agent 接入 / API 参数与生成方式

### 8.1 知识库服务与知识问答系统

| 要点 | 内容 |
|---|---|
| **基本原理** | 把企业资料（**企业资料** = 产品手册、制度规范、FAQ、合同模板、历史工单等）接入知识库 → 解析、切分、向量化入库 → 用户提问时检索 + 重排 → 将片段拼进上下文交给模型生成 → **附出处**供核验 |
| **和直接问模型的区别** | 直接问模型靠「**记忆**」（训练数据），知识库问答靠「**查资料**」—— 模型不必什么都靠记忆回答 |
| **质量改进方法** | 就是官方点名的五环节：**解析**（别丢内容）→ **切分**（别切碎语义）→ **检索**（别漏召）→ **重排序**（把最相关的排前面）→ **评测**（先归因再动手） |
| **为什么值得做** | 知识**可更新**（改文档即刻生效）、答案**可追溯**（附出处）、**可抑制幻觉**（有依据才答，无依据说「未找到」） |
| 🔴 **局限** | **知识库质量决定答案上限**；RAG 不执行动作、不改输出格式、受上下文窗口限制（详见 M3-K17） |

### 8.2 个人 AI Agent 接入知识库与工具（官方原文点名）

> 官方：「**工具调用、MCP** 和个人 AI Agent 接入**知识库与工具**的方法。」

| 接入对象 | 补的是什么 | 对应官方判据 |
|---|---|---|
| **接入知识库** | 补**知识** —— 让 Agent 能回答它本来不知道的企业资料 | **查企业资料用 RAG** |
| **接入工具** | 补**能力** —— 让 Agent 能拿到实时数据、做确定性计算、执行业务动作 | **实时数据 / 确定性计算 / 业务动作用工具** |
| **通过 MCP 接入** | 提供**标准化的连接方式**，降低对接与扩展成本 | **了解 MCP 的作用，不考协议细节** |

> **组合是常态**：一个能干活的 Agent 通常是「**知识库（补知识）+ 工具（补能力）+ MCP（标准化连接）**」三件事一起上，而不是三选一。

### 8.3 API 关键参数与生成方式（🟡 官方未在本模块点名，概念辨识要会）

#### 8.3.1 三个常见参数：只考**作用与方向**，⛔ **不考默认数值**

| 参数 | 作用 | 调大 → | 调小 → |
|---|---|---|---|
| **temperature** | 控制采样的随机性 | 更**发散**、更有创意，也可能更离谱 | 更**确定**、更保守、更可复现 |
| **top_p** | 核采样：只从累积概率达到阈值的候选词中选 | 候选集更大 → 更**多样** | 候选集更小 → 更**集中 / 稳定** |
| **max_tokens** | 生成**输出**的长度上限 | 允许更长输出，成本与延迟上升 | 可能被**截断**（答到一半没了） |

| 场景 | 方向 |
|---|---|
| 事实问答、RAG 问答、数据抽取 | **调低** temperature（要准确稳定） |
| 创意写作、起名、头脑风暴 | **调高** temperature（要多样性） |
| 输出总是被截断 | 调大 **max_tokens** |
| 想要多次提问结果一致 | **调低** temperature 与 top_p |

> ⚠️ `max_tokens` 限制的是**输出**，不是输入。⛔ 本认证**不考任何参数的默认数值**。
> 🔴 无论怎么调参，模型都**无法凭空获得训练数据之外的新知识** —— 要补知识请用 **RAG**。

#### 8.3.2 批量生成 vs 流式生成

| | 批量（一次性返回） | 流式（逐段返回） |
|---|---|---|
| 返回方式 | 全部生成完**一次性**给结果 | 边生成边返回，**逐步吐出** |
| 感知延迟 | 要等全部完成才有反馈 | 首字很快出现，等待感低 |
| 适合 | 离线批处理、批量摘要、需拿到完整结果再做后处理 | 对话式产品、实时交互界面 |

> **判定口诀：让人等的用流式，让机器等的用批量。**

## 九、易错辨析表

### 9.1 手段辨析：到底该用哪个（按官方判据重写）

| 场景 | 常见错误答案 | ✅ 正解 | 理由（官方依据） |
|---|---|---|---|
| 员工问公司最新的差旅报销标准 | 微调 | **RAG** | **查企业资料用 RAG**；知识可更新、可追溯 |
| 模型不知道上周刚修订的退货政策 | 微调 | **RAG** | 时效知识靠检索，不靠训练 |
| 问「上海仓现在还剩多少台设备」 | RAG | **工具** | **实时数据**用工具（判据一） |
| 要求金额、税率、折扣算得分毫不差 | 更仔细的提示词 | **工具** | **确定性计算**用工具（判据二） |
| 「帮我把周报发给项目组 / 提交请假单」 | RAG / 提示词 | **工具** | **业务动作**用工具（判据三） |
| 输出的 JSON 格式忽对象忽数组 | RAG | **提示词强约束 → 微调** | 这是**行为 / 格式**问题，不是知识问题 |
| 要模型一直用客服话术、语气稳定 | RAG | **微调** | 稳**行为 / 风格**才考虑微调 |
| 要跨 5 个系统完成一次退款全流程 | RAG / 工具 | **Agent**（高风险动作人工确认） | 多步编排 + 多工具调度 |
| 回答泛泛而谈、抓不住重点 | RAG / 微调 | **优化输入（提示词）** | 当前根因是表达不清，优先改输入 |
| 解释合同条款、给出医疗 / 金融建议 | 直接采纳 AI 结论 | **RAG 查资料 + 保留人工确认** | AI 可辅助整理起草，**不能替代最终责任人** |
| 想让搜索能召回「员工离司流程」来回答「离职手续怎么办」 | 加更多数据微调 | **向量检索（语义召回）** | 关键词字面不匹配，需语义匹配 |
| RAG 答错就想换生成模型 | 直接换模型 | **先归因**：看上下文里有没有答案 | 可能是检索侧没召回，换模型无效 |
| Agent 接了 MCP 就说「能查天气了」 | 认同 | **纠正**：能力来自具体工具 | MCP 是连接标准，不是工具 |

### 9.2 概念辨析

| 对比项 | A | B | 判据 |
|---|---|---|---|
| **RAG vs 工具** | 查**企业资料**（静态、可追溯） | 要**实时 / 算准 / 做事** | 官方原话：查企业资料用 RAG，实时数据、确定性计算或业务动作用工具 |
| **RAG vs 微调** | 补**知识**，改「喂什么」 | 改**行为 / 格式 / 风格**，改「怎么答」 | 改资料内容是 RAG，改说话方式是微调 |
| **MCP vs 工具** | **连接标准**（怎么连） | **能力本体**（连上后能干什么） | MCP ≈ Type-C 标准，工具 ≈ 外接设备 |
| **MCP vs Function Calling** | **连接侧**（资源如何被发现与对接） | **模型侧**（如何把调用意图说清楚） | 不同层次，通常共存，不是替代关系 |
| **解析 vs 切分** | 源头**提取内容**（丢了就永远召不回） | **切块粒度**（影响语义完整性） | 先有内容，再谈切得好不好 |
| **召回 vs 重排** | 求「全」与「快」 | 求「准」 | 别漏的是召回，别错的是重排；**rerank 不提升召回率** |
| **chunk 过大 vs 过小** | 噪声多、稀释相关性、浪费窗口 | 语义断裂、前提与结论分离 | 先看切出来的块能不能独立读懂 |
| **检索侧 vs 生成侧** | 上下文里**没有**答案 | 上下文里**有**答案却答错 | 先检索后生成 |
| **temperature 高 vs 低** | 发散、创新、不稳定 | 确定、稳定、可复现 | 事实问答调低，创意写作调高 |
| **max_tokens** | 限制**输出**长度，过小会截断 | — | 不是输入限制 |

### 9.3 判断题速记（对 / 错）

| 说法 | 判断 |
|---|---|
| 查企业内部的资料，应该用 RAG | ✅ **官方原话** |
| 需要实时数据、确定性计算或业务动作时，应该用工具 | ✅ **官方原话** |
| MCP 是一个具体的工具，能直接查天气查库存 | ❌ MCP 是**标准化连接协议**；工具才是执行能力 |
| 考试要求掌握 MCP 的协议实现细节 | ❌ **官方明说不要求掌握协议细节** |
| RAG 的解析、切分、检索、重排序和评测会影响答案质量 | ✅ **官方原话（背下来）** |
| 解析环节做不好，后面检索再优化也召不回 | ✅ 内容在源头就丢了 |
| 引入 rerank 能把没召回到的片段重新召回 | ❌ rerank 只重排候选集，**不扩大召回范围** |
| 向量检索能匹配同义词和语义相近的表述 | ✅ |
| 提问时必须使用与文档相同的 embedding 模型 | ✅ 否则不在同一向量空间 |
| 有了 RAG 就不需要微调 | ❌ 可组合：RAG 补知识 + 微调定风格 |
| chunk overlap 越大越好 | ❌ 会引入冗余，适度即可 |
| RAG 答错时，应先检查检索到的上下文 | ✅ 这是归因第一步 |
| 关键词检索在处理专有名词、订单号时可能优于向量检索 | ✅ 所以常做混合召回 |
| RAG 可以完全消除幻觉 | ❌ **降低**，不能消除（生成侧仍可能编） |
| 有了 MCP 就不需要 RAG 了 | ❌ 完全不同层：补知识仍是 RAG |
| 调低 temperature 能让模型学到新知识 | ❌ 调参不改变知识范围，补知识用 RAG |

## 十、⭐ 本模块高频陷阱 TOP 10

> 按丢分频率排序。**这 10 条覆盖了本模块绝大多数失分点，考前必看。**

| # | 陷阱 | ❌ 典型错误想法 | ✅ 正解（官方口径） |
|:---:|---|---|---|
| 1 | **企业资料 → 微调** | 「把公司制度 / 产品手册微调进模型，它就知道了」 | **查企业资料用 RAG**。知识进权重会过时、**不可追溯**、不可引用出处 |
| 2 | **实时数据 → RAG** | 「把库存 / 天气数据导成文档入库」 | **实时数据用工具**。入库的瞬间就是快照，永远慢一步 |
| 3 | **确定性计算 → 提示词** | 「写个详细提示词让它一步步仔细算」 | **确定性计算用工具**。模型按概率生成，算不准是本质缺陷 |
| 4 | **业务动作 → RAG** | 「资料接进知识库了，模型自然能帮我提交订单」 | **业务动作用工具**。RAG 只提供依据，**不执行任何动作** |
| 5 | **rerank 提升召回率** | 「加个 rerank，漏召回的段落就能找回来」 | rerank 只**重排候选集**，提升**精确率**；召回问题回检索 / 切分 / **解析** |
| 6 | **MCP = 工具** | 「接上 MCP，Agent 就能查天气查库存了」 | MCP 是**连接标准**；能力来自**被接入的具体工具** |
| 7 | **MCP 协议细节是考点** | 「要看传输层 / 报文 / 握手才能判断」 | 官方：**不要求掌握协议细节**；出现这类词的选项**一律不选** |
| 8 | **RAG 五环节漏「解析」** | 只背「切分、检索、重排、评测」 | 官方顺序：**解析 → 切分 → 检索 → 重排序 → 评测**（第一个最容易漏） |
| 9 | **调 temperature 改善检索** | 「提高 temperature 能召回更多相关片段」 | temperature 只作用于**生成**随机性，对检索**毫无影响**；且会让答案更容易编造 |
| 10 | **评测 = 打总分** | 「评测就是给最终答案打个分」 | 评测是为了**归因**：必须**分环节打分**（检索质量 / 上下文相关性 / 答案忠实度 / 答案相关性），且**先检索后生成** |

> 🔻 **两个次级陷阱（出现频率略低但同样致命）**：
> - **「把资料全文塞进提示词」** —— 撞上下文窗口上限、每次重复传输、资料更新不可持续；RAG 的价值正是**只喂相关片段**。
> - **「换更强的生成模型解决一切」** —— 先归因。检索侧没召回，再强的模型也无米下锅（**垃圾进，垃圾出**）。

## 十四、顺序题 1～150 增补记忆卡（题库扩展区）

### 14.1 RAG 全链路必须能默写

`文档解析 → 清洗 → 切分 → 向量化/建索引 → 查询表示 → 召回 → 过滤 → 重排 → 拼接上下文 → 生成 → 引用与评估`

考试题若问“哪里出问题”，先把问题放回链路：

- 文档没解析出来 → 解析问题。
- 相关片段没有进入候选 → 召回问题。
- 候选有正确片段但排名靠后 → 重排问题。
- 正确证据已进上下文仍答错 → 生成忠实度问题。
- 知识库没有该知识 → 不是调阈值能解决，应补数据或明确无法回答。

### 14.2 切分、滑窗和长文档

| 参数/方法 | 调大后的常见影响 | 风险 |
|---|---|---|
| Chunk 大小 | 单块语义更完整 | 噪声增多、定位变粗、占上下文 |
| Chunk 重叠 | 跨边界信息保留更多 | 冗余和索引成本增加 |
| 滑动窗口 | 提高边界内容覆盖 | 产生重复片段 |
| 文档摘要 | 压缩上下文 | 可能丢细节 |

原则：不是越大越好，应按文档结构、问题粒度和上下文预算评测。

### 14.3 召回增强方法

| 方法 | 核心动作 | 最适合的题干 |
|---|---|---|
| Multi-Query | 生成多个相关查询，从不同角度召回 | 问法多样、原查询覆盖不足 |
| Decomposition | 把复杂问题拆成多个子问题 | 多跳、复合问题 |
| Step-back | 先抽象出更高层问题再检索 | 原问题过细、缺背景 |
| RAG-Fusion | 多路检索后融合排序 | 多查询结果需要合并 |
| CRAG | 评估检索质量，低置信时纠正或补充 | 检索结果不可靠 |
| Hybrid Search | 关键词 + 向量检索 | 专有名词与语义同时重要 |

**口诀：多问扩面，拆问解难，退一步找背景，融合去重排，低分再纠正。**

### 14.4 向量、BGE、阈值与 Top-K

- **Embedding/BGE**：把文本转成向量，用于语义相似度检索；不是生成答案的模型。
- **相似度阈值升高**：通常召回更少、更严格；过高会漏召回。
- **阈值降低**：通常召回更多；噪声和无关片段可能增加。
- **Top-K 增大**：候选更多，召回可能提高，但上下文噪声和成本增加。
- **Rerank**：对候选按查询相关性重新打分排序，不负责产生新知识。

### 14.5 RAG、工具、Prompt、微调怎么选

| 需求 | 首选 |
|---|---|
| 企业内部、经常更新的资料 | RAG/知识库 |
| 实时天气、库存、价格 | 工具/API |
| 精确计算、查数据库、执行业务动作 | 工具/API |
| 调语气、格式、字数、输出结构 | Prompt |
| 长期稳定分类、风格、轻量部署 | 微调 |
| 多步骤自主执行 | Agent（组合知识库与工具） |

**高频错法**：用微调灌最新知识、用 RAG 做精确计算、用 Prompt 获得实时数据、用更大模型替代权限控制。

### 14.6 知识库边界与可信回答

- 只对已收录、可检索、权限允许的内容负责。
- 找不到依据时应明确“不足以回答”，而不是补全想象。
- 答案要保留来源链接或片段引用，方便核验。
- 引用正确不代表结论一定正确，还要评估生成忠实度。
- 权限过滤必须发生在检索链路，不能只靠提示词要求模型保密。

### 14.7 API 与部署补充

- `temperature` 越高通常越多样，越低通常越确定；不控制检索召回率。
- 流式生成适合用户等待的交互体验；批量生成适合离线程序处理。
- 容器解决环境一致和迁移部署；负载均衡分摊请求、提高可用性。
- 灰度发布用小流量验证新版本，必须能监控和回滚。
- 剪枝、量化、蒸馏、缓存可降低推理成本或时延，不能保证准确率上升。
