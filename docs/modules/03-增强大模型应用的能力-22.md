## 3. 逐考点详解

### M3-K01 · RAG 的定义与价值定位 🟢`[A]`

**RAG = Retrieval-Augmented Generation，检索增强生成。**

定义（背下来）：**先从外部知识库中检索出与问题相关的片段，再把这些片段作为上下文拼进提示词，让大模型基于给定资料作答。**

它解决三类问题：

| 问题 | 说明 | 举例 |
|---|---|---|
| **知识缺失** | 模型训练数据里没有你的私域资料 | 公司内部报销制度、产品手册 |
| **时效过期** | 模型训练有截止点，不知道之后的事 | 「最新的行业新规是什么」 |
| **幻觉** | 不知道就「编一个」 | 凭空捏造一条不存在的条款 |

不解决的（常考陷阱）：

| 它不解决 | 该用什么 |
|---|---|
| 输出格式不统一 | 提示词强约束 / **微调** |
| 行文风格不一致 | **微调** |
| 要去查实时数据、发请求、执行动作 | **插件 / Agent** |

> **核心记忆点：RAG 是「喂知识」，不是「改脑子」，也不是「装手脚」。**

### M3-K02 · RAG 完整流程与各环节作用 🟡`[B]`

分两段：**离线索引构建**（一次性/定期） + **在线查询应答**（每次提问）。

```
【离线】               【在线】
文档 → 解析 → 切片 → 向量化 → 存入向量库
                                    ↑
提问 → 向量化 → 检索召回 → 重排 → 拼上下文 → 生成 → 回答
```

| 环节 | 作用 | 出错后果 |
|---|---|---|
| 文件解析 | PDF/Word/网页 → 纯文本（含表格、图片 OCR 处理） | 解析丢内容 → 后面永远召不回 |
| 文本切片 | 长文档切成小片段（chunk） | 切不好 → 语义断裂或噪声大 |
| 向量化 | 用 embedding 模型把文本变成向量 | 模型不匹配 → 语义表征差 |
| 入库 | 存进向量数据库，建立索引 | — |
| 召回 | 用问题向量找相似片段，取 top-k | 召不到正确答案（检索侧失败） |
| 重排 | rerank 精排，把最相关排前面 | 好片段排在后面被省略 |
| 拼上下文 | 把片段 + 问题组装成提示词 | 顺序/冗余会影响注意力分布 |
| 生成 | 大模型依据上下文作答 | 有依据还答错（生成侧失败） |

> 详见第 4 章「RAG 全流程专章」。

### M3-K03 · 文档解析与文本切片 🟡`[B]`

**chunk size（切片大小）权衡 —— 两端都不好：**

| | 优点 | 缺点 |
|---|---|---|
| **chunk 过大** | 上下文完整，语义连贯 | 噪声多、稀释相关性、占用上下文窗口、成本上升 |
| **chunk 过小** | 粒度细、相关性强 | 语义被切断，一句话的前提和结论散落两块 |

**overlap（重叠）的作用**：相邻 chunk 之间保留一段重复文本，**防止一句话/一个表格被从中间切开导致两头都不可用**。代价是存储与检索冗余。

调优思路：
- FAQ / 条目型文档 → 小块、**按条目切**（不要按字数硬切）
- 论述型、剧情连贯文档 → 稍大块 + 适当 overlap
- 表格、代码块 → 尽量整块保留，不要切断

> **一句话：先保证「切出来的每一块自己能读懂」，再谈块大小。**

### M3-K04 · 向量检索原理 ⭐ V2.4 新增 🟢`[A]`

**三个关键词：embedding、相似度、ANN。**

| 概念 | 含义 |
|---|---|
| **Embedding（向量化 / 嵌入）** | 用一个专门的模型把**任意文本**映射成一个**固定长度的数值向量**，语义相近的文本在向量空间中位置也相近 |
| **相似度（Similarity）** | 度量两个向量有多近。常用**余弦相似度**（看方向，值越接近 1 越相似）或向量距离（值越小越相似） |
| **ANN（近似最近邻检索）** | 数据量一大，穷举比对太慢，于是建**索引 + 近似搜索**，牺牲极小精度换取极大速度 |

**为什么需要向量检索（对比关键词检索）：**

| | 关键词检索（BM25 一类） | 向量检索 |
|---|---|---|
| 匹配依据 | **字面**是否出现同样的词 | **语义**是否接近 |
| 「离职手续怎么办」 vs 文档写「员工离司流程」 | ❌ 一个词都不重合，召回失败 | ✅ 语义接近，能召回 |
| 错别字 / 同义词 / 跨语言 | 弱 | 强 |
| 精确专有名词（型号、订单号） | 强 | 可能召回一堆相近但不精确的结果 |

> **实践结论：单一路径都有短板，工程上常采用「关键词检索 + 向量检索」多路召回后融合（混合检索）。**

**易错提醒：**
- 向量**不是**大模型生成的摘要，它是另一类专门的 embedding 模型产出的数值表示。
- 检索时**用户的提问也要经过同一个 embedding 模型向量化**，否则两个向量不在同一空间，比较无意义。
- 向量相似度**高不代表答案一定对**，还需要重排与生成环节的把关。

### M3-K05 · 段落召回与重排序（rerank） 🟡`[B]`

**两阶段设计的原因**：召回阶段要「快」且「全」，精排阶段要「准」。

```
海量文档 --①粗召回(向量检索,快,取 top-50)--> 候选集 --②重排序(精排模型,准,取 top-5)--> 进上下文
```

| 阶段 | 目标 | 特点 |
|---|---|---|
| **召回（Retrieval）** | **别漏**（高召回率） | 速度快，允许有噪声 |
| **重排（Rerank）** | **别错**（高精确率） | 更精细地计算「问题 vs 候选段落」的相关性，重新打分排序 |

作用：
- 把真正相关的片段排到**靠前位置**，减少被上下文窗口截断而丢失的概率
- 过滤掉「只有几个词相似但其实无关」的噪声片段，降低幻觉来源

> **一句话：召回负责把门打开，重排负责把人挑出来。**

### M3-K06 · 召回优化思路 🟡`[B]`

按「先便宜后贵」的顺序排查（与全局决策树一致）：

| 顺序 | 手段 | 针对问题 |
|:---:|---|---|
| 1 | **调优切片策略**（大小、overlap、按结构切表格/条目） | 语义断裂、噪声稀释 |
| 2 | **查询改写 / 多路查询**（把用户口语化提问改写成检索友好表述；拆成多个子查询） | 提问与文档表述不一致 |
| 3 | **元数据过滤**（按时间、部门、文档类型先筛一遍再检索） | 检索范围过宽，被不相关文档干扰 |
| 4 | **加入关键词检索做混合召回** | 专有名词、型号、编号召回不准 |
| 5 | **更换 / 微调 embedding 模型** | 领域语义（黑话、缩写）表征不足 |
| 6 | **引入 rerank 重排** | 相关片段排在后面被丢弃 |
| 7 | **调整 top-k 与上下文压缩** | 上下文超限 / 信息密度低 |

> ⚠️ 所有手段的共同前提：**先做归因，别乱改**（见第 5 章）。

### M3-K08 · 插件机制与能力边界扩展 🟡`[B]`

**插件解决的是「能力边界」问题，不是「知识」问题。**

| | RAG | 插件 |
|---|---|---|
| 本质 | **喂知识**（给参考资料） | **装手脚**（给可执行能力） |
| 数据来源 | 你自己上传的**静态**知识库 | 外部**实时**系统 / 服务 |
| 时效 | 取决于知识库什么时候更新 | 调用即得当下结果 |
| 典型场景 | 产品手册问答、制度问答 | 查实时天气 / 汇率 / 库存、执行计算、下单、发消息 |

**判定口诀：**
> **「这事给模型一万本书它也答不出来吗？」**
> - 给了书就能答 → **RAG**
> - 给再多书也答不了（因为需要实时/外部动作） → **插件**

常见陷阱：
- ❌「做个能查今天天气的应用，用 RAG」 → 天气是实时的，知识库永远是昨天的数据，**应用插件**
- ❌「把公司制度微调进模型」 → 制度会改，知识类一律优先 **RAG**（可追溯、易更新）

### M3-K09 · API 调用与关键参数 🟡`[B]`

> ⛔ **不考也不背具体默认数值**，只考**作用与调大/调小的方向**。

| 参数 | 作用 | 调大 → | 调小 → |
|---|---|---|---|
| **temperature** | 控制采样的随机性 | 更**发散**、更有创意、也可能更离谱 | 更**确定**、更保守、更可复现 |
| **top_p** | 核采样：只从累积概率达到该阈值的候选词里选 | 候选集更大 → 更**多样** | 候选集更小 → 更**集中/稳定** |
| **max_tokens** | 生成**输出**的最大长度上限 | 允许更长输出，成本与延迟上升 | 可能被**截断**（答到一半没了） |

**取值策略（常考的方向题）：**

| 场景 | 建议 |
|---|---|
| 事实问答、RAG 问答、数据抽取、代码生成 | **调低** temperature（要准确稳定） |
| 创意写作、起名、头脑风暴、营销文案 | **调高** temperature（要多样性） |
| 输出总是被截断 | 调大 **max_tokens** |
| 想要「同一个问题多次问结果一致」 | **调低** temperature 与 top_p |

> 注意：`max_tokens` 限制的是**输出**，不是输入；超出上下文窗口的输入会被截断或报错，那是另一回事。

### M3-K10 · 批量生成 vs 流式生成 🟡`[B]`

| | 批量生成（一次性返回） | 流式生成（逐段返回） |
|---|---|---|
| 返回方式 | 生成全部完成后**一次性**给结果 | 边生成边返回，**逐步吐出** |
| 感知延迟 | 用户要等到全部生成完才有反馈 | 首字很快出现，等待感低 |
| 适合 | 离线批处理、数据清洗、批量摘要、报告生成、需要拿到完整结果再做后处理的任务 | 对话式产品、C 端实时交互、长回答的用户体验优化 |
| 不适合 | 长文本实时对话（用户干等进度条） | 必须拿到全文才能做的后处理（如 JSON 解析需完整，除分段处理外） |

> **判定口诀：让人等的用流式，让机器等的用批量。**

### M3-K11 · 技术选型边界与成本递增顺序 🟡`[B]`

```
                大模型回答不够好
                        │
               第1问：是「说不清」还是「不知道」？
                        │
        ┌───────────────┴───────────────┐
        ▼                               ▼
   【表达/理解问题】              【知识/能力问题】
        │                               │
        ▼                       第2问：缺知识还是缺能力？
   ① 优化提示词                          │
   成本最低，永远先试            ┌────────┴────────┐
        │                       ▼                 ▼
        │ 还不够好           缺知识/最新信息   能力边界不足
        │                       │            （实时/计算/执行）
        │                       ▼                 ▼
        │                    ② RAG             ③ 插件
        │
        ▼
   第3问：余下的问题是什么？
        │
   ┌────┴──────────┐
   ▼               ▼
需要固定格式/风格  任务复杂多步
   │               │
   ▼               ▼
 ④ 微调          ⑤ Agent
```

**五选一对照表（必背）：**

| 手段 | 解决什么 | 不解决什么 | 成本 | 归属 |
|---|---|---|:---:|---|
| **优化提示词** | 表达不清、指令模糊、输出不稳 | 缺知识、缺能力 | 💰 最低 | M2 |
| **RAG** | 缺私域知识、缺最新信息、幻觉 | 格式风格、执行动作 | 💰💰 | **M3** |
| **插件 / API** | 超出模型能力边界的事 | 知识组织、流程编排 | 💰💰 | **M3** |
| **微调** | 固定输出格式、行文风格、领域表达 | 知识更新（会过时、不可追溯） | 💰💰💰 | M5 |
| **Agent** | 复杂多步任务、自主规划、调度工具 | 简单单轮问答（杀鸡用牛刀） | 💰💰💰 | M4 |

**口诀：**
> **「先问再说，缺知检索，越界插件，定风微调，多步智能。」**

> 组合是允许的：**RAG 补知识 + 微调定风格 + Agent 做编排**，三者不互斥。

### M3-K12 · RAG 的局限性与不适用边界 🔴`[C]`

> ⚠️ 本考点为通用知识推断，**待与官方 V2.4 大纲 PDF 核对**。

- 上下文窗口有上限，**喂进去的资料再多也受窗口限制**
- 只能「提供依据」，**不能改变模型的表达风格或输出格式**
- 检索是被动的，**不会主动执行任何动作**（不能下单、不能发邮件）
- 知识库质量决定上限（**垃圾进垃圾出**），且不解决文档本身缺失
- 多跳推理（需要跨多个文档串联才能答）仍是难点

## 4. RAG 全流程专章（核心，必背）

```
┌─────────────────────── 离线：索引构建 ───────────────────────┐
│                                                              │
│   ①文档接入 → ②文件解析 → ③文本切片 → ④向量化 → ⑤入库建索引     │
│                                                              │
└──────────────────────────────────────────────────────────────┘
                                │
                                ▼
┌─────────────────────── 在线：查询应答 ───────────────────────┐
│                                                              │
│   ⑥用户提问 → ⑦提问向量化 → ⑧检索召回 → ⑨重排序 → ⑩拼上下文    │
│                                                    → ⑪生成回答 │
└──────────────────────────────────────────────────────────────┘
```

| 步骤 | 做什么 | 关键决策 | 常见坑 |
|:---:|---|---|---|
| ① 文档接入 | 收集 PDF / Word / HTML / 表格等原始资料 | 资料是否齐全、是否最新版 | 资料本身过时或缺失，后面白搭 |
| ② 文件解析 | 提取纯文本、保留标题层级、处理表格与图片 | 扫描件需 OCR | 表格被拉平成一串字，答案丢失 |
| ③ 文本切片 | 按 chunk size + overlap 切分 | 块大小、重叠长度、按结构还是按字数 | 条目型文档硬按字数切，语义断裂 |
| ④ 向量化 | embedding 模型 → 向量 | 选合适的 embedding 模型 | 提问与文档用了不同模型，空间不一致 |
| ⑤ 入库 | 存入向量数据库并建立 ANN 索引 | 元数据（时间/部门/类型）一并存 | 不存元数据，后面无法做过滤 |
| ⑥ 用户提问 | 接收自然语言问题 | — | — |
| ⑦ 提问向量化 | **用同一个 embedding 模型**处理问题 | 可先做查询改写 | 口语化提问与书面文档表述差异大 |
| ⑧ 检索召回 | 相似度计算，取 top-k 候选 | k 值、是否混合关键词检索 | k 太小漏掉答案，k 太大引入噪声 |
| ⑨ 重排序 | rerank 精排，取 top-n 进上下文 | n 值 | 省掉这步，好片段排在后面被截断 |
| ⑩ 拼上下文 | 片段 + 指令 + 问题拼成提示词 | 排序、去重、是否带引用出处 | 无出处 → 用户无法核实 → 信任低 |
| ⑪ 生成回答 | 大模型基于上下文作答 | 「无依据就说不知道」的兜底指令 | 没有兜底约束 → 上下文没有就编（幻觉） |

**离线 vs 在线的分界（常考）：**
> **③④⑤ 是离线环节**（一次做好，重复用）；
> **⑦⑧⑨⑩⑪ 是在线环节**（每次提问都要跑一遍）。
> 所以「回答慢」的优化重点在 **⑦⑧⑨**，「召不回」的优化重点在 **②③④⑤**。

**一条完整示例：**
> 用户问「试用期员工能不能申请住房补贴？」
> → 问题向量化 → 检索到《员工福利手册 v3.2》第 4.1 条「住房补贴适用于转正满 6 个月员工，试用期不在此列」→ rerank 后排第 1 → 拼进提示词 → 模型答「不能。依据《员工福利手册 v3.2》第 4.1 条，住房补贴需转正满 6 个月……」→ 附出处。

## 5. RAG 评测归因专章 ⭐ V2.4 新增（重中之重）

> 官方在 V2.4 把「RAG 评测归因」列为新增考点，意味着考试不再只问「RAG 有哪几步」，
> 而会问：**「RAG 答错了，你怎么知道是哪一步的锅？」**

### 5.1 归因总原则：一句话切断两半

```
        RAG 回答质量不好
                │
        第 1 步：把「检索到的上下文」打印出来看
                │
        ┌───────┴───────┐
        ▼               ▼
  上下文里【有】答案    上下文里【没有】答案
        │               │
        ▼               ▼
   【生成侧失败】      【检索侧失败】
   看到了还答错        压根没喂进去
```

> **口诀：有而答错是生成，没有可查是检索。**

### 5.2 两侧对照表（必背）

| | **检索侧失败** | **生成侧失败** |
|---|---|---|
| **现象** | 召回的片段里**根本没有**正确答案 | 正确答案**就在上下文里**，模型还是答错 / 答漏 / 自创 |
| **通俗说法** | 没喂进去 | 喂进去了没吃透 / 不老实 |
| **关注指标** | 召回率 / 命中率（Recall@k）：相关片段有没有进候选集 | **忠实度**（faithfulness）：答案是否严格来自上下文<br>**答案相关性**：是否答非所问 |
| **典型原因** | 切片把答案切断、embedding 不适配领域黑话、提问与文档表述不一致、k 太小、元数据没过滤导致被相似文档干扰 | 提示词没约束「只依据上下文」、上下文噪声太多稀释关键信息、模型能力不足、上下文过长导致「中间遗忘」、多条片段冲突时模型乱合并 |
| **对症手段** | ① 调切片策略（大小/overlap/按结构切）<br>② 查询改写 / 多路查询<br>③ 混合关键词检索<br>④ 元数据过滤<br>⑤ 换 embedding 模型<br>⑥ 加 rerank 重排<br>⑦ 增大 top-k | ① 优化提示词（明确「仅限上下文，无依据须回答『未找到』」）<br>② 上下文去重 / 压缩 / 重排序（关键片段放首尾）<br>③ 要求带引用出处，便于核验<br>④ 换更强的生成模型<br>⑤ 加入自检闭环（让模型核对自己的答案是否有依据） |
| **成本** | 相对低，先做 | 相对高，后做 |

### 5.3 归因的正确顺序

> **永远「先检索，后生成」：**
> 检索侧没修好就去调生成参数，等于对着错误资料优化措辞 —— **垃圾进，垃圾出**。
> 只有确认「相关资料稳定能被召回到」之后，再去优化生成侧才有意义。

### 5.4 评测思路（业界通用框架思路，如 RAGAS 一类）🔴`[C]`

> ⚠️ 具体框架名与指标算式属通用知识推断，**待与官方 V2.4 大纲 PDF 核对**。考试若出现，按「思路」理解即可，不必记公式。

通常把 RAG 拆成**三层指标**分别打分，这样失败时能直接定位是哪一层：

| 层次 | 问的问题 | 对应归因 |
|---|---|---|
| **检索质量** | 召回的片段里，包含答案的比例有多高？ | 检索侧 |
| **上下文相关性** | 召回的片段里，有多少是真正有用的、噪声多不多？ | 检索侧（偏重排） |
| **答案忠实度** | 生成的答案，每一句都能在上下文里找到依据吗？ | 生成侧 |
| **答案相关性** | 生成的答案，真的回应了用户的问题吗？ | 生成侧 |

> **总结：评测不是为了打分，是为了归因；归因不是为了甩锅，是为了对症下药。**

## 6. 易错辨析表

### 6.1 手段辨析：到底该用哪个

| 场景 | 常见错误答案 | ✅ 正解 | 理由 |
|---|---|---|---|
| 公司不知道新出的产品报价单 | 微调 | **RAG** | 知识类优先检索，可更新可追溯 |
| 不会回答公司内部的报销流程 | 微调 | **RAG** | 私域知识缺失 |
| 输出的 JSON 格式忽对象忽数组 | RAG | **提示词强约束 → 微调** | 这是格式/稳定性问题 |
| 要模型一直用客服话术且语气稳定 | RAG | **微调** | 固定行文风格是微调典型场景 |
| 要查实时天气 / 汇率 / 库存 | RAG | **插件** | 实时外部能力，知识库永远是旧数据 |
| 要读 Excel、算总和、再发邮件 | RAG / 插件 | **Agent** | 多步 + 多工具编排 |
| 回答泛泛而谈、抓不住重点 | RAG / 微调 | **优化提示词**（先试） | 成本最低，永远第一步 |
| 模型不知道 2026 年新发布的法规 | 微调 | **RAG** | 时效知识靠检索 |
| 想让搜索能召回「员工离司流程」来回答「离职手续怎么办」 | 加更多数据微调 | **用向量检索（语义召回）** | 关键词字面不匹配，需语义匹配 |
| RAG 答错了就想换生成模型 | 直接换模型 | **先归因**：看上下文里有没有答案 | 可能是检索侧没召回，换模型无效 |

### 6.2 概念辨析

| 对比项 | A | B | 判据 |
|---|---|---|---|
| **RAG vs 微调** | 补**知识**，改的是「喂什么」 | 改**行为**，改的是「怎么答」 | 改 paragraph 内容是 RAG，改说话方式/格式是微调 |
| **RAG vs 插件** | 静态**已入库**的知识 | 实时**外部**能力/动作 | 给再多书也答不出 → 插件 |
| **chunk 过大** vs **过小** | 噪声多、稀释相关性、浪费窗口 | 语义断裂、前提与结论分离 | 先看切出来的块能不能独立读懂 |
| **批量 vs 流式** | 一次性返回，适合离线批处理 | 逐段返回，适合实时对话体验 | 让人等 → 流式；让机器等 → 批量 |
| **召回 vs 重排** | 求「全」与「快」 | 求「准」 | 别漏的是召回，别错的是重排 |
| **temperature 高 vs 低** | 发散、创新、不稳定 | 确定、稳定、可复现 | 事实问答调低，创意写作调高 |
| **top_p 大 vs 小** | 候选词范围大 → 多样 | 候选词范围小 → 集中 | 与 temperature 同向使用更保险 |
| **max_tokens 太小** | 输出被截断 | — | 是**输出**上限，不是输入 |

### 6.3 判断题速记（对 / 错）

| 说法 | 判断 |
|---|---|
| RAG 可以完全消除幻觉 | ❌ **降低**，不能消除（生成侧仍可能编） |
| 向量检索能匹配同义词和语义相近的表述 | ✅ |
| 有了 RAG 就不需要微调 | ❌ 两者可组合：RAG 补知识 + 微调定风格 |
| 提问不向量化，可以直接拿原文去和文档向量算相似度 | ❌ 必须用**同一个 embedding 模型**向量化 |
| chunk overlap 越大越好 | ❌ 会引入冗余，适度即可 |
| RAG 答错时，应先检查检索到的上下文 | ✅ 这是归因第一步 |
| 关键词检索在处理专有名词、订单号时可能优于向量检索 | ✅ 所以常做混合召回 |
