## 三、⭐⭐ RAG vs 工具：官方选型判据专章（本模块最高频考法）

### 3.1 官方一句话总原则

> **「模型不是什么都要靠记忆回答。」**
> **「查企业资料用 RAG，需要实时数据、确定性计算或业务动作时用工具。」**

这句话可以直接拆成一张判据表 —— **本模块 11 题里至少 3~4 题是照着这张表出的**。

### 3.2 官方判据对照表（必背）

| | **RAG（接入知识库）** | **工具调用** |
|---|---|---|
| **官方判据** | **查企业资料** | **实时数据** ／ **确定性计算** ／ **业务动作** |
| 本质 | **喂知识**（给模型参考资料） | **装手脚**（给模型可执行能力） |
| 解决的是 | 「模型**不知道**」 | 「模型**做不到 / 拿不到 / 算不准**」 |
| 数据性质 | **静态**的企业资料（产品手册、制度、合同模板、FAQ） | **动态**的外部系统数据（库存、天气、汇率、订单状态） |
| 输出 | 一段有依据、可附出处的**回答** | 一次**查询 / 计算 / 操作**及其结果 |
| 典型场景 | 报销制度问答、产品手册问答、内部 SOP 检索 | 查实时库存、精确算税、下单、发邮件、改数据库记录 |
| 归属模块 | **M3** | **M3**（编排进流程后是 M4 Agent） |

### 3.3 三条「用工具」判据，逐条拆开看

| 判据 | 官方原词 | 为什么模型自己不行 | 举例 |
|---|---|---|---|
| **判据一** | **实时数据** | 模型训练有截止时间，且知识库入库的瞬间就已成快照 | 「上海仓现在还剩多少台设备」「今天杭州什么天气」「当前汇率多少」 |
| **判据二** | **确定性计算** | 大模型按概率生成，**算得不准**；金额、税率、库存扣减这类要求「一分不差」的计算不能交给它猜 | 「128 件 × 39.9 元，打 8 折再扣 13% 税，应付多少」「这批订单的总额和平均交付时长」 |
| **判据三** | **业务动作** | 模型只能**输出文字**，不会真的去操作系统；下单、发邮件、改数据库都是**动作**，不是**知识** | 「帮我提交请假单」「把这份周报发给项目组」「把该任务标记为已完成」 |

> **一句话记忆：要「现在的」、要「算得准的」、要「真的去做的」—— 这三件事都归工具。**

### 3.4 快速判断三问（做题时在心里过一遍）

```
                    这个需求，模型答不好
                            │
        第1问：给它足够的资料，它就能答出来吗？
                            │
              ┌─────────────┴─────────────┐
              ▼                           ▼
         【能】缺资料                 【不能】缺能力
              │                           │
              ▼                   第2问：缺的是哪一种？
       资料是企业内部的、           ┌───────┼───────┐
       会更新的、要可追溯的吗？      ▼       ▼       ▼
              │                 实时数据 确定性计算 业务动作
              ▼                    └───────┼───────┘
          ✅ RAG                            ▼
        （查企业资料用 RAG）              ✅ 工具
                                    （实时/计算/动作 用工具）

        第3问：都不是？→ 回看官方五选一：
        优化输入 → 接入知识库 → 调用工具 → 微调 → 协作 Agent → 或保留人工确认
```

### 3.5 典型场景判断题（8 题，做完这表选型题基本稳）

| # | 场景 | 该用什么 | 为什么 |
|:---:|---|---|---|
| 1 | 「公司最新的差旅住宿标准是多少钱一晚？」—— 制度写在内部文档里，每年修订 | ✅ **RAG** | **查企业资料用 RAG**：内部、会更新、要可追溯、可附出处 |
| 2 | 「我们上海仓库现在还剩多少台 XX 型号设备？」—— 每分钟都在变 | ✅ **工具** | **实时数据**：入库即快照，RAG 永远慢一步 |
| 3 | 「这批订单扣完折扣和税之后应付总额是多少？」—— 财务要求一分不差 | ✅ **工具** | **确定性计算**：模型是概率生成，算不准；交给计算/结算类接口 |
| 4 | 「帮我把这份周报发给项目组全体成员，并在系统里把任务标记为已完成」 | ✅ **工具** | **业务动作**：模型只会输出文字，不会真的发邮件、改记录 |
| 5 | 「帮我解释一下这份合同里第 7 条是什么意思」—— 合同是公司内部模板库里的 | ✅ **RAG**（＋ 高风险场景需**人工确认**） | 先查企业资料；涉及合同责任，AI 可辅助整理，**不能替代最终责任人** |
| 6 | 模型回答泛泛而谈、抓不住重点 | ✅ **优化输入（提示词）** | 成本最低，永远第一步；不是缺知识也不是缺能力 |
| 7 | 要求助手每天稳定输出**固定格式**的工单摘要，格式老跑偏 | ✅ **微调** | 稳**行为 / 格式 / 风格**才考虑微调；RAG 不解决格式问题 |
| 8 | 要跨订单系统、物流系统、财务系统完成一次**完整退款流程** | ✅ **协作 Agent** | 多步编排 + 多工具调度；且**高风险退款动作须人工确认** |

### 3.6 两个方向不能搞反（送命点）

| ❌ 常见错误 | ✅ 正解 | 理由 |
|---|---|---|
| 「做个能查今天天气的应用，用 RAG」 | **工具** | 天气是实时的，知识库永远是昨天的数据 |
| 「把公司制度微调进模型」 | **RAG** | 制度会改；知识进了权重就**不可追溯、不可更新** |
| 「模型算数不准，多写点提示词让它仔细算」 | **工具** | 算得准是**工具**的活，不是提示词能补的 |
| 「让 RAG 去帮用户把订单提交了」 | **工具** | RAG 只**提供依据**，不会执行任何动作 |
| 「查内部资料，让模型联网搜一下」 | **RAG** | 企业内部资料**不公开**，联网搜不到；且不可控不可追溯 |

## 四、⭐ MCP 的作用专章（本轮新增 · 官方明列在本模块）

### 4.1 MCP 是什么（一句话，背这句就够）

> **MCP 是一套标准化的连接协议 / 开放标准，用来规范「模型或 Agent 如何发现并连接外部的数据源和工具」。**
> **它是「怎么连」的标准，不是「连上之后能干什么」的工具本身。**

### 4.2 它解决什么问题（这是官方要求掌握的全部内容）

**没有统一标准时**：N 个 AI 应用 × M 个外部工具/数据源 = **N×M 个定制集成**。每接一个工具都要写一遍对接代码、定义一遍描述格式，重复建设、无法复用。

**有了统一标准后**：工具方按标准暴露一次，应用方按标准对接一次，集成量从 N×M 降到 **N+M**。

| 维度 | 没有 MCP（碎片化集成） | 有 MCP（标准化连接） |
|---|---|---|
| 对接成本 | 每个应用 × 每个工具都要定制 | 各方按同一套标准对接一次 |
| 工具复用 | 为 A 应用写的工具，B 应用用不了 | 按标准实现的工具可被多个应用复用 |
| 扩展新工具 | 要改应用代码 | 按标准接入即可被发现和使用 |
| 生态 | 各自为战 | 工具与应用可自由组合 |

### 4.3 考到什么程度（⚠️ 官方给了明确上限）

> **官方原文：「了解 MCP 的**作用**，**不要求掌握协议细节**。」**

| ✅ 考 | ⛔ **不考（官方明说不要）** |
|---|---|
| MCP **解决什么问题**（碎片化集成 / N×M） | 握手流程、连接建立过程 |
| MCP 的**定位**（标准化连接协议，不是工具） | 报文格式、JSON-RPC 等消息格式 |
| 有了 MCP **带来什么价值**（复用、可扩展、生态互通） | 传输层实现（stdio / SSE / HTTP 之类） |
| MCP 与**工具、Function Calling 的层级区别** | SDK、配置项、服务端开发、注册流程 |

> **做题提示**：只要选项里出现「传输层」「报文」「握手」「JSON-RPC」「协议字段」这类词，**一律不是答案** —— 官方已声明不考。

### 4.4 MCP 与「工具」「Function Calling」的层级关系

```
  L4  执行体：Agent（用这些能力去完成任务）
              │
  L3  连接标准：MCP（外部数据源与工具如何被「发现、描述和对接」）
              │
  L2  调用机制：Function Calling（模型侧 —— 把「要调什么、传什么参数」表达成结构化请求）
              │
  L1  能力本体：工具（查天气、查库存、发邮件、改数据库 —— 真正干活的东西）
              │
  L0  大模型
```

| 概念 | 在哪一层 | 回答的问题 | ❌ 常见误解 |
|---|---|---|---|
| **工具** | L1 能力本体 | **连上之后能干什么** | 「MCP 就是一个工具」 |
| **Function Calling** | L2 模型侧机制 | **模型怎么表达调用意图** | 「有了 MCP 就不需要 Function Calling」（不同层，通常共存） |
| **MCP** | L3 连接标准 | **怎么被发现、怎么接得上、怎么描述清楚** | 「MCP 能让模型自己学会用工具」 |
| **Skill**（M4） | 作业方法层 | **重复的工作方法怎么固化下来** | 「Skill 就是工具」 |

> **类比速记：MCP ≈ Type-C 接口标准；工具 ≈ 外接设备（U 盘、打印机）；Function Calling ≈ 系统发出的调用指令；Agent ≈ 用电脑干活的人。**
> 接口标准不是 U 盘本身，但你有了统一的 Type-C，什么设备都能插上来用。

### 4.5 易错判断表

| 说法 | 判断 | 说明 |
|---|:---:|---|
| MCP 是一个可以查天气的工具 | ❌ | MCP 是**连接标准**；查天气是被接入的**具体工具** |
| MCP 解决了模型与外部数据源、工具对接的碎片化问题 | ✅ | 这是官方要求掌握的**作用** |
| 有了 MCP，模型就能自己学会使用工具 | ❌ | 协议只解决「接得上、描述得清」；用得好不好仍取决于模型能力与工具描述质量 |
| MCP 可以替代 RAG | ❌ | 两者完全不同层：RAG 是**补知识**的方法，MCP 是**连接外部资源**的标准；查企业资料仍用 RAG |
| 考试会考 MCP 的传输层与报文格式 | ❌ | 官方原文：**不要求掌握协议细节** |

## 五、RAG 五环节专章（按官方口径重排）

> **官方原文：「理解 RAG 的**解析、切分、检索、重排序和评测**会影响答案质量。」**
> ⚠️ 考试以官方这五个词为准。工程上完整链路还包含「向量化、入库、拼上下文、生成」，但**官方点名的影响环节就是这五个**，多选题按官方口径作答。

```
┌──────────────── 离线：资料入库（一次做好，反复使用）────────────────┐
│                                                                    │
│   企业资料 → ①解析 → ②切分 → （向量化 → 入库建索引）                 │
│                                                                    │
└────────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────── 在线：查询应答（每次提问都跑一遍）────────────────┐
│                                                                  │
│   提问 → ③检索（粗召回 top-k）→ ④重排序（精排 top-n）→ 拼上下文 → 生成 │
│                                                                  │
└──────────────────────────────────────────────────────────────────┘
                                  │
                                  ▼
┌──────────────── 贯穿全程 ────────────────┐
│  ⑤评测：建评测集 → 分环节打分 → 归因 → 对症下药 │
└──────────────────────────────────────────┘
```

### 5.1 ① 解析（本轮补齐）

| 项目 | 内容 |
|---|---|
| **做什么** | 把原始资料（PDF / Word / Excel / HTML / 扫描件 / 图片）**提取成干净、可检索的文本**，并尽量保留**标题层级、表格的行列关系、图片与图表中的有效信息** |
| **关键动作** | 格式转换与清洗；**扫描版 PDF / 图片需先做 OCR**；表格要按结构提取而不是拉平成一串字；保留文档元信息（标题、章节、时间、来源） |
| **做不好会怎样** | 🔴 **内容在源头就丢了，后面检索再怎么优化也永远召不回**；表格被拉平后「参数名—参数值」的对应关系消失，答非所问；扫描件未 OCR 则整页变成空内容 |
| **优化方向** | 选用更合适的解析方式；扫描件补 OCR；表格/清单按结构化提取并保留行列关系；保留标题层级与出处元信息，便于后续引用与过滤 |
| **易错** | 把「解析丢内容」误判成「切分不好」或「embedding 不行」—— 前者是**源头缺失**，后两者只是**找得不准** |

### 5.2 ② 切分

| 项目 | 内容 |
|---|---|
| **做什么** | 把长文档切成便于检索的小片段（chunk），并决定块大小、块间重叠（overlap）与切分依据 |
| **关键权衡** | **chunk 过大**：上下文完整但噪声多、稀释相关性、占用上下文窗口；**chunk 过小**：粒度细但**语义被切断**，前提与结论散落两块 |
| **overlap 的作用** | 相邻块之间保留一段重复文本，**防止一句话 / 一个表格被从中间切开导致两头都不可用**；代价是存储与检索冗余，适度即可 |
| **做不好会怎样** | 召回的片段「只有一半意思」；答案看起来总像缺斤少两 |
| **优化方向** | FAQ / 条目型文档 → **按条目切**，不要按字数硬切；论述型文档 → 稍大块 + 适当 overlap；表格、代码块 → 尽量**整块保留** |
| **一句话** | **先保证「切出来的每一块自己能读懂」，再谈块大小。** |

### 5.3 ③ 检索（含向量检索）

| 项目 | 内容 |
|---|---|
| **做什么** | 根据用户提问，从知识库中找出**相关**的候选片段（粗召回，通常取 top-k） |
| **核心原理** | **Embedding（向量化）**：用专门的 embedding 模型把文本映射成固定长度的向量，语义相近的文本在向量空间中距离更近；**相似度**：常用余弦相似度衡量两个向量有多近；**ANN（近似最近邻）**：建索引 + 近似搜索，牺牲极小精度换取海量向量上的检索速度 |
| **为什么需要向量检索** | 突破关键词检索「**字面必须重合**」的限制：「离职手续怎么办」能召回写「员工离司办理流程」的文档；对同义词、口语化表述、跨语言更鲁棒 |
| **做不好会怎样** | 相关段落**根本进不了候选集**（检索侧失败）→ 答案只能答「未找到」或开始编 |
| **优化方向** | 调优切片；**查询改写 / 多路查询**（把口语化提问改写成检索友好表述）；**元数据过滤**（按时间/部门/类型先筛）；**混合检索**（向量 + 关键词）；更换更适配领域的 embedding 模型；调整 top-k |
| **易错** | ① 向量**不是**大模型生成的摘要，由专门的 embedding 模型产出；② 用户的**提问也要用同一个 embedding 模型**向量化，否则不在同一空间、比较无意义；③ 相似度**高不等于答案对**，还需重排与生成把关 |

> **混合检索结论**：向量检索长于语义、弱于精确；关键词检索长于精确（型号、订单号、专有名词）、弱于语义。**单一路径都有短板，工程上常做「关键词 + 向量」多路召回后融合。**

### 5.4 ④ 重排序（rerank）

| 项目 | 内容 |
|---|---|
| **做什么** | 对粗召回的候选片段，用更精细的方式重新计算「问题 vs 段落」的相关性并**重新打分排序**，取前 n 条进入上下文 |
| **两阶段设计** | **召回求「全」且「快」**（别漏，允许有噪声）；**重排求「准」**（别错，把最相关的提到前面） |
| **做不好会怎样** | 真正相关的片段排在**靠后位置**，被 top-n 截断或超出上下文窗口而丢失；噪声片段混进上下文 → 稀释关键信息、增加幻觉来源 |
| **优化方向** | 引入 rerank 模型；调整候选集大小（k）与进入上下文的条数（n）；关键片段尽量放在上下文首尾 |
| 🔴 **高频陷阱** | **rerank 只对「已召回的候选集」重新排序，不会把没召回到的片段变出来**，因此它**提升的是精确率，不是召回率**。检索侧「压根没召回」的问题必须回到检索/切分/解析环节解决 |

> **一句话：召回负责把门打开，重排负责把人挑出来。**

### 5.5 ⑤ 评测

| 项目 | 内容 |
|---|---|
| **做什么** | 建立评测集与指标，对 RAG 各环节分别打分，**定位答案质量下降到底出在哪一环** |
| **为什么必须有** | 官方把「评测」列为影响答案质量的五个环节之一 —— **评测不是为了打分，是为了归因；归因不是为了甩锅，是为了对症下药** |
| **常见分层** | **检索质量**（相关片段有没有进候选集）、**上下文相关性**（召回的片段噪声多不多）、**答案忠实度**（答案每句是否有上下文依据）、**答案相关性**（有没有答非所问） |
| **做不好会怎样** | 出问题只能「瞎调」：检索侧没修好就去调生成参数，等于**对着错误资料优化措辞**（垃圾进，垃圾出） |
| **优化方向** | 先建小而有代表性的评测集；分环节打分；先归因（见第六章）再动手；改完**回到评测集复测**，形成闭环 |
| **易错** | 「评测就是给最终答案打个总分」❌ —— 只打总分无法定位环节，违背官方把评测列为独立环节的用意 |

## 六、RAG 评测归因专章（检索侧 vs 生成侧）

### 6.1 归因总原则：一句话切断两半

```
                RAG 答案质量不好
                        │
            第 1 步：把「检索到的上下文」拿出来看
                        │
                ┌───────┴───────┐
                ▼               ▼
        上下文里【有】答案     上下文里【没有】答案
                │               │
                ▼               ▼
        【生成侧失败】        【检索侧失败】
          看到了还答错         压根没喂进去
```

> **口诀：有而答错是生成，没有可查是检索。**

### 6.2 两侧对照表（必背）

| | **检索侧失败** | **生成侧失败** |
|---|---|---|
| **现象** | 召回的片段里**根本没有**正确答案 | 正确答案**就在上下文里**，模型还是答错 / 答漏 / 自创 |
| **通俗说法** | 没喂进去 | 喂进去了没吃透 / 不老实 |
| **关注指标** | 召回率 / 命中率（Recall@k）：相关片段有没有进候选集 | **忠实度**：答案是否严格来自上下文；**答案相关性**：是否答非所问 |
| **典型原因** | 解析丢了内容、切片把答案切断、embedding 不适配领域黑话、提问与文档表述不一致、k 太小、未做元数据过滤被相似文档干扰 | 提示词没约束「只依据上下文」、上下文噪声太多稀释关键信息、模型能力不足、上下文过长导致「中间遗忘」、多条片段冲突时模型乱合并 |
| **对症手段** | ① 改进**解析**<br>② 调**切分**策略<br>③ 查询改写 / 多路查询<br>④ 混合关键词检索<br>⑤ 元数据过滤<br>⑥ 换 embedding 模型<br>⑦ 加 rerank、调 top-k | ① 优化提示词（明确「仅限上下文，无依据须回答『未找到』」）<br>② 上下文去重 / 压缩 / 关键片段放首尾<br>③ 要求带引用出处，便于核验<br>④ 换更强的生成模型<br>⑤ 加入自检闭环（核对答案是否有依据） |
| **成本** | 相对低，**先做** | 相对高，**后做** |

### 6.3 归因的正确顺序

> **永远「先检索，后生成」：**
> 检索侧没修好就去调生成参数，等于对着错误资料优化措辞 —— **垃圾进，垃圾出**。
> 只有确认「相关资料稳定能被召回到」之后，再去优化生成侧才有意义。

## 七、知识库服务 / 知识问答系统 / 个人 AI Agent 接入（官方「建议掌握的知识」原文）

### 7.1 知识库服务与知识问答系统

| 要点 | 内容 |
|---|---|
| **基本原理** | 把企业资料（**企业资料** = 产品手册、制度规范、FAQ、合同模板、历史工单等）接入知识库 → 解析、切分、向量化入库 → 用户提问时检索 + 重排 → 将片段拼进上下文交给模型生成 → **附出处**供核验 |
| **和直接问模型的区别** | 直接问模型靠「**记忆**」（训练数据），知识库问答靠「**查资料**」—— 模型不必什么都靠记忆回答 |
| **质量改进方法** | 就是官方点名的五环节：**解析**（别丢内容）→ **切分**（别切碎语义）→ **检索**（别漏召）→ **重排序**（把最相关的排前面）→ **评测**（先归因再动手） |
| **为什么值得做** | 知识**可更新**（改文档即刻生效）、答案**可追溯**（附出处）、**可抑制幻觉**（有依据才答，无依据说「未找到」） |

### 7.2 个人 AI Agent 接入知识库与工具（官方原文点名）

> 官方：「**工具调用、MCP** 和个人 AI Agent 接入**知识库与工具**的方法。」

| 接入对象 | 补的是什么 | 对应官方判据 |
|---|---|---|
| **接入知识库** | 补**知识** —— 让 Agent 能回答它本来不知道的企业资料 | **查企业资料用 RAG** |
| **接入工具** | 补**能力** —— 让 Agent 能拿到实时数据、做确定性计算、执行业务动作 | **实时数据 / 确定性计算 / 业务动作用工具** |
| **通过 MCP 接入** | 提供**标准化的连接方式**，降低对接与扩展成本 | **了解 MCP 的作用，不考协议细节** |

> **组合是常态**：一个能干活的 Agent 通常是「**知识库（补知识）+ 工具（补能力）+ MCP（标准化连接）**」三件事一起上，而不是三选一。

## 八、API 关键参数与生成方式（🟡 官方未在本模块点名，了解即可，不出题）

### 8.1 三个常见参数：只考**作用与方向**，不考默认值

| 参数 | 作用 | 调大 → | 调小 → |
|---|---|---|---|
| **temperature** | 控制采样的随机性 | 更**发散**、更有创意，也可能更离谱 | 更**确定**、更保守、更可复现 |
| **top_p** | 核采样：只从累积概率达到阈值的候选词中选 | 候选集更大 → 更**多样** | 候选集更小 → 更**集中/稳定** |
| **max_tokens** | 生成**输出**的长度上限 | 允许更长输出，成本与延迟上升 | 可能被**截断**（答到一半没了） |

| 场景 | 方向 |
|---|---|
| 事实问答、RAG 问答、数据抽取 | **调低** temperature（要准确稳定） |
| 创意写作、起名、头脑风暴 | **调高** temperature（要多样性） |
| 输出总是被截断 | 调大 **max_tokens** |
| 想要多次提问结果一致 | **调低** temperature 与 top_p |

> ⚠️ `max_tokens` 限制的是**输出**，不是输入。🔴 无论怎么调参，模型都**无法凭空获得训练数据之外的新知识** —— 要补知识请用 **RAG**。

### 8.2 批量生成 vs 流式生成

| | 批量（一次性返回） | 流式（逐段返回） |
|---|---|---|
| 返回方式 | 全部生成完**一次性**给结果 | 边生成边返回，**逐步吐出** |
| 感知延迟 | 要等全部完成才有反馈 | 首字很快出现，等待感低 |
| 适合 | 离线批处理、批量摘要、需拿到完整结果再做后处理 | 对话式产品、C 端实时交互 |

> **判定口诀：让人等的用流式，让机器等的用批量。**

## 九、易错辨析表

### 9.1 手段辨析：到底该用哪个（按官方判据重写）

| 场景 | 常见错误答案 | ✅ 正解 | 理由（官方依据） |
|---|---|---|---|
| 员工问公司最新的差旅报销标准 | 微调 | **RAG** | **查企业资料用 RAG**；知识可更新、可追溯 |
| 模型不知道上周刚修订的退货政策 | 微调 | **RAG** | 时效知识靠检索，不靠训练 |
| 问「上海仓现在还剩多少台设备」 | RAG | **工具** | **实时数据**用工具（判据一） |
| 要求金额、税率、折扣算得分毫不差 | 更仔细的提示词 | **工具** | **确定性计算**用工具（判据二） |
| 「帮我把周报发给项目组 / 提交请假单」 | RAG / 提示词 | **工具** | **业务动作**用工具（判据三） |
| 输出的 JSON 格式忽对象忽数组 | RAG | **提示词强约束 → 微调** | 这是**行为 / 格式**问题，不是知识问题 |
| 要模型一直用客服话术、语气稳定 | RAG | **微调** | 稳**行为 / 风格**才考虑微调 |
| 要跨 5 个系统完成一次退款全流程 | RAG / 工具 | **Agent**（高风险动作人工确认） | 多步编排 + 多工具调度 |
| 回答泛泛而谈、抓不住重点 | RAG / 微调 | **优化输入（提示词）** | 成本最低，永远第一步 |
| 解释合同条款、给出医疗/金融建议 | 直接采纳 AI 结论 | **RAG 查资料 + 保留人工确认** | AI 可辅助整理起草，**不能替代最终责任人** |
| 想让搜索能召回「员工离司流程」来回答「离职手续怎么办」 | 加更多数据微调 | **向量检索（语义召回）** | 关键词字面不匹配，需语义匹配 |
| RAG 答错就想换生成模型 | 直接换模型 | **先归因**：看上下文里有没有答案 | 可能是检索侧没召回，换模型无效 |

### 9.2 概念辨析

| 对比项 | A | B | 判据 |
|---|---|---|---|
| **RAG vs 工具** | 查**企业资料**（静态、可追溯） | 要**实时 / 算准 / 做事** | 官方原话：查企业资料用 RAG，实时数据、确定性计算或业务动作用工具 |
| **RAG vs 微调** | 补**知识**，改「喂什么」 | 改**行为 / 格式 / 风格**，改「怎么答」 | 改资料内容是 RAG，改说话方式是微调 |
| **MCP vs 工具** | **连接标准**（怎么连） | **能力本体**（连上后能干什么） | MCP ≈ Type-C 标准，工具 ≈ 外接设备 |
| **MCP vs Function Calling** | **连接侧**（资源如何被发现与对接） | **模型侧**（如何把调用意图说清楚） | 不同层次，通常共存，不是替代关系 |
| **解析 vs 切分** | 源头**提取内容**（丢了就永远召不回） | **切块粒度**（影响语义完整性） | 先有内容，再谈切得好不好 |
| **召回 vs 重排** | 求「全」与「快」 | 求「准」 | 别漏的是召回，别错的是重排；**rerank 不提升召回率** |
| **chunk 过大 vs 过小** | 噪声多、稀释相关性、浪费窗口 | 语义断裂、前提与结论分离 | 先看切出来的块能不能独立读懂 |
| **检索侧 vs 生成侧** | 上下文里**没有**答案 | 上下文里**有**答案却答错 | 先检索后生成 |
| **temperature 高 vs 低** | 发散、创新、不稳定 | 确定、稳定、可复现 | 事实问答调低，创意写作调高 |
| **max_tokens** | 限制**输出**长度，过小会截断 | — | 不是输入限制 |

### 9.3 判断题速记（对 / 错）

| 说法 | 判断 |
|---|---|
| 查企业内部的资料，应该用 RAG | ✅ **官方原话** |
| 需要实时数据、确定性计算或业务动作时，应该用工具 | ✅ **官方原话** |
| MCP 是一个具体的工具，能直接查天气查库存 | ❌ MCP 是**标准化连接协议**；工具才是执行能力 |
| 考试要求掌握 MCP 的协议实现细节 | ❌ **官方明说不要求掌握协议细节** |
| RAG 的解析、切分、检索、重排序和评测会影响答案质量 | ✅ **官方原话（背下来）** |
| 解析环节做不好，后面检索再优化也召不回 | ✅ 内容在源头就丢了 |
| 引入 rerank 能把没召回到的片段重新召回 | ❌ rerank 只重排候选集，**不扩大召回范围** |
| 向量检索能匹配同义词和语义相近的表述 | ✅ |
| 有了 RAG 就不需要微调 | ❌ 可组合：RAG 补知识 + 微调定风格 |
| 提问不向量化，可以直接拿原文去和文档向量算相似度 | ❌ 必须用**同一个 embedding 模型**向量化 |
| chunk overlap 越大越好 | ❌ 会引入冗余，适度即可 |
| RAG 答错时，应先检查检索到的上下文 | ✅ 这是归因第一步 |
| 关键词检索在处理专有名词、订单号时可能优于向量检索 | ✅ 所以常做混合召回 |
| RAG 可以完全消除幻觉 | ❌ **降低**，不能消除（生成侧仍可能编） |
| 有了 MCP 就不需要 RAG 了 | ❌ 完全不同层：补知识仍是 RAG |
