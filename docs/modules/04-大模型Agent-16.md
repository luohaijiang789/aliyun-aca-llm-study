## 三、⭐⭐ Agent 四要素专章（官方最核心考点）

> **官方原文**：「掌握如何给 Agent 明确**目标、资料来源、工具边界和阶段检查点**。」

**一句话理解**：把 Agent 当成一个**新来的同事**——你交代得越含糊，它越会自由发挥；四要素就是一份让它不容易跑偏的"任务委托书"。

**四要素全景：**

| 要素 | 回答的问题 | 一句话定义 | 不明确时的典型后果 |
|---|---|---|---|
| **目标** | 到底要交付什么？ | 交付物 + 范围 + 成功标准 | 做完了，但不是你要的 |
| **资料来源** | 依据什么来答？ | 允许/禁用哪些信息源 | 混入模型记忆或臆测，编数据、不可追溯 |
| **工具边界** | 能动哪些东西？动到什么程度？ | 工具白名单 + 每个工具的可做/不可做 | 越权调用，误删、误发、误改 |
| **阶段检查点** | 什么时候停下来给你看？ | 预设的暂停核对点，通过才继续 | 一步错步步错，错误被"执行"出去后返工成本极高 |

> 📌 **四要素之间的配套关系（易考辨析）**
> 「**阶段检查点**」讲的是**在什么时间点拦下来**；「**自检清单**」（第四章）讲的是**拦下来之后拿什么去核对**。两者必须成对出现——只设检查点没有清单，人/模型不知道看什么；只有清单没有检查点，错误会一路跑到最后才被发现。

### 3.1 要素① 目标 ⭐⭐

**是什么**：任务最终要交付的东西，以及"做成什么样算完成"。

**不明确会怎样**：Agent 会按它自己的理解自由发挥。最常见的结果是——**它确实干完了活，但干的是另一件事**。

**怎么写才算明确**（三个必填项）：

| 必填 | 说明 | 例子 |
|---|---|---|
| **交付物形态** | 具体是什么：一份报告 / 一个表格 / 一封邮件 / 一次工单创建 | 「输出一份 Markdown 周报文件」 |
| **范围边界** | 包含什么、**不包含什么**、时间范围、对象范围 | 「只覆盖 8 月华东大区，不含华南」 |
| **成功标准** | 什么叫做完、什么叫合格 | 「含 3 张图表，字数 ≤ 800 字，所有数字均可回溯到源表」 |

**Good vs Bad：**

| ❌ 模糊写法 | ✅ 明确写法 |
|---|---|
| 「帮我分析一下上月的销售数据」 | 「输出上月（2026-08）华东大区的销售分析，含同比/环比两张表与一段 200 字结论，所有数字必须能在『销售明细-08.xlsx』中找到同名行」 |
| 「写个周报，专业一点」 | 「按『周报模板v3』结构写周报，三个小节，每节 ≤ 3 条要点，不写主观评价」 |

---

### 3.2 要素② 资料来源 ⭐⭐

**是什么**：允许 Agent 依据哪些信息来回答问题/完成任务。

**不明确会怎样**（这是 Agent 最容易出事的一处）：
- Agent 会**默认使用模型自身的记忆**作答 → 知识可能过期、可能不是你们公司的口径
- 会把不同来源的信息混在一起，产出**看似合理实则拼凑**的结论
- 一旦出错**无法追溯、无法定责**——你不知道它这句话是从哪来的

**怎么写才算明确**（四项动作）：

1. **指定来源**：哪个知识库 / 哪个文件 / 哪个接口 / 哪个看板，尽量精确到版本或路径。
2. **限定 exclusivity**：明确「**只用**这些来源」，其余一律不许参考。
3. **规定缺省行为**（最关键的一条）：来源里查不到时，**必须回答"未找到 / 未收录"**，禁止自行推测或补全。
4. **要求留出处**：每条关键结论标注来自哪个文档的哪一段，便于人工核查。

**示例：**

> ❌ 「根据公司资料回答客户关于退款政策的问题。」
> ✅ 「只依据知识库『售后政策-v3.2』中的内容回答；该库未收录的一律回答『该问题超出当前资料范围，需转人工确认』；每条回答结论后注明依据的章节名。」

> ⚠️ **与 M3 的衔接**：指定"资料来源"后，Agent 取资料的机制就是 **知识库 / RAG**（详见 M3）。本模块只需知道：**资料来源是四要素之一，由人来指定；接了知识库不等于模型永久学会了。**

### 3.3 要素③ 工具边界 ⭐⭐

**是什么**：Agent 被允许调用哪些工具，以及每个工具**能做什么、不能做什么、做到什么程度要停下**。

**不明确会怎样**：Agent 有行动能力却不设边界，等于把钥匙交给它还不告诉它哪些门不能开。典型事故：**误删文件、误发邮件、误改生产数据、误下单**。

**怎么写才算明确**（四件套）：

| 动作 | 说明 | 例子 |
|---|---|---|
| **工具白名单** | 明确列出可使用的工具，未列出的默认不可用 | 「只允许使用『读文件』『生成图表』两个工具」 |
| **范围限制** | 对同一工具限定作用范围 | 「读文件仅限 `/shared/report/` 目录」 |
| **读写/禁用声明** | 明确哪些操作被禁止 | 「禁止删除、禁止覆盖已有文件、禁止写入任何目录」 |
| **高风险动作标注** | 划出必须人工确认的动作（详见第五章） | 「发送外部邮件前必须经我确认」 |

**示例：**

> ❌ 「你可以用你能用的工具来帮我处理文件。」
> ✅ 「可调用『读取文件』与『生成图表』工具，作用目录限定为 `/shared/report/`，**禁止写入与删除**；涉及向外部邮箱发信时，必须生成草稿交我确认后由我发送。」

> 📌 **记忆锚点**：官方把「工具边界」和「**高风险动作必须人工确认**」放在同一句话里——**边界负责事前限制，人工确认负责事后兜底**，二者缺一不可。

---

### 3.4 要素④ 阶段检查点 ⭐⭐

**是什么**：在多步任务推进过程中，**预先约定好的暂停核对点**。到达该点时 Agent 停下来做自检或请人确认，**通过才进入下一阶段**。

**它解决的核心问题**：多步任务有依赖传递性——第 2 步错，第 3~N 步会基于错误结果继续跑，到最后才发现，**返工成本指数级上升**；如果中途还执行了真实动作（发邮件、改数据），损失已经无法撤回。

**怎么写才算明确**（三步式）：

```
在第【几步之后】停下来 → 核对【什么内容】 → 【通过】才继续，【不通过】怎么办（停下/回滚/转人工）
```

**示例：**

> ❌ 「你看着办，有把握就行。」
> ✅ 「① 数据抓取完成后，**先输出字段口径清单交我确认**，通过后才进入分析；② 分析结论生成后，**再对照自检清单核对一遍**；③ 最终报告发送前，**生成待发版本给我终审**。」

**常见的三类检查点：**

| 类型 | 放在哪里 | 拦什么 |
|---|---|---|
| **口径确认点** | 取数/检索之后、分析之前 | 拦住"取错数据、取错口径" |
| **中间结果自检点** | 每一步产出之后 | 拦住"字段缺失、格式不符、不可解析" |
| **终审发布点** | 对外交付/不可逆动作之前 | 拦住"错误结论被真实执行出去"（→ 第五章人工确认） |

> ⚠️ **高频辨析**：阶段检查点 ≠ 只是"让它慢一点"。它的价值在于**在错误还能低成本修正的时候把错误拦住**。

### 3.5 四要素速查卡（考前 1 分钟）

```
目标      → 交付什么？什么算做完？
资料来源  → 依据什么？查不到怎么办？（答：说未找到，不许编）
工具边界  → 能动哪些？禁止哪些？哪些要人确认？
阶段检查点→ 何时停下？核对什么？不通过怎么处置？
```

## 四、⭐⭐ 自检清单三要求专章（官方原话：具体、可核对、有证据）

> **官方原文**：「**自检清单要具体、可核对、有证据。**」

**定位一句话**：自检清单是 Agent 交付前的**验收闸门**——写得好，它是过滤器；写得含糊，它只是一句自我安慰。

| 要求 | 回答的问题 | 含义 | 怎么检验这条够不够格 |
|---|---|---|---|
| **具体** | 检查**什么**、按**什么门槛**判定？ | 把"好不好"翻译成"哪个字段、满足什么条件"；含对象、环节、判定阈值 | 换个不熟业务的人来对照，**能不能得到同一个结论**？ |
| **可核对** | 能不能**逐项打勾**判定通过/不通过？ | 每条都能被机械地执行并给出是/否，不依赖主观感觉 | 这条能不能做成一张**逐项打勾的表**？还是只能"看着差不多"？ |
| **有证据** | 凭什么说它过了？ | 每条都要求留下**可展示的凭证**（原文出处、工具返回值、计算结果、失败报错），供第三方复核 | 别人复核时，能不能**看到那条凭证**，而不是只看到一个"✅"？ |

> 📌 **三者关系**：**具体**解决"检查项不存在歧义"，**可核对**解决"结论可以稳定复现"，**有证据**解决"结论可以被追责和复盘"。缺任一条，清单都会退化成形式。

---

### 4.1 反例：模糊的清单长什么样（考试常拿来当错误选项）

| ❌ 模糊写法 | 它违反了哪一条 | 为什么没用 |
|---|---|---|
| 「检查一下内容是否准确」 | 不**具体** | 什么叫准确？没有判定对象与门槛，模型只能自己给自己发合格证 |
| 「确保整体质量达标」 | 不具体 + 不可核对 | 全靠主观感觉，不同人不同 Agent 结论完全不同 |
| 「数据应该是正确的」 | 不可核对 | 没有数据源可比对，无法逐项判定 |
| 「注意不要有错误」 | 不可核对 | 这是**祈使句**，不是检查项；没有"查出来了怎么办"的动作 |
| 「已检查完毕」 | 无**证据** | 只有一个结论，没有留下任何可供复核的凭证 |

> ⚠️ **识别口诀**：凡是出现「**准确 / 合理 / 完善 / 适当 / 差不多 / 质量好**」这类形容词而**没有判定门槛和凭证**的，一律是不合格清单。

---

### 4.2 正例：合格的清单长什么样

| 检查项 | 具体（对象+门槛） | 可核对（怎么打勾） | 有证据（留下什么） |
|---|---|---|---|
| 数据一致性 | 报告中每个数字必须能在源表 `销售明细-08.xlsx` 的「华东」页签找到同名行 | 逐个数字回溯比对，命中为✅、查无为❌ | 记录每个数字的**源表行列位置** |
| 依据可溯源 | 每条政策结论必须注明知识库文档名 + 章节号 | 缺出处的条目直接判❌ | 保留检索到的**原文片段** |
| 格式可交付 | 输出必须能被标准 JSON 解析器解析，且含 5 个指定字段 | 跑一次解析，通过为✅ | 保留**解析结果 / 报错信息** |
| 范围合规 | 不得出现来源清单之外的任何数据来源 | 列出全部引用来源与白名单比对 | 保留**引用来源清单** |
| 工具安全 | 本轮未调用任何白名单外的工具，未发生删除/外发操作 | 比对工具调用日志 | 保留**调用记录**（详见 M6 审计追踪） |

**一份可直接套用的模板：**

```
自检清单（每条后面必须能贴上证据）
□ 交付物形态符合要求：________（附：文件/输出预览）
□ 必填字段齐全，无空缺：________（附：字段清单）
□ 每个数字可回溯到指定源：________（附：源表行列位置）
□ 每条结论有出处（文档名+章节）：________（附：原文片段）
□ 未引用白名单外的来源：________（附：引用清单）
□ 未发生禁止类工具调用：________（附：调用记录）
□ 未通过项已列出并已修正/已转人工：________
```

> 📌 **记住「四条不合格判定」**：凡检查项里出现 **形容词没有门槛**、**结论没有凭证**、**只有要求没有动作**、**不合格了没有处置** 中的任何一条，就不算合格的清单。

---

### 4.3 两个「不等于」（高频混淆点，必考）

| 说法 | 判断 | 正解 |
|---|---|---|
| 自检清单齐全 = 可以不要人工审核 | ❌ | 自检是 **Agent 按清单自动核对**，解决的是"常见错误可以批量拦住"；**高风险动作的拍板权在人**（第五章）。官方把两者并列写出，说明**自检替代不了人工确认** |
| 按清单自检 = 让模型多生成几个版本挑最好的（best-of-N 采样） | ❌ | best-of-N 只是**多次采样择优**——只有"挑"，没有"针对发现的具体问题去修正"，也不产生证据；自检是「**逐项核对 → 发现具体不符 → 带着问题修正 → 再审**」，有明确的修正靶向与留痕 |

**还须记住的两个"不能"：**

- 自检**不能保证 100% 正确**——清单本身可能有漏洞、模型自评也可能不准，它提升的是**稳定性与可拦截率**，不是消除错误。
- 自检**必须设重试/停止上限**——否则会陷入反复修正的循环，导致时延与调用成本失控；超限时**转人工**。

## 五、⭐ 高风险动作必须人工确认（官方硬性规则）

> **官方原文**：「**高风险动作必须人工确认。**」
> ⚠️ 注意这是官方给出的**陈述句规则**，不是建议。凡看到选项说「自检足够完善时可免除人工确认」「由 Agent 自主判断是否跳过确认」，一律判错。

### 5.1 哪些算高风险动作

判据很简单——满足以下任一条即视为高风险：**不可逆（undone 成本极高）**、**对外产生实际影响**、**涉及资金/数据资产/他人权益**。

| 类别 | 典型动作 | 为什么高风险 |
|---|---|---|
| **删除 / 覆盖** | 删除文件、清空目录、覆盖已有文档、删库 | **不可逆**，误操作难以恢复 |
| **对外发送** | 发邮件/群消息给客户或外部联系人、提交表单、发布至公网 | 一旦发出**无法撤回**，且直接影响公司形象 |
| **支付 / 交易** | 下单、付款、退款、修改价格、动用额度 | 直接涉及**资金**，损失真实且难以追回 |
| **改生产数据** | 修改线上数据库、变更配置、执行生产环境命令 | 影响真实业务运行，可能引发**系统性故障** |
| **对外发布** | 发布公告、发布营销内容、对外答复政策口径 | 属于**对外承诺**，错发的代价远高于内部草稿 |
| **合同 / 承诺类** | 生成并签署合同、给出法律/医疗/金融结论 | 官方 M6 明确的高风险领域，**AI 不能替代最终责任人** |

### 5.2 为什么要人工确认

1. **Agent 会犯错，且错误是有执行力的**——普通问答错了只是答错，Agent 错了是**做错了**，损失已经发生。
2. **自检清单拦不住"清单之外的错"**——清单是人写的，覆盖不到的盲区恰恰是最危险的地方。
3. **责任不能被转移**——官方金句：「**AI 可以辅助整理和起草，但不能替代最终责任人。**」
4. **合规要求**——医疗、金融、合同、对外发布等场景本身就要求人工复核留痕（详见 M6）。

### 5.3 怎么落地（三件套）

| 落地手段 | 做法 | 对应四要素 |
|---|---|---|
| **① 事前划定清单** | 明确列出哪些动作属于高风险、必须停下来等人 | **工具边界**（3.3） |
| **② 事中卡住执行** | 到达高风险动作时**只生成待执行草稿/预案**，由人点击才真正执行 | **阶段检查点**（3.4） |
| **③ 事后留痕可查** | 记录谁确认的、确认了什么、依据是什么 | M6 **审计追踪 / 来源留存** |

**示例：**

> ❌ 「接到告警后，你可以自行判断是否需要重启服务并直接执行。」
> ✅ 「接到告警后先完成查询与原因分析并输出处置建议；涉及**重启服务、回滚版本、修改生产配置**的动作，一律生成操作预案提交我确认，**未经确认不得执行**；执行过程与确认人全程留痕。」

### 5.4 易错辨析

| 说法 | 判断 | 说明 |
|---|---|---|
| 自检闭环做得足够好，高风险动作就可以由 Agent 自主执行 | ❌ | 官方明确「**必须**人工确认」，且自检无法覆盖清单之外的错误 |
| 人工确认只针对对外发布类动作 | ❌ | 删除、支付、改生产数据同样属于高风险 |
| 高风险动作让 Agent 生成草稿、由人审阅后执行，符合要求 | ✅ | 这正是官方「协作方式」的典型落地 |
| 人工确认只需要有一个人点确认，不需要留痕 | ❌ | 合规要求留痕可追溯（详见 M6） |

## 六、Skill、工具调用、MCP、知识库、桌面 Agent

### 6.1 Skill：固化重复工作方法（官方措辞）

> **官方原文**：「理解 **Skill 用来固化重复工作方法**。」

**定义（用官方措辞背）**：**Skill 是把一套重复性的工作方法固化下来、可反复调用的可复用单元。**

```
Skill = 流程步骤（先做什么、后做什么）
      + 所需工具（每一步要调用哪些工具 / 查哪个知识库）
      + 约束与验收标准（格式要求、禁用行为、什么算做合格）
```

**为什么需要 Skill（它解决的痛点）**：同一件事每次都靠临时写一段长提示词 → 说法不一致、工具调用顺序全靠当时的心情、质量和格式不稳定、别人无法复用。**Skill 把"这次怎么说"变成"这套活儿以后都这么干"。**

**Skill 与提示词的区别（考辨析必背）：**

| 对比维度 | Skill | 提示词 |
|---|---|---|
| 官方定位 | **固化重复工作方法** | 优化单次输入（见 M2） |
| 粒度 | 一套**完整的多步工作方法** | 一次交互的说法/指令 |
| 是否含工具编排 | ✅ 明确规定了何时调哪个工具 | ❌ 一般不含 |
| 是否含验收标准 | ✅ 通常自带，直接支撑自检清单 | 视写法而定 |
| 复用性 | 沉淀为**可复用资产**，换人换会话直接套用 | 每次重写、难沉淀 |

> 📌 **一句话**：工具回答"**能做什么**"，Skill 回答"**这件事该怎么干**"，**Skill 编排**回答"**这些事按什么顺序干**"。

**Skill 编排**：把多个 Skill / 工具按依赖关系组织成一个工作流（A 的产出是 B 的输入，或按条件分支选择不同 Skill）。

**三个「不是」：**

| 说法 | 判断 | 正解 |
|---|---|---|
| Skill 等于一句写得很长的提示词 | ❌ | 关键增值在于**工具集合 + 约束/验收标准 + 可复用** |
| Skill 会给模型增加新能力 | ❌ | 它封装的是**已有的模型能力 + 工具**，不产生新能力 |
| 用了 Skill 就一定能做对 | ❌ | 流程设计本身有问题照样错，仍需自检清单与阶段检查点 |

---

### 6.2 工具调用（Function Calling）

**一句话：模型不执行工具，模型只是"说出"它想调用什么。**

```
① 事先告诉模型有哪些工具（名称 / 功能描述 / 入参格式）
② 模型判断需要用工具时，输出【结构化的调用请求】（工具名 + 参数）
③ 由模型之外的运行时（Agent）执行该工具，拿到返回值
④ 把返回值作为新的上下文回灌给模型，模型继续推理或直接作答
```

| 要点 | 说明 |
|---|---|
| 模型负责 | 决定"**要不要调、调哪个、参数填什么**" |
| 运行时负责 | 真正执行、处理异常、把结果回灌 |
| 为什么必须结构化 | 自然语言不可靠，结构化请求才能被程序稳定解析执行 |
| **不解决什么** | 工具调用**不给模型增加知识**（那是知识库/微调），也**不保证结果正确**（工具可能失败、参数可能填错） |

> ⚠️ 最高频陷阱：「模型在执行过程中**直接执行**被调用的程序」 → ❌，**执行在模型之外**。

---

### 6.3 MCP（只考作用与定位，主考点在 M3）

> ⛔ **官方明示不考协议实现细节**（握手、报文格式、传输方式等一律不考）。
> 📌 **主考点归属 M3**（官方把 MCP 放在「考试内容 3 · 增强大模型应用的能力」）。本模块只掌握下面这一句用法层表述。

**本模块要掌握的全部内容（一句）：**

> **MCP 是一套让 Agent / 应用更方便地连接外部工具与数据源的通用方式**——按同一方式适配一次，就可以被多处使用，不必为每个工具单独做一套对接。

**必须记住的两条边界：**

| 说法 | 判断 | 原因 |
|---|---|---|
| MCP 是一个具体好用的工具 | ❌ | MCP 是**连接方式/标准**，真正执行动作的是被连进来的**工具** |
| MCP 等同于 Function Calling | ❌ | Function Calling 是**模型侧**的调用机制（怎么表达调用意图）；MCP 是**连接侧**的方式（工具与数据源怎么接进来）。**层次不同、不是互相替代** |

> 📌 **类比速记**：MCP ≈ **接口标准**（Type-C），工具 ≈ **外接设备**（U 盘、打印机），Function Calling ≈ **发出的驱动调用**，Agent ≈ **用电脑干活的人**。
> ⚠️ 类比只用于理解定位，**考试不会考接口如何实现**。

---

### 6.4 个人 AI Agent 接入知识库

**Agent + 知识库 = 既有依据地回答、又能动手把事做掉的「执行体」。**

| 只有知识库（RAG） | 只有工具调用 | 知识库 + 工具调用（Agent） |
|---|---|---|
| 能查到答案并讲清楚 | 能做事但**不知道你的规矩** | **按库里的规矩做事** |

典型链路：用户提需求 → Agent 先**检索知识库**拿到依据/标准/模板（这就是四要素中的「**资料来源**」）→ 依据检索结果**调用工具执行** → 输出交付物并附出处。

**接了知识库，哪些变了、哪些没变（高频辨析）：**

| ✅ 变了 | ❌ 没变 |
|---|---|
| 能使用**私域/最新**知识，结论可追溯出处 | **不提升模型本身**的推理能力 |
| 减少"不知道就编"的幻觉 | **不等于把知识永久写进模型参数**（那是**微调**） |
| 文档更新后**立即生效**，无需重新训练 | **不等于获得执行外部动作的能力**（那是**工具**） |

### 6.5 桌面 Agent

> ⚠️ **产品名称待核实**：具体产品名称、安装包获取方式、菜单路径**不在本资料考证范围内**，也不考安装步骤与配置项。**只考概念与定位。**

**桌面 Agent = 运行在用户本地设备上的 Agent 形态。**

| 维度 | 桌面 Agent（本地） | 云端 Agent（服务端） |
|---|---|---|
| 运行位置 | **用户自己的电脑 / 本地环境** | 云端服务器 |
| 可达资源 | **本地文件系统、本地命令行/终端、本地已安装软件** | 云端 API、SaaS 服务、云数据库 |
| 典型任务 | 整理本地文件夹、批量重命名、读改本地文档、跑本地脚本 | 在线助手、定时任务、事件触发流程 |
| 关键特点 | 数据可留在本机、贴近个人工作流 | 可长期在线、多端访问、易横向扩展 |

**三条核心考点：**
1. **形态定位**：本地运行 → 能触碰**本地文件与终端**，这是它区别于云端 Agent 的关键。
2. **因为是同一套范式**，桌面 Agent 依然遵循「感知—思考—行动」，四要素、Skill、自检清单、人工确认**同样适用**。
3. **风险同源放大**：拥有本地文件/终端权限 → **权限最小化** + **高风险动作人工确认**（删除、覆盖本地文件属高风险）缺一不可。

## 七、⭐ 适用场景、局限性与协作使用方式

> **官方原文**：「AI Agent 的基本能力、**适用场景、局限性**和**协作使用方式**。」

### 7.1 适用场景（该上 Agent 的信号）

**官方「建议掌握的知识」列举的五大任务：**

| 任务类型 | 说明 | Agent 的用武之地 |
|---|---|---|
| **信息提取** | 从大量文档/网页中抽取结构化字段 | 检索 + 抽取 + 按字段清单自检 |
| **内容生成** | 写报告、文案、摘要 | 查资料 → 按模板生成 → 对照清单自检 |
| **资料分析** | 读表取数、比对、归因 | 多次取数 + 反复验证 + 阶段检查点 |
| **知识问答** | 基于企业资料的问答 | 接知识库限定**资料来源**，答不上就说未找到 |
| **办公自动化** | 批量改文档、整理文件、生成工单、发通知 | 多步执行 + 工具调用 + 高风险动作留人工确认 |

**该上 Agent 的五个信号（满足越多越该上）：**
1. 任务**无法一步完成**，需要拆成多步
2. 步骤间**有依赖**，下一步取决于上一步结果
3. 需要调用**外部能力**（检索、接口、文件、终端）
4. 需要根据中间结果**动态调整**计划
5. 验收标准**可描述**（能写成自检清单）

---

### 7.2 局限性（何时不该上 Agent）

| 场景 | 不该上 Agent 的原因 | 应改用什么 |
|---|---|---|
| 一句话问答、闲聊、常识解释 | 单轮即可，**上 Agent 只会增加时延、成本与出错面** | 直接调用模型 + 优化提示词 |
| 只缺私域/最新知识，不需要执行动作 | 本质是"不知道"，不是"不会做" | **知识库 / RAG** |
| 只要求统一的格式、语气、风格 | 本质是"行为不稳定" | **微调** |
| 单次固定动作（查一次天气、翻译一句） | 单步即可闭环 | 单次**工具调用**即可 |
| 验收标准写不出来 | **无法写自检清单 → 无法验收 → 不该自动化** | 先人工跑通流程，再考虑固化 |

> 📌 **最重要的一条局限性**：**写不出验收标准的任务不要交给 Agent 全自动跑。** 这正是官方要求「自检清单要具体、可核对、有证据」的原因。

**其他固有局限：**

| 局限 | 表现 | 应对方向 |
|---|---|---|
| **错误会被执行出去** | 普通问答错了只是答错；Agent 错了会真的造成损失 | 阶段检查点 + **高风险动作人工确认** |
| **循环失控 / 成本与时延** | 多轮调用重复打转，token 与时延远超单轮问答 | 明确适用范围、**设重试与步数上限**、超时停止 |
| **权限与越界风险** | 拥有文件/终端/接口权限后误删、误改、误发 | **权限最小化**、工具边界白名单、留审计记录 |
| **幻觉被放大、错误沿链路传播** | 一步错导致后续全错 | 指定资料来源、要求标注出处、阶段检查点分段拦 |

---

### 7.3 协作使用方式（人与 Agent 怎么分工）

> 官方把它写成「**协作**使用方式」，隐含的判断是：**Agent 是协作者，不是替代者。**

| 环节 | 谁主导 | 具体动作 |
|---|---|---|
| **定目标** | **人** | 明确交付物、范围、成功标准（M4-K03） |
| **定资料来源** | **人** | 指定可用/禁用来源与查不到怎么办（M4-K04） |
| **定工具边界** | **人** | 白名单、读写限制、高风险动作清单（M4-K05） |
| **检索 / 起草 / 计算 / 批量执行低风险动作** | **Agent** | 多轮取数、草稿生成、格式化输出 |
| **自检** | **Agent** | 按「具体·可核对·有证据」的清单逐项核对并修正 |
| **阶段确认** | **共担** | Agent 到检查点停下提交，人确认是否继续 |
| **高风险动作拍板** | **人** | 删除、外发、支付、改生产数据、对外发布（M4-K08） |
| **最终责任** | **人** | 官方金句：**AI 可以辅助整理和起草，但不能替代最终责任人** |

> 📌 **一句话**：**Agent 负责"多、快、稳地干"，人负责"定方向、设边界、拍高风险、担最终责任"。**

## 八、概念层级辨析（用官方用词）

### 8.1 四层结构图

```
┌──────────────────────────────────────────────────────┐
│ L4  作业方法：Skill（流程SOP + 所需工具 + 约束/验收标准）    │
│      └─ Skill 编排：多个 Skill 按依赖组成工作流            │
├──────────────────────────────────────────────────────┤
│ L3  执行体：Agent（感知-思考-行动循环，对目标负责；含桌面形态）│
├──────────────────────────────────────────────────────┤
│ L2  连接与执行：MCP（怎么接进来）｜工具（连进来后能做什么）    │
├──────────────────────────────────────────────────────┤
│ L1  调用机制：Function Calling（结构化地表达调用意图）       │
├──────────────────────────────────────────────────────┤
│ L0  基础：大模型（理解 + 推理 + 生成）                     │
└──────────────────────────────────────────────────────┘
```

> 说明：Skill（作业方法）位于最上层，它**规定** Agent 该按什么流程调用哪些工具；Agent 位于 Skill 之下，是被调度去干活的执行体。**层级是"谁规定谁"，不是"谁包含谁"，考试只要求能区分四者定位。**

### 8.2 一句话区分（横向对照表）

| 概念 | 一句话 | 类比 | 常被误认为 |
|---|---|---|---|
| **Function Calling** | 模型**表达"我要调用谁、传什么参"**的机制 | 发出的驱动调用 | 被当成工具本身 |
| **工具 / 工具调用** | 具体可执行某个动作的能力单元 | 外接设备（U 盘、打印机） | 被当成连接方式 |
| **MCP** | 让 Agent **把工具与数据源接进来**的通用方式 | Type-C 接口标准 | 被当成工具本身 |
| **Skill** | 把一堆工具 + 流程 + 规矩封装成的**工作方法** | 作业指导书 / SOP | 被当成一句长提示词 |
| **Agent** | 用大脑（L0）调度以上全部、**为目标负责**的执行体 | 干活的人 | 被当成"更强的模型" |

### 8.3 四组常考对比结论

1. **MCP ≠ 工具**：MCP 是"**怎么接进来**"，工具是"**接进来之后能提供什么能力**"。
2. **MCP ≠ Function Calling**：Function Calling 在**模型侧**（如何把意图说成结构化请求）；MCP 在**连接侧**（工具与数据源如何接进来）。二者不在同一层，**不是互相替代**关系。
3. **Skill ≠ 提示词**：提示词偏"**这次怎么说**"；Skill 是"**这套活儿以后都这么干**"，且含工具集合与验收标准，是可复用资产。
4. **Agent ≠ 更强的模型**：Agent 是**基于大模型的应用架构**，模型能力仍是底座；也没有"有了 Agent 就不需要好提示词"这回事。

## 九、易错辨析表

### 9.1 手段辨析：该用哪个（官方五选一 + 人工确认）

| 需求 | 正确方案 | 典型错误选法 |
|---|---|---|
| 回答质量不稳定、理解有偏差 | **优化输入（提示词）** | 上 Agent |
| 缺公司制度、最新产品信息等私域/时效知识 | **接入知识库（RAG）** | 微调 |
| 需要实时数据、确定性计算或业务动作 | **调用工具** | 微调 |
| 输出格式、文风不统一 | **微调** | 知识库 |
| 多步任务 + 需边看结果边调整 + 调外部工具 | **协作 Agent** | 单次工具调用 |
| **删除 / 外发 / 支付 / 改生产数据 / 对外发布** | **保留人工确认** | 交给 Agent 自主执行 |
| 把一套多步骤工作方法沉淀复用 | **Skill** | 每次重写长提示词 |
| 想让产出稳定达标 | **具体·可核对·有证据的自检清单 + 自检闭环** | 多生成几份挑一个（best-of-N） |
| 简单单轮问答 | **直接调模型** | 上 Agent（过度设计） |

### 9.2 四要素辨析（🆕 本轮新增）

| 做法 | 属于哪个要素 |
|---|---|
| 「输出一份 ≤800 字、含 3 张图表的周报」 | **目标** |
| 「只依据知识库『售后政策-v3.2』，库中没有就答未找到」 | **资料来源** |
| 「只允许读取 `/shared/report/`，禁止写入和删除」 | **工具边界** |
| 「数据抓取完成后先输出口径给我确认，通过再分析」 | **阶段检查点** |
| 「调用上一步生成的 Pass 结果继续下一步」 | ❌ 不是检查点，缺少停下核对动作 |
| 「检查一下内容是否准确」 | ❌ 不合格的自检项（不具体、不可核对、无证据） |

### 9.3 概念辨析

| 说法 | 判断 | 说明 |
|---|---|---|
| Agent 是比大模型更强的模型 | ❌ | 是**基于大模型的应用架构**，模型能力仍是底座 |
| Agent 的价值是把「回答问题」推进到「完成任务」 | ✅ | 官方原文金句 |
| Agent 只需给个目标，其余它可以自己搞定 | ❌ | 官方要求明确**四要素** |
| 有了 Agent 就不需要好的提示词 | ❌ | 目标描述、工具说明、约束仍是质量关键 |
| 工具执行是在模型内部完成的 | ❌ | 模型**只输出调用请求**，执行在模型之外的运行时 |
| 工具调用会给模型补充知识 | ❌ | 提供的是**能力**，不是知识（知识靠知识库/微调） |
| MCP 是一个强大的工具 | ❌ | MCP 是**连接方式/标准**，真正执行动作的是工具 |
| 有了 MCP 就不需要 Function Calling | ❌ | 不同层次，通常共存 |
| Skill 就是写得很长的一条提示词 | ❌ | 含工具集合与验收标准，可复用、可编排 |
| Skill 的作用是固化重复工作方法 | ✅ | 官方原文措辞 |
| 自检清单只要写得"全面"就够了 | ❌ | 官方要求**具体、可核对、有证据** |
| 自检清单完善后高风险动作可由 Agent 自主执行 | ❌ | 官方：**高风险动作必须人工确认** |
| 按清单自检等同于 best-of-N 多次采样择优 | ❌ | 后者只"挑"不"改"，且无针对性修正与留痕 |
| 自检闭环可以不设上限，让它改到对为止 | ❌ | 必须设重试上限，超限转人工 |
| 自检闭环能保证结果百分百正确 | ❌ | 只能提升稳定性，标准本身也可能有漏洞 |
| 桌面 Agent 与云端 Agent 是两种技术路线 | ❌ | 同一套范式，**部署形态与可达资源**不同 |
| Agent 接入知识库后，模型就永久学会了知识 | ❌ | 检索是**外挂**，文档更新即刻生效；写进参数是微调 |
| 接了知识库就自动获得写文件、发请求的能力 | ❌ | 那是**工具**的职责，与知识库无关 |
| Agent 出错只是答错，不会造成实际损失 | ❌ | **Agent 有执行力**，错误会被执行出去（这是它的主要局限） |

### 9.4 判断题速记

| 表述 | 对/错 |
|---|---|
| Agent 四要素 = 目标、资料来源、工具边界、阶段检查点 | ✅ |
| 自检清单三要求 = 具体、可核对、有证据 | ✅ |
| 高风险动作必须人工确认 | ✅ |
| 阶段检查点解决"何时拦"，自检清单解决"拦下来查什么" | ✅ |
| 「查不到就说未找到」是对资料来源缺省行为的正确要求 | ✅ |
| 感知、思考、行动构成 Agent 的闭环 | ✅ |
| 简单单轮问答不应引入 Agent | ✅ |
| 桌面 Agent 拥有本地文件与终端权限，需权限最小化 | ✅ |
| Skill 适合用来固化一次性的、只做一遍的任务 | ❌（固化**重复**工作方法） |
| 检查项里出现"准确/合理/完善"等形容词没有门槛，算合格 | ❌ |
| Agent 可以替代最终责任人签署对外文件 | ❌ |
