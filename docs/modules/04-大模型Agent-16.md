### 为什么本模块涨幅最大

> V2.4 的整体导向是：**从「会让模型答得好」转向「会让模型替你把活干完」**。
> 这一转向的载体就是 Agent。所以课时从「讲概念」直接落到「装一个 Agent → 接知识库和工具 → 固化成 Skill → 加自检闭环」这条**完整落地链路**。

### 一句话主线

> **「给大模型装上感知、思考和手脚，让它自己去把活干完，并且自己检查活干没干好。」**
>
> - **感知 Perception**：拿到任务与环境信息（用户输入、文件内容、检索结果、工具返回值）
> - **思考 Reasoning**：把目标拆成步骤，决定下一步干什么（含规划、反思）
> - **行动 Action**：真正调用工具/API/终端去执行，并把结果拿回来继续推进

### 技术选型决策树（V2.4 官方口径，必背）

| 症状 | 首选方案 |
|---|---|
| 回答不够好（表达/理解偏差） | **先优化提示词** |
| 缺私域知识 / 最新知识 | **RAG（知识库）** |
| 需要固定格式、固定风格 | **微调** |
| **任务复杂、多步执行、需要调外部 API / 工具** | **Agent** |
| 超出模型本身能力边界（联网、实时、计算、执行） | **插件 / 工具** |

> ⚠️ M3 里那条「成本递增顺序」在 V2.4 的完整版是：**提示词 → RAG/插件 → 微调/Agent**。
> Agent 不是「提示词写不好时的替代品」，而是**任务形态变了**（从"一问一答"变成"多步执行"）才上的方案。

## 3. 逐考点详解

### M4-K01 · Agent 的定义与三大核心能力 🟢`[A]`

**定义（背下来）：Agent = 以大模型为"大脑"，能感知环境、自主规划决策、并调用工具执行动作，通过多轮「思考—行动—观察」循环完成目标的系统。**

与普通大模型应用最本质的区别：**普通应用是"输入 → 输出"的一次性映射；Agent 是一个带反馈的循环，且它真的能对外部世界产生作用。**

| 核心能力 | 英文 | 它在干什么 | 缺了会怎样 |
|---|---|---|---|
| **感知** | Perception | 接收并理解任务与环境状态：用户指令、文件内容、检索结果、**工具返回的结果** | 拿不到外界反馈，只能凭空设想，等于闭眼干活 |
| **思考** | Reasoning | 拆解目标、规划步骤、判断该调哪个工具、评估当前结果是否达标 | 不会拆任务，走一步算一步，复杂任务必崩 |
| **行动** | Action | 真正调用工具 / API / 终端去执行，把结果拿回来喂给下一轮思考 | 只会"说"，不会"做"，退化成一个聊天机器人 |

**三者关系是闭环，不是并列：**

```
        感知 ←────────── 工具返回的结果 / 环境反馈
         │
         ▼
        思考（这一步做什么？做完了吗？不达标怎么办？）
         │
         ▼
        行动（调用工具执行）
```

**不解决的 / 易错：**
- Agent 不是"更强的模型"，它是**大模型之上的一种应用架构**，模型推理能力仍是基础。
- 有了 Agent 不代表不需要好提示词：任务指令、工具描述、约束条件写得含糊，Agent 一样乱来。

### M4-K02 · ReAct 范式 🟡`[B]`

**ReAct = Reasoning（推理）+ Acting（行动）交替进行。**

```
Thought（想）：用户要的是A，我需要先查B
Action（做）：调用 搜索工具("B")
Observation（看）：返回结果为 X
Thought（想）：有了 X，还差 C，再算一次
Action（做）：调用 计算器(...)
Observation（看）：得到 Y
Answer（答）：最终结论是……
```

**为什么要有它（核心价值）：把模型的推理过程"外化"成可观察、可干预、可追溯的轨迹。**
- 便于定位错在哪一步（是查错了，还是算错了，还是结论归纳错了）
- 让外部世界的事实（工具返回值）可以**中途纠正**模型的思路，抑制幻觉

### M4-K03 · CoT / ToT 的定位 🟡`[B]`

| 概念 | 是什么 | 属于 M4 的哪一环 | 是不是 Agent |
|---|---|---|---|
| **CoT（思维链）** | 让模型把推理步骤一步步写出来再得结论 | **思考**环节的一种**提示策略** | ❌ 仍是一次生成，"想"完直接出答案 |
| **ToT（思维树）** | 在多个推理分支上展开搜索、评估、择优 | **思考**环节的搜索/规划策略 | ❌ 同样不调用外部工具、不改变外部状态 |
| **ReAct** | 推理与**工具行动**交替、有真实反馈 | 完整覆盖了思考 + 行动 | ✅ 属于 Agent 的典型范式 |

> **一句话记：CoT/ToT 只是"想得更细"，ReAct 才是"想完真的去做、做完再看"。**

---

### M4-K04 · 何时用 Agent / 何时不用 🟢`[A]`

**该上 Agent 的信号（满足越多越该上）：**
1. 任务**无法一步完成**，需要拆解成多个步骤
2. 步骤之间**有依赖**，下一步取决于上一步的结果
3. 需要调用**外部能力**（检索、API、数据库、文件、终端）
4. 需要根据中间结果**动态调整**计划
5. 完成质量的**验收标准可描述**（便于做自检）

**不该上 Agent 的场景（考试高频反向题）：**

| 场景 | 应改用什么 |
|---|---|
| 一句话问答、闲聊、常识解释 | 直接调用模型（优化提示词） |
| 只涉及私域/最新知识，不需要执行动作 | **RAG / 知识库** |
| 只要统一格式、统一语气风格 | **微调** |
| 单次查天气、单次翻译这类**固定单步动作** | 单次工具/插件调用即可，不必搭多轮循环 |

> **陷阱记忆：不是"问题难"就要上 Agent，而是"任务需要多步执行与外部交互"才上 Agent。**
> 简单任务上 Agent 只会增加时延、成本与出错面。

### M4-K05 · 工具调用 / Function Calling ⭐V2.4 新增 🟢`[A]`

**这是最容易出概念题的一节，务必记住一句话：模型不执行工具，模型只是"说出"它想调用什么。**

标准流程（三步 + 回灌）：

```
① 事先告诉模型有哪些工具（名称 / 功能描述 / 入参格式）
② 模型判断需要用工具时，输出【结构化的调用请求】（工具名 + 参数），而不是自然语言
③ 由外部程序（Agent 运行时）执行该工具，拿到返回值
④ 把返回值作为新的上下文回灌给模型，模型继续推理或直接作答
```

| 要点 | 说明 |
|---|---|
| **模型负责什么** | 决定"要不要调、调哪个、参数填什么" |
| **运行时负责什么** | 真正执行、处理异常、把结果回灌 |
| **为什么是结构化** | 自然语言不可靠；结构化请求才能被程序稳定解析执行 |
| **没有工具调用会怎样** | 模型只能"描述"要做什么，无法真正产生作用（比如只能说"我已帮您下单"，实际没下单） |

**不解决的：**
- 工具调用**不给模型增加知识**，只给它增加**能力**
- 工具调用不保证结果正确 —— 选错工具、填错参数、工具本身失败都可能发生

### M4-K06 · MCP 协议 ⭐V2.4 新增 🟢`[A]`

**MCP（Model Context Protocol）= 模型上下文协议：一套用于标准化「模型/Agent 如何与外部数据源、工具建立连接」的开放协议。**

**它解决的核心痛点：集成碎片化（N × M 问题）。**

```
没有统一协议时： N 个 Agent/应用  ×  M 个工具/数据源  =  需要写 N×M 个定制适配器
有了统一协议后：每方只需按协议适配一次  →  变成 N + M
```

**必须记牢的三条"不是"：**

| 说法 | 判断 | 原因 |
|---|---|---|
| MCP 是一个好用的工具 | ❌ | MCP 是**连接工具的协议/标准**，工具才是执行具体动作的东西 |
| MCP 等同于 Function Calling | ❌ | Function Calling 是模型侧的**调用机制**（怎么表达调用意图）；MCP 是**连接协议**（怎么发现与对接外部资源）。二者层次不同、可并存 |
| MCP 能让模型自己学会用工具 | ❌ | 协议只解决「接得上、描述得清」，用得好不好仍取决于模型能力与工具描述质量 |

> **类比速记：MCP ≈ USB / Type-C 接口标准，工具 ≈ 外接设备（U 盘、打印机），Function Calling ≈ 操作系统发出的驱动调用，Agent ≈ 使用电脑干活的人。**

### M4-K07 · 桌面 Agent ⭐V2.4 新增 🟢`[A]`

> ⚠️ **产品名称待核实**：官方课时标题为「安装桌面 Agent，开始用它干活」，但**具体产品名称 / 安装包获取方式 / 菜单路径不在本资料的考证范围内**，考试也几乎不可能考安装步骤。**只考概念与定位。**

**桌面 Agent = 运行在用户本地设备上的 Agent 形态。**

| 维度 | 桌面 Agent（本地） | 云端 Agent（服务端） |
|---|---|---|
| 运行位置 | **用户自己的电脑 / 本地环境** | 云端服务器 |
| 可达资源 | **本地文件系统、本地命令行/终端、本地已安装软件** | 云端 API、SaaS 服务、云数据库 |
| 典型任务 | 整理本地文件夹、批量重命名、读改本地文档、跑本地脚本 | 对外提供服务的在线助手、定时任务、webhook 触发流程 |
| 关键特点 | 数据不出本机、贴近个人工作流 | 可长期在线、多端访问、易横向扩展 |

**核心考点三条：**
1. **形态定位**：本地运行 = 它能接触**本地文件与终端**，这是它区别于云端 Agent 的关键。
2. **正因为能动本地资源，权限与风险是必考点**：文件误删、执行危险命令 → 需要**权限最小化**与**关键动作二次确认**。
3. 桌面 Agent 依然遵循同一套 Agent 范式（感知/思考/行动），**不是另一种技术路线的东西**。

### M4-K08 · 知识库应用（Agent 接知识库）⭐V2.4 新增 🟢`[A]`

**Agent + 知识库（RAG）= 既有依据地回答，又能动手把事做掉的「执行体」。**

| 只有 RAG | 只有工具调用 | RAG + 工具调用（Agent） |
|---|---|---|
| 能查到答案并讲清楚 | 能做事但不知道你的规矩 | **按知识库里的规矩做事** |

典型链路：用户提需求 → Agent 先**检索知识库**拿到依据/标准/模板 → 依据检索结果**调用工具执行**（写文件、发请求、生成工单）→ 输出交付物并附出处。

**接了知识库之后，哪些变了、哪些没变（高频辨析点）：**

| 变化（✅） | 没变化（❌） |
|---|---|
| 能使用**私域/最新**知识，答案可追溯出处 | 不会提升模型本身的推理智商 |
| 减少"不知道就编"的幻觉 | 不等于把知识**永久写进模型参数**（那是微调） |
| 文档更新后**立即生效**，无需重新训练 | 不等于给模型增加了执行外部动作的能力（那是工具） |

### M4-K09 · Skill 与 Skill 编排 ⭐V2.4 新增 🟢`[A]`

**Skill = 把一套"工作方法"固化下来的可复用单元**，通常包含三部分：

```
Skill = 流程步骤（SOP，先做什么后做什么）
      + 所需工具（过程中要调用哪些工具/知识库）
      + 约束与验收标准（格式要求、禁用行为、什么算做合格）
```

**与相关概念的差别（考辨析必背）：**

| 对比 | Skill | 提示词 | 单个工具 |
|---|---|---|---|
| 粒度 | **一套完整工作方法**（多步流程） | 一次交互的说法/指令 | 一个原子能力（如查天气） |
| 是否含工具编排 | ✅ 明确规定了什么时候调什么工具 | ❌ 一般不含 | — 本身就是被调用者 |
| 复用方式 | 沉淀为**可复用资产**，换个人/换个会话直接套用 | 每次要重写、难沉淀 | 可被多个 Skill 引用 |
| 是否含验收标准 | ✅ 通常自带，支撑自检闭环 | 视写法而定 | 只返回结果，不判好坏 |

**Skill 编排 = 把多个 Skill / 工具按依赖关系组织成一个工作流**（串起来跑：A 的产出是 B 的输入；或按条件分支选择不同 Skill）。

> **一句话：工具回答"能做什么"，Skill 回答"这件事该怎么干"，编排回答"这些事按什么顺序干"。**

### M4-K10 · 自检闭环 ⭐V2.4 新增 🟢`[A]`

**自检闭环 = Agent 产出结果后，按预先设定的校验标准自行检查；不达标则修正或重试，形成一个「生成 → 检查 → 修正」的闭环。**

```
生成初稿 → 按校验标准检查 → 通过？ ── 是 → 交付
                            │
                            否 → 带着问题回到上一步修正 → 再检查（达到重试上限则转人工/报错）
```

**四要素（缺一不可，常考"还缺什么"）：**

| 要素 | 说明 | 缺了会怎样 |
|---|---|---|
| **校验标准** | 事先定义"什么叫合格"（格式、字段完整性、是否覆盖要点、能否通过解析等） | 没有标准，"自检"就成了一句空话 |
| **检查动作** | 谁用什么方式检查（模型自评、规则校验、脚本/单测、另一个 Agent 交叉校验） | 只有要求没有动作，不会真的发生 |
| **修正反馈** | 把"哪里不合格"具体回灌给模型，让它针对性改 | 只说"重做一遍"，大概率重犯同样的错 |
| **重试上限** | 最多重试几次，超限就停止 | 可能陷入无限循环，成本与时长失控 |

**三个"不等于"（高频错误选项）：**

| 说法 | 判断 | 正解 |
|---|---|---|
| 自检闭环 = 人工审核 | ❌ | 自检是**Agent 自动完成**的检查环节；人工审核是人在环路上，二者可叠加但不是一回事 |
| 自检闭环 = 让模型多生成几个答案挑最好的（best-of-N） | ❌ | best-of-N 只是**多次采样择优**，没有"针对问题修正"的环节；best-of-N 靠运气，自检闭环靠**标准 + 反馈修正** |
| 自检闭环能保证 100% 正确 | ❌ | 检查标准本身可能有漏洞、模型可能自评不准；它**提高稳定性**，不是消除错误 |

---

### M4-K11 · Multi-Agent 协作 🟡`[B]`

**多个 Agent 按角色分工协作**：一个负责分发/统筹（主控），若干个负责专项（检索、写作、检查、执行），最后由主控汇总。

| 优点 | 代价 / 风险 |
|---|---|
| 单一 Agent 上下文不至于被塞爆，职责清晰易维护 | Agent 间通信轮次增加 → **时延与成本上升** |
| 专项 Agent 可用更聚焦的提示词/Skill，质量更稳 | 结果汇总与冲突消解变复杂，易出现责任推诿式循环 |

> 🔴`[C]` Multi-Agent 是否为 V2.4 官方必考项未核实，作为背景理解掌握，**待与官方 V2.4 大纲 PDF 核对**。

---

### M4-K12 · Agent 的局限与风险 🟡`[B]`

| 风险 | 表现 | 常规应对（考方向，不考细节） |
|---|---|---|
| **失控循环** | 反复调用同一工具、步骤来回打转，烧掉大量 token | 设最大步数 / 重试上限、超时熔断 |
| **权限越界** | 拥有文件/终端权限后误删、误改、误发 | **权限最小化**、危险操作需人工确认、重要操作留审计日志 |
| **成本与时延** | 多轮循环 = 多次调用，比单轮问答贵得多、慢得多 | 明确"值得上 Agent"的场景边界，简单任务不上 |
| **幻觉被放大** | 一步错导致后续全错，且错误被"执行"出去造成实际损失 | 引入自检闭环、关键结论要求附带出处/依据 |

## 4. V2.4 六大新增点专章 ⭐（重中之重）

> 官方明列的六个新增点：**桌面 Agent、知识库应用、工具调用、MCP、Skill 编排、自检闭环**。
> 下面的每一节都按「**是什么 / 解决什么 / 不解决什么 / 易错点**」四段式展开。

### 4.1 桌面 Agent

- **是什么**：运行在**本地设备**上的 Agent 形态，可直接读写本地文件、执行本地命令。
- **解决什么**：把 Agent 的能力延伸到**个人电脑的工作现场**——处理那些只有在本机才拿得到的文件与工具；数据留在本地。
- **不解决什么**：不代表更强的模型推理能力；长期在线、多端访问、大规模横向扩展是云端形态的强项。
- **易错点**：
  1. 误以为桌面 Agent 是另一种技术（❌，它仍是同一套感知-思考-行动范式，只是**部署形态**不同）。
  2. 忽略权限风险 —— **能动本地资源是它的价值，也是它的最大风险**，考试常在此设选项。
- ⚠️ 具体产品名称、安装方式、菜单路径**一律待核实，不作考证内容**。

### 4.2 知识库应用

- **是什么**：给 Agent 挂载**外部知识库**（检索增强），使其在执行前能先查到事实依据。
- **解决什么**：私域知识、时效知识、以及"按公司规定办事"这类需要依据的任务（如按模板生成、按制度判答）。
- **不解决什么**：不提升模型推理能力；不把知识写进模型参数；不赋予动作执行能力。
- **易错点**：把"接了知识库"等同于"模型学会了这些知识"（❌，那是**微调**做的事）。

### 4.3 工具调用（Tool Use / Function Calling）

- **是什么**：模型输出**结构化的调用请求**（工具名 + 参数），由外部运行时执行并将结果**回灌**给模型的机制。
- **解决什么**：让模型从"只能说"变成"真的能做"——查数据、发请求、写文件、操作业务系统。
- **不解决什么**：不增加知识；不保证调用结果正确（工具可能失败、参数可能填错）。
- **易错点**：认为模型**直接执行**了工具（❌，模型只负责决定调用意图，执行在模型之外）。

### 4.4 MCP 协议

- **是什么**：标准化模型/Agent 与外部数据源、工具之间**连接与交互方式**的开放协议。
- **解决什么**：消除"每个 Agent 对接每个工具都要单独写适配器"的 **N×M 集成碎片化**问题，让工具/数据源可以**一次适配、多处复用**。
- **不解决什么**：它本身**不是工具**、不执行任何动作；也不提升模型的推理或规划能力。
- **易错点**：把 MCP 当成工具或当成 Function Calling 的替代品（❌，见第 5 章层级图）。

### 4.5 Skill 编排

- **是什么**：把「**流程 SOP + 所需工具 + 约束与验收标准**」打包成可复用单元（Skill），并将多个 Skill 按依赖关系组织成工作流（编排）。
- **解决什么**：把个人经验沉淀成**组织资产**，避免每次重复写长提示词；让复杂任务的执行过程稳定、可复现。
- **不解决什么**：Skill 不产生新能力，它封装的是**已有的模型能力 + 工具**；编排也不等于"自动就能做对"，流程设计本身有问题照样错。
- **易错点**：把 Skill 等同于一句长提示词（❌，Skill 的关键增值在于**工具集合 + 约束/验收标准 + 可复用**）。

### 4.6 自检闭环

- **是什么**：产出后按**校验标准**自动检查，不达标则带着具体问题回退修正重试，直到通过或达到重试上限。
- **解决什么**：降低"一次生成就交付"的不稳定性，把偶发错误变成可拦截错误。
- **不解决什么**：不等于人工审核；不等于 best-of-N 多次采样择优；不能保证 100% 正确。
- **易错点**：漏掉"**必须有明确的校验标准**"和"**必须设置重试上限**"这两条，是最常见的丢分点。

## 5. 概念层级辨析（最高频混淆点，必背）

### 5.1 六层结构图

```
┌──────────────────────────────────────────────────────┐
│ L5  执行体：Agent（感知-思考-行动循环，对目标负责）        │
│      └─ Multi-Agent：多个 Agent 分工协作                │
├──────────────────────────────────────────────────────┤
│ L4  作业方法：Skill（流程SOP + 工具 + 约束/验收标准）      │
│      └─ Skill 编排：多个 Skill 按依赖组成工作流           │
├──────────────────────────────────────────────────────┤
│ L3  连接标准：MCP（定义如何对接/发现/描述外部资源）         │
├──────────────────────────────────────────────────────┤
│ L2  被调用对象：工具 / 插件（查天气、检索、下单、计算器…）    │
├──────────────────────────────────────────────────────┤
│ L1  调用机制：Function Calling（结构化地表达调用意图）      │
├──────────────────────────────────────────────────────┤
│ L0  基础：大模型（理解 + 推理 + 生成）                    │
└──────────────────────────────────────────────────────┘
```

### 5.2 一句话区分（横向对照表）

| 概念 | 一句话 | 类比 | 常被误认为 |
|---|---|---|---|
| **Function Calling** | 模型**表达"我要调用谁、传什么参"**的机制 | 发出的设备驱动调用 | 被当成工具本身 |
| **工具 / 插件** | 具体可执行某个动作的能力单元 | 外接设备（U 盘、打印机） | 被当成协议 |
| **MCP** | 规定上述两者**如何被发现和对接**的开放协议 | Type-C 接口标准 | 被当成工具或普通插件 |
| **Skill** | 把一堆工具 + 流程 + 规矩封装成的**工作方法** | 作业指导书 / SOP | 被当成一句长提示词 |
| **Skill 编排** | 多个 Skill 按依赖/条件组织成的工作流 | 流水线工序表 | 被当成单个工具调用 |
| **Agent** | 用大脑（L0）调度以上全部、**为目标负责**的执行体 | 干活的人 | 被当成"更强的模型" |
| **Multi-Agent** | 多个执行体分工协作 | 一个团队 | 被当成同一件事的并行重试 |

### 5.3 三组常考对比结论

1. **MCP ≠ 工具**：MCP 是"怎么连"的标准，工具是"连上之后能提供什么能力"。
2. **MCP ≠ Function Calling**：Function Calling 在**模型侧**（如何把意图说成结构化请求）；MCP 在**连接侧**（资源如何被发现与对接）。二者不在同一层，也不是互相替代关系。
3. **Skill ≠ 提示词**：提示词偏"这次怎么说"；Skill 是"这套活儿以后都这么干"，且包含工具集合与验收标准，是可复用的资产。

## 6. 易错辨析表

### 6.1 手段辨析：该用哪个

| 需求 | 正确方案 | 典型错误选法 |
|---|---|---|
| 回答质量不稳定、理解有偏差 | **优化提示词** | 上 Agent |
| 缺公司制度、最新产品信息等私域/时效知识 | **RAG / 知识库** | 微调 |
| 输出格式、文风不统一 | **微调** | RAG |
| 需要联网/计算/执行等超出模型本身的能力 | **插件 / 工具调用** | 微调 |
| 多步任务 + 需边看结果边调整 + 调外部 API | **Agent** | 单次插件调用 |
| 把一套多步骤工作方法沉淀复用 | **Skill** | 每次重写长提示词 |
| 想让产出稳定达标 | **自检闭环** | 多生成几份挑一个（best-of-N） |
| 简单单轮问答 | **直接调模型** | 上 Agent（过度设计） |

### 6.2 概念辨析

| 说法 | 判断 | 说明 |
|---|---|---|
| Agent 是比大模型更强的模型 | ❌ | 是**基于大模型的应用架构**，模型能力仍是底座 |
| Agent 必须调用工具才叫 Agent | ✅ 通常 | 「行动」是三大能力之一，只会回答 = 退化成普通对话应用 |
| 有了 Agent 就不需要好的提示词 | ❌ | 任务描述、工具说明、约束仍是质量关键 |
| 工具执行是在模型内部完成的 | ❌ | 模型只输出调用请求，执行在外部运行时 |
| Function Calling 会给模型补充知识 | ❌ | 提供的是**能力**，不是知识（知识靠 RAG/微调） |
| MCP 是一个强大的工具 | ❌ | MCP 是**协议/标准** |
| 有了 MCP 就不需要 Function Calling | ❌ | 不同层次，通常共存 |
| Skill 就是写得很长的一条提示词 | ❌ | 含工具集合与验收标准，可复用、可编排 |
| 自检闭环就是让 Assistant 多看几遍 | ❌ | 需要**标准 + 检查 + 反馈修正 + 重试上限** |
| 自检闭环能保证结果百分百正确 | ❌ | 只能提升稳定性，标准是可能出错的 |
| 桌面 Agent 与云端 Agent 是两种技术路线 | ❌ | 同一套范式，**部署形态与可达资源**不同 |
| Agent 接入知识库后，模型就永久学会了知识 | ❌ | 检索是**外挂**，文档更新即刻生效；写进参数是微调 |
| CoT 属于 Agent 的「行动」环节 | ❌ | CoT/ToT 都属于**思考**环节，且不含工具执行 |

### 6.3 判断题速记

| 表述 | 对/错 |
|---|---|
| 感知、思考、行动构成 Agent 的闭环 | ✅ |
| ReAct 是推理与行动交替、带真实反馈的循环 | ✅ |
| 任务是单轮问答时不应引入 Agent | ✅ |
| Agent 拥有本地/外部操作权限，需权限最小化 | ✅ |
| Multi-Agent 一定比单 Agent 更快更省 | ❌（通信轮次使时延成本上升） |
| 自检闭环可以不设上限，让它改到对为止 | ❌（必须设重试上限） |
