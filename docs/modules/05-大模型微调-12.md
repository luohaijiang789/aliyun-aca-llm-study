## 三、【专章 ⭐⭐】微调适合什么（官方五项）

> **官方原文（背下来）：**
> **「掌握微调适合什么：稳定行为、格式、风格、分类能力，或支持轻量模型部署。」**
>
> 这五项是本模块**唯一**被官方点名的适用场景。考场上凡是超出这五项的「微调能干什么」，基本都是干扰项。

```
            微调适合什么？（官方五项，逐个背）
    ┌─────────┬─────────┬─────────┬─────────────┬──────────────┐
    │ ①稳定行为 │ ②格式   │ ③风格    │ ④分类能力     │ ⑤轻量模型部署  │
    │ 行为不漂移 │ 结构不变 │ 语气一致  │ 归到既定类别   │ 专项能力下放    │
    └─────────┴─────────┴─────────┴─────────────┴──────────────┘
         └────────────── 共同本质：改的是「怎么说」，不是「知道什么」─────────────┘
```

### 3.1 ① 稳定行为 ⭐

**是什么**：让模型在某个任务上的**整体行为长期稳定下来**——同样的输入类型，输出反应一致，不随问法、不随上下文漂移。

| 维度 | 说明 |
|---|---|
| 典型表现 | 一律按既定步骤应答；该拒答的边界稳定不摇摆；对同一类询问给出同质的处理动作 |
| 与其他四项的关系 | **「稳定行为」是总纲，格式 / 风格 / 分类是它的三种具体表现**——官方把它们并列列出，说明既可以考总纲也可以考分支 |
| 为什么提示词做不到 | 提示词是**每次输入的外部要求**，长尾问法下会偶发失效；微调是把行为**写进权重**，成为模型本身的习惯 |

> **一句话：提示词是"每次提醒"，微调是"养成习惯"。**

### 3.2 ② 格式

**是什么**：要求模型**每次都按同一个结构输出**，并且这个要求长期不变。

| 维度 | 说明 |
|---|---|
| 典型表现 | 永远输出符合约定结构的 JSON；病历按「主诉 - 现病史 - 诊断 - 处置」四段输出；工单必须含「问题类型 / 紧急度 / 责任部门」三个字段 |
| 为什么选微调 | 提示词能约束格式，但在**长尾输入**下会偶发跑偏；微调把格式内化，稳定性质变 |
| 判断信号词 | 「字段固定」「必须能被程序解析」「下游系统要自动读取」 |

> ⚠️ **前置条件**：题干如果说「已在提示词中写明格式并附示例，反复优化后**仍**跑偏」→ 标准答案就是**微调**。
> 题干如果说「刚提出格式要求，还没试过」→ 正确答案是**先优化提示词**。

### 3.3 ③ 风格

**是什么**：让输出的**语气、话术、文风**长期统一。

| 维度 | 说明 |
|---|---|
| 典型表现 | 客服永远用温和话术且不评价竞品；法务文书的严谨措辞；公文风 / 内容平台风二选一 |
| 为什么选微调 | 风格是「怎么说」的典型形态，属于行为范畴，与知识无关 |
| 判断信号词 | 「品牌调性」「话术规范」「语气」「人设」「统一口吻」 |

### 3.4 ④ 分类能力 🆕（本轮补齐，重点看）

**是什么**：让模型**稳定地把输入归入既定的类别集合**——类别是预先定义好、数量有限、边界明确的。

| 维度 | 说明 |
|---|---|
| 典型场景 | **意图分类**（用户这句话是咨询 / 投诉 / 售后 / 闲聊）、**工单分类**（归属哪个部门与紧急程度）、**情感分类**（正面 / 中性 / 负面）、**标签打标**（内容属于哪几个既定标签） |
| 为什么分类特别适合微调 | ① 类别**既定**，不需要外部知识；② 输出空间很小，行为极易被稳定和规范化；③ 一旦训好，模型能**直接输出类别标签**，不必在提示词里塞一长串类别说明和示例 |
| 相对提示词的三个优势 | **更稳定**（边界case不再摇摆）、**更快**（提示词不用每次都携带大量示例）、**更省 Token**（少传一长串说明，调用成本也更低） |
| 前置条件 | 必须**先试提示词**：用提示词写清类别定义 + 少量示例，若准确率仍不稳定，再考虑微调 |
| 类别会变怎么办 | 类别体系频繁增减 → **先别微调**，退回提示词（把类别列表放进输入） |

> 🔑 **考场信号词**：「自动归类」「打标签」「路由到不同部门」「判定属于哪一类」「分类准确率不稳定」→ 选**微调（分类能力）**。
> ⚠️ 但如果题干强调「类别每个月都在变」「要依据最新的分类规则文档」→ 那是**知识 / 规则更新**问题，转向 **RAG**。

### 3.5 ⑤ 支持轻量模型部署 🆕（本轮补齐，重点看）

**是什么**：把一个专项能力从大模型**迁移到参数量更小的模型**上，让**小模型**在这个专项任务上也能有接近的表现，从而**降低推理成本与延迟**。

```
   大模型（通用能力强、推理成本高）
            │  用它在专项任务上的高质量输出作为样本
            ▼
   小模型（轻量、成本低、延迟小）  ←── 微调，把专项能力迁移过来
            │
            ▼
   部署到资源受限 / 高并发 / 成本敏感的场景
```

| 维度 | 说明 |
|---|---|
| **为什么值得做** | 大模型「杀鸡用牛刀」：一个只做意图分类的场景，用通用大模型既贵又慢；小模型在该专项上经过微调后，性价比显著更好 |
| **降的是什么** | **推理成本**与**响应延迟**（小模型每次推理更省更快），也便于部署在资源受限的环境 |
| **代价 / 边界** | 小模型的**通用能力有限**——它只在被微调的那个专项上表现好，专项之外的能力弱于大模型 |
| **与 RAG 的配合** | 若轻量模型同时还**需要准确回答最新资料**，它自己的知识不够，仍要给它**接知识库（RAG）**。**轻量部署解决的是"跑得动、跑得起"，不解决"知道最新的事"** |
| **判断信号词** | 「推理成本太高」「响应太慢」「想用小模型」「高并发下成本扛不住」「部署到资源受限环境」 |

> 🔑 **考场信号词**：「希望用一个**更小的模型**完成这个固定任务，降低推理成本与延迟」→ 选**微调（支持轻量模型部署）**。
> ⚠️ 陷阱：若选项写成「用小模型替代大模型去做**开放式问答 / 全领域知识问答**」→ 错，轻量模型扛不住通用任务。

### 3.6 ❌ 微调不适合什么（"不是万能按钮"的四种典型）

| 不该用微调的场景 | 原因（对应官方口诀） | 正确解法 |
|---|---|---|
| **缺私域知识**（公司制度、产品手册、政策） | 知识会改，一改就要重训；且融进权重后**无法溯源** | **RAG**（查知识用 RAG） |
| **要最新 / 时效信息**（新法规、今日价格） | 训练完即冻结，追不上变化 | **RAG** |
| **要实时数据或要执行业务动作**（查汇率库存、下单退款） | 模型本身没有实时数据源、也没有执行能力 | **工具 / 工具调用**（做动作靠工具） |
| **只是指令没说清楚、回答泛泛** | 零成本手段还没试过 | **优化提示词**（先做第一步） |

> **口诀：查知识用 RAG，做动作靠工具，稳行为才考虑微调。**（详见第五章）

### 3.7 一个对照记忆法

```
   ┌──────────────────────────────────────────┐
   │  同一份「答案内容」，两种改法：              │
   │                                          │
   │  改「答什么」  →  RAG（换喂进去的资料）      │
   │  改「怎么答」  →  微调（换模型的行为习惯）    │
   └──────────────────────────────────────────┘
```

> **一句话主线：微调改的是「怎么说」，不是「知道什么」。**
> **RAG 换资料，微调换习惯。**

## 四、【专章 ⭐⭐】微调五步流程（官方原文版）

> **官方原文（务必逐字背）：**
> **「理解微调的基本流程：定义目标、准备样本、选择基模、控制数据质量、评估效果。」**

```
   ① 定义目标 ──► ② 准备样本 ──► ③ 选择基模 ──► ④ 控制数据质量 ──► ⑤ 评估效果
        │                                                                │
        └────────────────── 效果不达标则回到 ① 或 ② 迭代 ───────────────┘
```

> 🔴 **本轮重要修正（🔧）**：本库旧版写的是**六步**（数据准备→选基座→配超参→训练→评测→部署），**与官方不一致，已作废**。
> 请以官方**五步**为准。注意官方五步里**没有**单独的「配置超参数」「训练执行」「上线部署」——因为官方明示**不考模型训练细节**。
> ⛔ 顺序记忆口诀：**目、样、基、质、评。**

### ① 定义目标

| 项目 | 内容 |
|---|---|
| **做什么** | 明确「要把模型的**什么行为**稳定下来」，以及**什么叫做好了**（验收标准 / 评测口径） |
| **关键决策** | 目标是**行为问题**还是**知识问题**？目标是否**单一、明确、可定义**（如固定格式 / 统一风格 / 分对类别）？提示词这条路是否已经试过？ |
| **常见坑** | ❌ 目标写成「让模型更聪明 / 懂我们的业务」——那是**知识问题**，该走 RAG；<br>❌ 只有模糊期望、没有可衡量的验收标准，导致第 ⑤ 步无法判成败；<br>❌ 还没试过提示词就直接立项微调（跳过官方手段序列的前几步） |

### ② 准备样本

| 项目 | 内容 |
|---|---|
| **做什么** | 收集 / 整理成「**输入 → 期望输出**」的成对样本，让样本**代表目标行为**，并覆盖真实场景中的各类情况 |
| **关键决策** | 期望输出长什么样，样本就必须长什么样（要 JSON 就全给 JSON，要温和语气就全是温和语气）；覆盖面与获取成本怎么权衡 |
| **常见坑** | ❌ 样本里混着旧格式 / 不同语气的样例 → 模型学不到**稳定**行为；<br>❌ 直接把原始聊天记录 / 日志丢进去，不做整理；<br>❌ 只挑容易的样本，遇到真实长尾就崩 |

### ③ 选择基模

| 项目 | 内容 |
|---|---|
| **做什么** | 挑一个**预训练好的模型**作为起点（微调不是从零训练） |
| **关键决策** | 基座的**通用能力是否已达标**（基座是天花板，微调只能在天花板下做改善）；是否贴合领域；**若为轻量部署，是否需要选择更小的模型** |
| **常见坑** | ❌ 基座本身不具备该能力，指望微调「从不会变会」——那是补知识，不是微调；<br>❌ 误以为「选择基模＝从头训练一个模型」；<br>❌ 规模选择与实际部署诉求不匹配（嘴上说要降本低延迟，却选了更大的模型） |

### ④ 控制数据质量

| 项目 | 内容 |
|---|---|
| **做什么** | **清洗**（去重、剔除错误与矛盾样本、统一格式）、**规范标注口径**、划分训练集与**独立的评测集** |
| **关键决策** | **质量 > 数量**：一致性与正确性优先于堆量；评测集必须**先划出来**，且不参与训练 |
| **常见坑** | ❌ 标注标准不一致（同一类问题两种写法）→ 正好毁掉微调的意义——学不到稳定行为；<br>❌ 噪声数据直接把行为「教歪」（垃圾进，垃圾出）；<br>❌ 用训练集自评 → 分数虚高 |

> ⭐ **注意官方把「控制数据质量」单独列为一步**，而不是并进「准备样本」。这说明**数据质量是一个独立且关键的环节**，很可能在选项中作为独立正确项出现。

### ⑤ 评估效果

| 项目 | 内容 |
|---|---|
| **做什么** | 在**未参与训练**的评测集上，对照第 ① 步的目标验收；与**基座模型对比**看是否真的更好；检查通用能力是否退化 |
| **关键决策** | 评测指标要与第 ① 步的目标口径一致（格式合规率、分类准确率、风格一致性……）；是否需要人工评审 |
| **常见坑** | ❌ 只看训练过程的指标下降，不看真实业务表现；<br>❌ 用训练过的数据自评（等于让学生考做过的卷子）；<br>❌ 上线后不持续监控，效果衰减发现不了 |

### 流程题的常见挖坑方式（记住这四条即可）

| 坑 | 正解 |
|---|---|
| 把「评估效果」放到「准备样本」之前 | 错，评估是第 ⑤ 步、最后一步 |
| 说「用全部数据训练，再用同一批数据评估」 | 错，评估必须用**未参与训练**的数据 |
| 说「先考虑微调，提示词以后再说」 | 错，官方手段序列里**优化输入排在微调之前** |
| 把「选择基模」说成「从零训练一个模型」 | 错，微调的前提是**已经有**预训练模型 |

## 五、【专章 ⭐⭐】官方选型口诀（本模块最高频考法）

> **官方原文（逐字背，一字不差）：**
> # 「查知识用 RAG，做动作靠工具，稳行为才考虑微调。」

```
                        业务需求来了
                             │
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
   模型「不知道」        要「做动作」          只是「说不好」
   缺知识 / 要最新      执行业务动作          行为不够稳定
        │                    │                    │
        ▼                    ▼                    ▼
      RAG                工具 / 工具调用     先优化提示词
  （可更新、可追溯）   （实时数据、确定性计算、 （仍不达标）
                          业务动作）              │
                                                 ▼
                                              微调 ✅
```

### 5.1 逐句拆解

#### 第一句：**「查知识用 RAG」**

| 要点 | 说明 |
|---|---|
| 适用场景 | 模型**不知道**答案需要的信息：企业资料、产品手册、内部制度、政策条款、最新事件 |
| 为什么不是微调 | 知识一旦微调进权重，**会过时**（变了要重训）+ **不可追溯**（说不出来自哪份文档） |
| RAG 的两个制胜点 | **可更新**：改文档即刻生效；**可追溯**：答案能附出处 |
| 高频陷阱 | 题干出现「资料」「手册」「制度」「文档」「政策」「报价单」「上周刚更新」→ **一律优先 RAG** |

#### 第二句：**「做动作靠工具」**

| 要点 | 说明 |
|---|---|
| 适用场景 | 需要**实时数据**（今天天气 / 汇率 / 库存）、**确定性计算**（算金额、算日期）、**执行业务动作**（下单、退款、建工单、发邮件） |
| 为什么不是微调 | 微调改的是模型的说话方式，**既拿不到实时数据，也没能力执行动作**；知识也不可能实时更新 |
| 复杂多步时 | 多个工具需要**编排与规划** → 交给 **Agent**（官方手段序列的下一站） |
| 高频陷阱 | 题干出现「实时」「今天」「查询余额」「自动生成工单」「调用外部系统」→ **工具 / 工具调用**（多步则 Agent） |

#### 第三句：**「稳行为才考虑微调」**

| 要点 | 说明 |
|---|---|
| 适用场景 | 官方五项：**稳定行为、格式、风格、分类能力、支持轻量模型部署** |
| 前置条件（易漏） | **先做低成本尝试**——优化提示词；少样本示例能解决的就别微调 |
| 「才」字的分量 | 一个"才"字说明微调是**后置选项**：排在优化输入、接入知识库、调用工具之后 |
| 高频陷阱 | 题干出现「效果不好，**立刻**启动微调」「回答不好就微调」→ 基本都是**错项** |

### 5.2 口诀驱动的快速判断题（6 题热身）

| # | 场景 | ✅ 正解 | ❌ 经典错选 | 一句理由 |
|:---:|---|---|---|---|
| 1 | 客服问「咱们**上周刚改**的退货政策是什么」 | **RAG** | 微调 | 知识会变 + 要可追溯 → **查知识用 RAG** |
| 2 | 要查**今天的外汇汇率**并写入报价单 | **工具调用** | 微调 / RAG | 实时外部数据 → **做动作靠工具** |
| 3 | 客服回答内容对，但**语气时冷时热**不符合品牌调性 | **微调**（风格） | RAG | 风格 = 行为问题 → **稳行为才考虑微调** |
| 4 | 要求**每次输出同一结构的 JSON**，提示词反复优化后仍跑偏 | **微调**（格式） | RAG / 换模型 | 格式稳定性 → 把格式内化进权重 |
| 5 | 想把用户来单**自动归到 8 个既定工单类别** | **微调**（分类能力） | RAG | 既定类别，无需外部知识 |
| 6 | 工会制度文档**每月更新**，答案要随文档同步 | **RAG** | 微调 | 高频更新 → 每月重训不现实 |

> 📌 **做题口诀**：先看题干有没有「最新 / 变了 / 出处」（→RAG），再看有没有「实时 / 查询系统 / 执行动作」（→工具），剩下的「格式 / 风格 / 语气 / 分类 / 想用小模型」，且提示词已试过仍不行（→微调）。

## 六、【决策章】何时用微调 vs 何时不用

> 本模块 6 题里**至少 3 题是场景判断题**。这一章的价值 = 本模块的生命线。

### 6.1 决策对照表（必背）

| 维度 | **优化提示词** | **RAG** | **工具调用** | **微调** |
|---|---|---|---|---|
| **一句话** | 把话说清楚 | **补知识**（改「喂什么」） | **做事**（拿数据 / 执行动作） | **改行为**（改「怎么说」） |
| **解决什么** | 指令不清、缺示例 | 缺私域知识、缺最新信息、幻觉 | 实时数据、确定性计算、业务动作 | 稳定行为、格式、风格、分类能力、轻量部署 |
| **是否改模型权重** | ❌ 不改 | ❌ 不改，只改输入上下文 | ❌ 不改 | ✅ **改**，更新模型参数 |
| **更新方式** | 改提示词即刻生效 | **改文档即刻生效** | 接口侧更新 | 必须**重新训练** |
| **可追溯性** | — | ✅ 可附出处、可引用原文 | ✅ 结果来自系统 | ❌ 融进权重，**无法指出来源** |
| **前置条件** | 无（永远第一步） | 有资料文档即可 | 有可用接口 | 高质量样本 + 明确目标 |
| **典型失败表现** | 回答泛泛、抓不住重点 | 召不回 / 答错 | 接口失败 / 参数错 | 行为没学会 / 过拟合 / 遗忘 |

### 6.2 判定三连问（做题时默念，直接对应官方口诀）

```
第1问：是「查知识」吗？（模型不知道 / 要最新 / 要可追溯）
        └── 是 ─────────────────────────► RAG ✅
        └── 否 ↓

第2问：是「做动作」吗？（实时数据 / 确定性计算 / 业务动作）
        └── 是 ─────────────────────────► 工具 / 工具调用 ✅
             （多步编排 → Agent）
        └── 否 ↓

第3问：是「稳行为」吗？（格式 / 风格 / 分类 / 轻量部署 / 整体稳定）
        └── 还没试过优化提示词 ─────────► 先优化提示词 ✅
        └── 提示词反复优化后仍不达标 ───► 微调 ✅
```

> **「查知识」「做动作」「稳行为」三个词就是官方口诀的三个关键词，也是本模块全部场景题的答案池。**

### 6.3 场景判断题（10 题，逐题练手感）

| # | 场景 | ✅ 正解 | ❌ 经典错选 | 一句理由 |
|:---:|---|---|---|---|
| 1 | 要求模型问诊回复必须像**资深医生写病历**（术语、句式、结构） | **微调**（风格 / 领域表达） | RAG | 表达方式 = 行为问题 |
| 2 | 用户问「公司**内部报销流程**是什么」 | **RAG** | 微调 | 私域知识缺失 → 查知识用 RAG |
| 3 | 要回答 **2026 年新发布**的行业法规 | **RAG** | 微调 | 时效知识，训练完即冻结 |
| 4 | 要读 Excel → 汇总 → 发邮件 → 建待办 | **Agent** | 微调 | 多步 + 多工具编排 |
| 5 | 回答**泛泛而谈、抓不住重点** | **先优化提示词** | 微调 / RAG | 成本最低，永远第一步 |
| 6 | 只有 **5 条**样本想让模型学会新格式 | **提示词加少样本示例** | 微调 | 样本量太少，微调不成立 |
| 7 | 既要**最新产品条款**（已接 RAG），又要**统一客服话术** | **RAG + 微调组合** | 二选一 | 补知识 + 定行为，不互斥 |
| 8 | 医疗问答要求**每条结论必须标注出处文档** | **RAG** | 微调 | 强溯源需求，微调做不到 |
| 9 | 想把**意图分类**能力迁到一个**小模型**上，降低高并发下的推理成本与延迟 | **微调**（分类能力 + 轻量模型部署） | RAG | 专项能力下放，官方场景第 ④⑤ 项 |
| 10 | **售后退款**需要真的调用业务系统完成退款操作 | **工具调用**（多步则 Agent） | 微调 / RAG | 业务动作 → 做动作靠工具 |

### 6.4 最高频的三个陷阱句式

> **陷阱一：「把公司资料 / 制度微调进模型」**
> → 看到「资料」「制度」「手册」「政策」「文档」这类**名词性知识**，一律优先 **RAG**。理由：可更新、可追溯、改完即生效。

> **陷阱二：「回答不够好，那就微调一下」**
> → 缺了前提。正确表述：**先优化提示词**，再判断是不是「稳行为」问题，最后才考虑微调。「一上来就微调」这个顺序本身就是错的。

> **陷阱三：「用了 RAG 就不需要微调 / 微调了就不需要 RAG」**
> → 两者**不互斥**：**RAG 负责「答什么」，微调负责「怎么答」**，典型组合是「RAG 补知识 + 微调定风格」。

### 6.5 组合使用的正确姿势

```
        ┌──────────── RAG：负责「答什么」────────────┐
        │  知识库检索 → 得到最新、可追溯的资料片段      │
        └───────────────────┬──────────────────────┘
                            ▼
        ┌──────────── 微调：负责「怎么答」────────────┐
        │  用固定话术 + 固定 JSON schema 输出答案       │
        └───────────────────┬──────────────────────┘
                            ▼
                    （可选）Agent 负责「串起来」
```

> **记忆句：RAG 提供「料」，微调提供「味」，Agent 提供「流程」，工具负责「动手」。**

## 七、微调的局限（"不是万能按钮"的具体表现）

| 局限 | 说明 | 导致的后果 |
|---|---|---|
| **知识会过时** | 训练结束那一刻，知识就被「冻结」在权重里 | 新政策、新价格、新事件一律不知道；要跟上只能**重新训练** |
| **不可追溯** | 知识融进参数，无法指出答案来自哪份文档哪一条 | 医疗、金融、法务等**强溯源**场景难以合规 → 只能用 RAG |
| **迭代不灵活** | 每次调整都要重新经历「准备样本 → 控制质量 → 评估」的完整循环 | 不像 RAG 那样「改完文档即生效」，跟不上高频变化 |
| **灾难性遗忘** | 过度训练可能损害模型原有的通用能力 | 「专科变强了，常识变差了」 |
| **高度依赖样本质量** | 口径不一致、充满噪声的样本会把行为教歪 | **质量 > 数量**；教材印错了，习惯就养歪了 |
| **不解决时效与实时** | 模型本身没有外部数据源，也没有执行能力 | 实时数据 / 业务动作 → **工具调用** |
| **不降低成本敏感度** | 相对「改几句话」「改几篇文档」的其他手段，微调投入明显更重 | 所以排在官方手段序列的**后位**，不该作为首选 |

> **口诀：微调三宗罪 —— 会过时、查不到、改不动。**
> 与之相对：**RAG 三优势 —— 可更新、可追溯、改完即生效。**

### 8.1 全参数微调 vs PEFT（了解即可）

| | **全参数微调** | **PEFT（高效参数微调）** |
|---|---|---|
| 做法 | 更新模型**全部**参数 | **冻结**基座大部分参数，只训练**少量**参数 |
| 开销 | 高 | 低得多 |
| 存储 | 每个任务一份完整模型副本 | 只存一份很小的增量权重，基座可复用 |
| 效果 | 理论上拟合上限更高 | 多数业务场景**接近**全参数微调，性价比高 |
| 备考 | ⚠️ 了解即可 | ⚠️ 了解即可 |

> **一句话：全参数微调是「重写整本教材」，PEFT 是「只贴几页修订页」。**

### 8.2 LoRA / QLoRA（了解即可）

- **LoRA**：**冻结**基座模型原始权重**不动**，在旁路引入一对低秩小矩阵学习「增量」，训练时只更新这些少量参数。
  - ⚠️ 常考错项澄清（仅供与技术人员沟通，不考）：「LoRA 会修改基座原权重」是**错的**，恰恰相反它被冻结。
- **QLoRA**：LoRA **+ 量化（Quantization）**，把被冻结的基座用更低精度表示，进一步降低资源占用。

> ⛔ **以下一律不考**：低秩的秩取值、学习率、训练轮数、批大小、显存占用数值、训练时长、训练费用、训练框架与代码。

## 九、易错辨析表

### 9.1 手段辨析：到底该用哪个

| 场景 | 常见错误答案 | ✅ 正解 | 理由 |
|---|---|---|---|
| 输出 JSON 时而是对象时而是数组 | RAG / 换模型 | **提示词强约束 → 微调** | 格式稳定性（官方场景②） |
| 要模型一直用统一客服话术 | RAG | **微调** | 固定行文风格（官方场景③） |
| 工单要自动归到既定类别且长期不变 | RAG | **微调** | 分类能力（官方场景④） |
| 想把专项能力迁到小模型降本提速 | RAG | **微调** | 支持轻量模型部署（官方场景⑤） |
| 公司新出的产品报价单问答 | 微调 | **RAG** | 查知识用 RAG |
| 模型不知道内部报销流程 | 微调 | **RAG** | 私域知识缺失 |
| 要查实时天气 / 汇率 / 库存 | 微调 | **工具调用** | 做动作靠工具 |
| 要真的完成退款 / 下单 | 微调 / RAG | **工具调用**（多步则 Agent） | 模型不能执行动作 |
| 读表格 → 计算 → 发邮件 | 微调 | **Agent** | 多步编排 |
| 回答泛泛、抓不住重点 | 微调 | **优化提示词**（先试） | 永远第一步 |
| 要求答案必须标出处 | 微调 | **RAG** | 微调不可追溯 |
| 只有几条样例想统一格式 | 微调 | **提示词少样本示例** | 样本量不足以微调 |
| 既要最新条款又要统一话术 | 只选一个 | **RAG + 微调** | 两者可组合 |

### 9.2 概念辨析

| 对比项 | A | B | 判据 |
|---|---|---|---|
| **RAG vs 微调** | 改**输入**（喂资料），不改权重 | 改**权重**（改行为） | 「有没有改模型参数」是唯一硬判据 |
| **工具调用 vs 微调** | 拿到实时数据 / 执行动作，不改模型 | 改模型行为，拿不到实时数据 | 「要做事」还是「要稳行为」 |
| **提示词 vs 微调** | 改输入，成本低、立即生效、灵活性高 | 改模型，行为更稳定、但重且难改 | **先提示词，后微调** |
| **质量 vs 数量**（样本） | 一致性、正确性优先 | 堆量而噪声大反而更差 | 质量 > 数量 |
| **训练集 vs 评测集** | 用来学习 | **必须独立**，用来验证 | 用训练集自评 = 分数虚高 |
| **「查知识」vs「稳行为」** | 不知道 → RAG | 说不好 → 微调 | 官方口诀给出的第一分水岭 |
| **「不知道」vs「不会做」** | 缺知识 → RAG | 缺动作能力 → 工具 / Agent | 官方口诀第二分水岭 |

### 9.3 判断题速记（对 / 错）

| 说法 | 判断 |
|---|---|
| 微调适合稳定行为、格式、风格、分类能力或支持轻量模型部署 | ✅ **官方原句** |
| 官方微调基本流程为：定义目标 → 准备样本 → 选择基模 → 控制数据质量 → 评估效果 | ✅ **官方原句** |
| 查知识用 RAG，做动作靠工具，稳行为才考虑微调 | ✅ **官方原句** |
| 微调是在预训练模型基础上用特定数据继续训练 | ✅ |
| 微调会修改模型权重，RAG 不会 | ✅ |
| 微调最适合用来给模型补充最新的事实知识 | ❌ **查知识用 RAG** |
| 要让模型查询实时库存并完成下单，应该做微调 | ❌ **做动作靠工具** |
| 微调可以提升模型的分类能力，且比在提示词中塞大量示例更省 Token | ✅ |
| 支持轻量模型部署是指把专项能力迁移到小模型以降低成本与延迟 | ✅ |
| 轻量小模型经过微调后可以胜任开放式的全领域知识问答 | ❌ 通用能力有限，跨专项就弱 |
| 微调后知识更新只需换掉知识库文档即可 | ❌ 那是 RAG；微调必须**重新训练** |
| 微调进权重的知识可以溯源到具体文档 | ❌ **不可追溯** |
| 有了 RAG 就不需要微调 / 微调了就不需要 RAG | ❌ 可组合：RAG 补知识 + 微调定行为 |
| 微调应排在优化提示词、接入知识库、调用工具之后考虑 | ✅ 官方手段序列如此 |
| 微调可以完全解决幻觉 | ❌ 只能**降低**，不能消除 |
| 评测应当使用未参与训练的独立数据，并与基座对比 | ✅ |
| 样本质量比数量更重要，标注口径必须一致 | ✅ |
| 微调数据里有少量噪声没关系，多堆一些就行 | ❌ 质量 > 数量，噪声会把行为教歪 |
| 微调可能导致模型原有通用能力下降（灾难性遗忘） | ✅ |
| 少样本（few-shot）示例能解决时，优先于微调 | ✅ |
| 考试会考查 LoRA 的原理、超参数设置与训练成本 | ❌ **官方明示不考模型训练细节** |
