### 课时标题的三个字眼 = 三个考点

官方课时叫**「通过微调改善大模型在垂直领域的表现」**，标题本身就是送分题：

| 标题字眼 | 暗示的考点 | 反过来说（陷阱） |
|---|---|---|
| **改善** | 模型**已经会做**这件事，只是做得不够好 → 改的是**行为** | ❌ 微调不是「用不会变会」，那是补知识 |
| **表现** | 表现 = 怎么说、怎么答、什么格式 → **格式 / 风格 / 表达习惯** | ❌ 不是「知道什么」 |
| **垂直领域** | 面向特定行业/场景的习惯与术语 → **领域表达** | ❌ 不等于「把领域资料灌进去」 |

> **一句话主线：微调改的是「怎么说」，不是「知道什么」。**

### 为什么权重会下调

> V2.4 的核心导向是：**考核重心从「理论概念」转向「实际落地」**。
> 落地时 **RAG 与 Agent 的使用频次远高于微调**，M3（+2）、M4（+6）上调，微调相应让位。
> 但微调没有被删除 —— 说明**它仍是选型决策树里不可替代的一支**，考核重点放在**「选得对不对」**上。

### ⛔ 本模块的备考红线

1. **不背超参数**：学习率、训练轮数、LoRA 的秩、batch size …… **一律不考具体数值**，只考「有这个东西、它的作用方向」。
2. **不背成本数字**：不考训练要多少钱、多少卡、多少小时，只考**成本高低排序**（提示词 < RAG < 微调）。
3. **不背平台操作**：不考控制台菜单、按钮、产品开通流程。
4. **背的是判断力**：给一个业务场景，你能不能一句话说清「该不该微调」。

## 3. 逐考点详解

### M5-K01 · 微调的定义与本质 🟢`[A]`

**定义（背下来）：**
> **微调（Fine-tuning）是在已经预训练好的基座模型之上，用特定领域或特定任务的数据集继续训练，从而更新模型部分（或全部）参数，使模型在该领域/任务上的表现得到改善。**

三个关键词拆解：

| 关键词 | 含义 | 为什么重要 |
|---|---|---|
| **预训练基座** | 起点是一个已经「读过海量文本、具备通用语言能力」的模型 | 微调不是从零训练，是**站在巨人肩膀上做定向改造** |
| **特定领域/任务数据** | 用你自己的、有代表性的数据 | 数据决定微调的上限 |
| **继续训练 / 更新参数** | **模型权重真的被改了** | 这是与 RAG 最本质的区别：**RAG 不改权重，微调改权重** |

> **最硬的一条判据（必背）：**
> **「有没有改动模型权重？」**
> - 改了 → 微调
> - 没改，只是往输入里塞资料 → **RAG / 提示词**

**为什么"改权重"这件事代价很大：**
- 知识一旦进权重，就**混在参数里**，你无法指着某个答案说「它来自第几份文档第几条」→ **不可追溯**
- 知识一变，就得**重训** → **更新成本高**
- 训练数据之外的新事件，模型**照样不知道** → **不能解决时效问题**

### M5-K02 · 微调解决什么：固定格式 / 行文风格 / 领域表达 ⭐ 🟢`[A]`

> **本模块第一考点。一句话：微调解决的是「表达方式」问题，不是「知识储量」问题。**

#### ✅ 微调真正擅长的三类问题

| 类型 | 说明 | 典型例子 |
|---|---|---|
| **固定输出格式** | 每次都按同一个结构输出，稳定性远超提示词约束 | 永远输出符合约定 schema 的 JSON；病历必须按「主诉-现病史-诊断-处置」四段输出；工单必须含「问题类型/紧急度/责任部门」三个字段 |
| **固定行文风格 / 语气** | 品牌调性、客服话术、专业口吻 | 客服永远用「亲，……哦」的温和语气且不说竞品坏话；法务文书的严谨措辞；小红书风 / 公文风二选一 |
| **领域表达习惯** | 行业黑话、术语、缩写、特定推理套路 | 医疗报告里的「鉴别诊断」写法；代码评审意见的惯用句式；金融研报的行文套路 |

#### ❌ 微调不擅长（= 千万别选微调）的三类问题

| 不该用微调的场景 | 原因 | 正确解法 |
|---|---|---|
| **缺私域知识**（公司制度、产品手册） | 知识会改 → 一改就要重训 | **RAG** |
| **缺最新/时效信息**（新法规、今日价格） | 训练完就固定，追不上变化 | **RAG / 插件** |
| **回答质量差是因为指令没说清** | 先做零成本尝试 | **优化提示词** |

#### 一个对照记忆法

```
   ┌──────────────────────────────────────────┐
   │  同一份「答案内容」，两种改法：              │
   │                                          │
   │  改「答什么」  →  RAG（换喂进去的资料）      │
   │  改「怎么答」  →  微调（换模型的行为习惯）    │
   └──────────────────────────────────────────┘
```

> **口诀：RAG 换资料，微调换习惯。**

### M5-K03 · 决策点：✅ 该用微调 / ❌ 不该用微调 ⭐⭐ 🟢`[A]`

> **本模块最高频考法：给一个业务场景，问你「该不该微调 / 该用什么」。**
> 做完第 4 章的判断题，这题就稳了。

#### ✅ 该用微调的判据（满足其一即可，越多越确定）

1. **要求输出格式高度稳定**，提示词约束仍会偶发跑偏（如 JSON 时而是对象时而是数组）
2. **要求行文风格/语气长期一致**（品牌调性、客服人设、专业口吻）
3. **垂直领域的表达习惯与术语**与通用语料差异大
4. 已经**先试过提示词优化**，仍达不到稳定要求（**这是前置条件，不是可选项**）
5. 任务是**单一、明确、可定义**的（分类、抽取、格式化改写、风格化生成）
6. 有足够的**高质量领域标注数据**

#### ❌ 不该用微调的判据（命中任一条就转向）

| 命中情况 | 转向 |
|---|---|
| 问题本质是**缺知识**（模型不知道） | → **RAG** |
| 知识**会频繁更新 / 需可追溯** | → **RAG** |
| 需要**实时数据**（天气、股价、库存） | → **插件 / API** |
| 任务**复杂多步**、需规划与调度工具 | → **Agent** |
| 只是**指令没说清楚**、回答泛泛 | → **优化提示词**（先试） |
| **没有高质量标注数据** | → 先攒数据，或退回提示词/RAG |
| 只有很少的样例（几条到几十条） | → 提示词里的**少样本示例**更合适 |

#### 判定口诀（三连问）

```
第1问：模型「不知道」还是「说不好」？
        不知道 ──────────────► RAG（知识问题）
        说不好 ↓
第2问：改改提示词能不能解决？
        能 ─────────────────► 优化提示词（零成本优先）
        不能 ↓
第3问：要固定的是「格式 / 风格 / 领域表达」吗？
        是 ─────────────────► 微调 ✅
        否（是多步编排）────► Agent
```

> **「不知道」和「说不好」是两条完全不同的路。分不清这两条路，本模块必丢分。**

### M5-K04 · 全参数微调 vs PEFT 高效参数微调 🟡`[B]`

> ⛔ **只考概念与取舍方向，不考任何具体数值。**

| | **全参数微调（Full Fine-tuning）** | **PEFT（Parameter-Efficient Fine-Tuning，高效参数微调）** |
|---|---|---|
| 做法 | 更新模型**全部**参数 | **冻结**基座模型绝大部分参数，只训练**少量**新增/指定的参数 |
| 训练开销 | 高（显存、算力、时间） | **低得多** |
| 存储 | 每个任务要存一份**完整模型副本** | 只需存一份**很小的增量权重**，基座可复用 |
| 效果上限 | 理论上更高，数据充足时拟合能力更强 | 多数业务场景下**接近**全参数微调，性价比高 |
| 风险 | 更容易**灾难性遗忘**、过拟合 | 基座能力被冻结，遗忘风险相对小 |
| 适用 | 数据量大、算力充足、与基座差异极大的任务 | **绝大多数业务场景的默认选择** |

**PEFT 的常见实现思路（了解即可，不考细节）：**
- **LoRA 系**（见 K05）
- **Adapter**：在模型层间插入小模块，只训练这些模块
- **Prefix / Prompt Tuning**：只训练一段可学习的「虚拟提示」向量

> **一句话：全参数微调是「重写整本教材」，PEFT 是「只贴几页修订页」。**

### M5-K05 · LoRA / QLoRA ⭐ 🟡`[B]`

> **本模块最容易出「概念辨析单选」的考点。**

#### LoRA（Low-Rank Adaptation，低秩适配）

| 要点 | 说明 |
|---|---|
| 核心做法 | **冻结**预训练模型的原始权重**不动**，在旁路上引入一对**低秩**的小矩阵来学习「增量」，训练时**只更新这些小矩阵** |
| 参数量 | 被训练的参数量相对基座**小得多**（⛔ 具体倍数与数值不考、不背） |
| 显存为何友好 | 需要保存和更新的**梯度、优化器状态**大幅减少 → 显存占用显著下降 |
| 推理时 | 训练完可把低秩增量**合并回**原权重，不额外增加推理延迟 |
| 部署优势 | 一份基座 + 多个不同任务的 LoRA 小权重，**按需切换**，存储成本极低 |

#### QLoRA

> **QLoRA = 量化（Quantization）+ LoRA。**

- 在 LoRA 的基础上，**再把被冻结的基座模型做量化**（用更低精度的数值表示权重）
- 目的：进一步**降低显存占用**，让有限的资源也能跑起来
- 代价与权衡：量化会带来**极小的精度损失**，换的是**大幅的资源节省**

#### 三个必记辨析点

| 说法 | 判断 | 理由 |
|---|---|---|
| LoRA 会修改基座模型的原始权重 | ❌ | **恰恰相反**：原始权重被**冻结**，LoRA 只学增量 |
| LoRA 训练的参数量远少于全参数微调 | ✅ | 这是「低秩」与「高效」的含义所在 |
| QLoRA 是在 LoRA 基础上叠加量化以进一步降低显存 | ✅ | 记忆：Q = Quantization |
| LoRA / QLoRA 能让模型学到训练数据里没有的新知识 | ❌ | 任何微调都只是**调整已有能力的行为表现**，不能凭空注入时效知识 |
| 微调后需要为每个任务保存一份完整模型副本 | ❌（对 LoRA 而言） | LoRA 只需存很小的一份增量权重，基座可复用 |

> **口诀：LoRA 冻结大的、只训小的；QLoRA 再把它变小一点。**

### M5-K06 · 数据要求：质量 > 数量 🟡`[B]`

> **「质量 > 数量」这五个字是本考点的全部灵魂。**

| 要求 | 说明 |
|---|---|
| **质量 > 数量** | 少量**高质量、高一致性**的数据，效果远好于大量噪声数据。**垃圾进，垃圾出** |
| **清洗** | 去重、剔除错误/矛盾样本、去掉无关与脏数据、统一格式 |
| **标注** | 需要**人工或可靠的标注**，且**标注标准必须一致**（同一类问题不能两种写法） |
| **代表性 / 覆盖面** | 数据要覆盖真实场景中的各类情况，否则模型只在训练集分布内表现好 |
| **与目的一致** | 想固定格式，数据就必须**全部**是目标格式；想固定风格，数据就必须是该风格的示范 |
| **划分数据集** | 留出**未参与训练的评测集**用于验证，防止「背答案」（过拟合） |
| **格式规范** | 通常整理成「输入 → 期望输出」（指令-回答）的成对样本 |

**常见错误认知（易成为干扰项）：**

| 错误说法 | 正解 |
|---|---|
| 数据越多越好，先堆量再说 | ❌ **一致性**与**正确性**优先，噪声数据会直接损害效果 |
| 原始数据直接喂进去就行，不用清洗标注 | ❌ 未清洗未标注的数据会让模型学到错误行为 |
| 微调不需要多少数据，随便找几条就行 | ❌ 数据量过少时，用提示词中的**少样本示例**更合适 |
| 数据只要多，标注标准不一致也没关系 | ❌ 标注矛盾会让模型**学不到稳定行为**，恰好毁掉微调的意义 |

> **一句话：微调是在教模型「养成习惯」，教材印错了，习惯就养歪了。**

### M5-K07 · 微调流程六步 🟡`[B]`

```
① 数据准备 → ② 选择基座模型 → ③ 配置训练参数 → ④ 训练 → ⑤ 评测 → ⑥ 部署
```

| 步骤 | 做什么 | 关键决策 | 常见坑 |
|:---:|---|---|---|
| **① 数据准备** | 收集、清洗、标注、划分训练/评测集 | 质量与一致性优先；格式必须是「期望输出」的样子 | 数据里混着旧格式样本 → 模型学不到稳定格式 |
| **② 选择基座模型** | 挑一个能力满足要求的预训练模型 | 通用能力是否够、是否适配领域、规模与成本权衡 | 基座本身能力不足，微调也救不回来 |
| **③ 配置训练参数** | 设定训练相关配置（学习率、轮数、批大小等） | ⛔ **具体数值不考**，只考「有这一步」 | 轮数过多 → 过拟合（只会背训练题） |
| **④ 训练** | 在数据集上更新模型参数 | 全参数还是 PEFT（LoRA/QLoRA） | 资源不足 → 优先考虑高效微调 |
| **⑤ 评测** | 在**未参与训练**的评测集上对比基座，必要时做人工评审 | 是否真的比基座好？有没有退化？ | 用训练集自评 → 分数虚高，上线翻车 |
| **⑥ 部署** | 上线服务，持续监控与迭代 | 灰度、回滚方案、与 RAG/Agent 的组合 | 一次上线不监控，效果衰减无法发现 |

> **顺序记忆口诀：数、基、参、训、评、上。**
> **最常考的一个细节：评测必须用「没训练过的数据」，否则等于让学生考做过的卷子。**

---

### M5-K08 · 微调的局限性 🟡`[B]`

| 局限 | 说明 | 导致的后果 |
|---|---|---|
| **知识会过时** | 训练结束的那一刻，知识就被「冻结」在权重里 | 新政策、新价格、新事件一律不知道；要更新就得**重训** |
| **不可追溯** | 知识融进参数，无法指出答案来自哪份文档哪一条 | 金融、医疗、法务等**强溯源**场景难以合规 |
| **成本相对高** | 需要数据、算力、时间与工程投入 | 明显**高于**提示词优化与 RAG，不该作为首选手段 |
| **灾难性遗忘** | 过度训练可能损害模型原有的通用能力 | 「专科变强了，常识变差了」 |
| **过拟合风险** | 数据少或训练轮数过多 | 只会背训练样本，遇到新问法就崩 |
| **不解决时效与实时** | 无外部数据源 | 实时类需求必须靠 **RAG / 插件** |
| **迭代不灵活** | 每次调整都要重新训练与评测 | 不如改知识库（RAG）那样「改完即生效」 |

> **口诀：微调三宗罪 —— 会过时、查不到、改不动。**
> 与之相对：**RAG 三优势 —— 可更新、可追溯、改完即生效。**

---

### M5-K09 · 与 RAG 的边界及组合使用 ⭐⭐ 🟢`[A]`

> **本模块与 M3 的接缝处，也是单选题最爱埋陷阱的地方。详见第 4 章专章。**

一句话边界：

> **RAG 决定「喂什么资料」（知识，可更新、可追溯）；微调决定「怎么说话」（行为，稳定但难改）。**

**两者不互斥，典型组合：**
> **RAG 补知识 + 微调定风格**
> 例：先用 RAG 检索到最新的产品条款，再由微调过的模型用**固定的客服话术与 JSON 格式**输出答案。

> ⚠️ 判断题必背：**「用了 RAG 就不需要微调」是错的**；**「微调了就不需要 RAG」也是错的**。

### M5-K10 · 在决策树中的位置 🟡`[B]`

```
                    大模型回答不够好
                            │
                   先做零成本尝试
                            ▼
              ① 优化提示词（成本最低，永远第一步）
                            │ 还不够
                            ▼
        第1分叉：问题出在「知识」还是「行为」？
                            │
        ┌───────────────────┴───────────────────┐
        ▼                                       ▼
   【缺知识 / 要实时】                    【缺格式 / 缺风格 / 领域表达】
        │                                       │
        ▼                                       ▼
   ② RAG / 插件                            ③ 微调  ★本模块
   （可更新、可追溯）                    （改行为，成本高、难更新）
        │
        ▼
   任务复杂、多步、需编排
        │
        ▼
   ④ Agent
```

**成本递增顺序（背下来，选择题常考排序）：**

| 顺序 | 手段 | 成本 |
|:---:|---|:---:|
| 1 | **优化提示词** | 💰 最低（改几句话） |
| 2 | **RAG / 插件** | 💰💰（建知识库 / 接接口） |
| 3 | **微调** | 💰💰💰（数据 + 算力 + 评测 + 迭代） |
| 4 | **Agent** | 💰💰💰（编排 + 工具 + 闭环） |

> **核心结论：微调在决策树里排在提示词和 RAG 之后，不是第一选择。**
> 考场上凡是看到「一上来就微调」「回答不好就微调」的选项，基本都是错的。

### M5-K11 · 微调后的评测与部署 🔴`[C]`

> ⚠️ 本考点为通用知识推断，**待与官方 V2.4 大纲 PDF 核对**。

- 必须用**未参与训练**的评测集评估，避免过拟合造成的虚高分数
- 应与**基座模型做对比**（ ablation 思路）：微调后是否**真的**更好，还是只是「看起来更顺」
- 关注**能力是否退化**：通用任务上是否出现灾难性遗忘
- 上线建议**灰度 + 可回滚**，并保留基座版本做对照
- 业务指标（准确率、格式合规率、人工满意度）比「损失下降」更有意义

### M5-K12 · 微调与提示词工程的先后边界 🟡`[B]`

| | 提示词工程 | 微调 |
|---|---|---|
| 改什么 | 改**输入**（不改模型） | 改**权重**（改模型） |
| 成本 | 极低，随时可改 | 高，需数据/算力/评测 |
| 生效速度 | 改完即生效 | 训练完才生效 |
| 稳定性 | 长尾场景可能偶发跑偏 | 行为**内化**，一致性更好 |
| 适合 | 探索期、需求未定型、样例很少 | 需求已定型、格式/风格要长期稳定 |

**先后关系（必背）：**
> **提示词是「先试」，微调是「提示词搞不定之后」的选项。**
> 少样本示例（few-shot）能解决的，先别微调；需求还在变的，先别微调。

## 4. 【专章】何时用微调 vs 何时用 RAG ⭐⭐（本模块生命线）

> 这一章的分值密度最高。本模块 6 题里，**至少 3 题是场景判断题**。

### 4.1 决策对照表（必背）

| 维度 | **RAG** | **微调** |
|---|---|---|
| **一句话** | **补知识**（改「喂什么」） | **改行为**（改「怎么说」） |
| **是否改动模型权重** | ❌ **不改**，只改输入上下文 | ✅ **改**，更新模型参数 |
| **解决的核心问题** | 缺私域知识、缺最新信息、幻觉 | 输出格式不稳、行文风格不统一、领域表达不地道 |
| **知识更新方式** | 改知识库 / 换文档，**改完即生效** | 必须**重新训练** |
| **可追溯性** | ✅ 可附出处、可引用原文 | ❌ 融进权重，**无法指出来源** |
| **时效性** | ✅ 可随时喂最新资料 | ❌ 训练截止即冻结 |
| **成本** | 💰💰 中 | 💰💰💰 高 |
| **前置条件** | 有资料文档即可 | 需**高质量标注数据** + 算力 |
| **失败时的表现** | 召不回 / 答错（可归因到检索侧或生成侧） | 行为没学会 / 过拟合 / 遗忘 |
| **典型场景** | 制度问答、产品手册问答、最新政策问答 | 固定 JSON 输出、客服语气统一、医疗/法律文书风格 |

### 4.2 判定三连问（做题时默念）

```
第1问：模型是「不知道」还是「说不好」？
        ┌── 不知道（缺知识/要最新）──► RAG ✅
        └── 说不好（格式/风格/表达）─┐
                                     │
第2问：改提示词能解决吗？             │
        ┌── 能 ──────────────────► 优化提示词 ✅（别急着微调）
        └── 不能 ─────────────────┐
                                  │
第3问：要的「稳定性」是长期且固定的吗？│
        ┌── 是 ──────────────────► 微调 ✅
        └── 否（是复杂多步编排）──► Agent
```

### 4.3 典型场景判断题（逐题练手感）

| # | 场景 | ✅ 正解 | ❌ 经典错选 | 一句理由 |
|:---:|---|---|---|---|
| 1 | 用户问「咱们最新的退货政策是什么」，政策**上周刚改过** | **RAG** | 微调 | 知识会变 + 要可追溯 → 检索 |
| 2 | 客服机器人回答内容对，但**语气时冷时热**，不符合品牌调性 | **微调** | RAG | 风格/语气 = 行为问题 |
| 3 | 要求模型**每次都输出同一 schema 的 JSON**，提示词约束后仍偶发跑偏 | **微调** | RAG / 换模型 | 格式稳定性 → 把格式内化进权重 |
| 4 | 模型**不知道**公司内部报销流程 | **RAG** | 微调 | 私域知识缺失 |
| 5 | 想让输出像**资深医生写病历**（术语、句式、结构） | **微调** | RAG | 领域表达习惯 |
| 6 | 需要回答**2026 年新发布的行业法规** | **RAG** | 微调 | 时效知识 |
| 7 | 要查**今天的外汇汇率** | **插件 / API** | 微调 / RAG | 实时外部数据 |
| 8 | 要读 Excel → 汇总 → 发邮件 → 建待办 | **Agent** | 微调 | 多步 + 多工具编排 |
| 9 | 回答**泛泛而谈、抓不住重点** | **先优化提示词** | 微调 / RAG | 成本最低，永远第一步 |
| 10 | 只有 **5 条**样本想让模型学会新格式 | **提示词加少样本示例** | 微调 | 数据量太少，微调不成立 |
| 11 | 既要**最新产品条款**（RAG 已接入），又要**统一客服话术** | **RAG + 微调组合** | 二选一 | 补知识 + 定风格，不互斥 |
| 12 | 医疗问答要求**每条结论必须标注出处文档** | **RAG** | 微调 | 强溯源需求，微调做不到 |
| 13 | 一份固定的合同条款抽取任务，格式要求**长期不变** | **微调** | RAG | 单一明确任务 + 稳定格式 |
| 14 | 知识库文档**每月更新**，要求答案随文档同步 | **RAG** | 微调 | 高频更新 → 重训不现实 |

### 4.4 最高频的两个陷阱句式

> **陷阱一：「把公司资料/制度微调进模型」**
> → 看到「资料」「制度」「手册」「政策」「文档」这种**名词性知识**，一律优先 **RAG**。
> 理由：可更新、可追溯、改完即生效；微调进去则**过时且不可追溯**。

> **陷阱二：「回答不够好，那就微调一下」**
> → 缺了前提。正确表述是：**先优化提示词，再判断是否属于格式/风格问题，最后才考虑微调。**
> 「先微调」这个顺序本身就是错的。

### 4.5 组合使用的正确姿势

```
        ┌──────────── RAG：负责「答什么」────────────┐
        │  知识库检索 → 得到最新、可追溯的资料片段      │
        └───────────────────┬──────────────────────┘
                            ▼
        ┌──────────── 微调：负责「怎么答」────────────┐
        │  用固定话术 + 固定 JSON schema 输出答案       │
        └───────────────────┬──────────────────────┘
                            ▼
                    （可选）Agent 负责「串起来」
```

> **记忆句：RAG 提供「料」，微调提供「味」，Agent 提供「流程」。**

## 5. 微调流程（六步）

> 完整表格见 M5-K07。这里给出**流程全景图**与**每步最容易考的一句话**。

```
①数据准备 ──► ②选基座 ──► ③配参数 ──► ④训练 ──► ⑤评测 ──► ⑥部署
     │                                              ▲
     └──────────── 效果不达标则回到 ① 或 ③ ─────────┘
```

| 步骤 | 最该记住的一句话 |
|:---:|---|
| ① 数据准备 | **质量 > 数量**；数据长什么样，模型就学成什么样 |
| ② 选基座 | 基座能力是天花板，微调只能在天花板下做改善 |
| ③ 配参数 | ⛔ **不考具体数值**；轮数过多会过拟合 |
| ④ 训练 | 资源受限时优先 **PEFT / LoRA / QLoRA** |
| ⑤ 评测 | **必须用没训练过的数据**评测，并与基座对比 |
| ⑥ 部署 | 灰度上线 + 持续监控，保留回滚能力 |

**流程题的常见挖坑方式：**
- 把「评测」放在「训练」之前 → 错
- 说「用全部数据训练、再用同一批数据评测」 → 错（等于考做过的卷子）
- 说「先微调再考虑提示词」 → 错（顺序反了）
- 把「选基座」说成「从零训练一个模型」 → 错（微调的前提是**已有**预训练模型）

## 6. 易错辨析表

### 6.1 手段辨析：到底该用哪个

| 场景 | 常见错误答案 | ✅ 正解 | 理由 |
|---|---|---|---|
| 输出 JSON 时而是对象时而是数组 | RAG / 换模型 | **提示词强约束 → 微调** | 格式稳定性问题 |
| 要模型一直用统一客服话术 | RAG | **微调** | 固定行文风格 |
| 公司新出的产品报价单问答 | 微调 | **RAG** | 知识类优先检索 |
| 模型不知道内部报销流程 | 微调 | **RAG** | 私域知识缺失 |
| 要查实时天气 / 汇率 / 库存 | 微调 | **插件 / API** | 实时外部能力 |
| 读表格 → 计算 → 发邮件 | 微调 | **Agent** | 多步编排 |
| 回答泛泛、抓不住重点 | 微调 | **优化提示词**（先试） | 成本最低，永远第一步 |
| 要求答案必须标出处 | 微调 | **RAG** | 微调不可追溯 |
| 只有几条样例想统一格式 | 微调 | **提示词少样本示例** | 数据量不足以微调 |
| 既要最新条款又要统一话术 | 只选一个 | **RAG + 微调** | 两者可组合 |

### 6.2 概念辨析

| 对比项 | A | B | 判据 |
|---|---|---|---|
| **RAG vs 微调** | 改**输入**（喂资料），不改权重 | 改**权重**（改行为） | 「有没有改模型参数」是唯一硬判据 |
| **全参数微调 vs PEFT** | 更新全部参数，成本高 | 只训少量参数，高效 | 业务场景默认选 PEFT 更经济 |
| **LoRA vs QLoRA** | 低秩适配，只训少量参数 | LoRA **+ 量化**，进一步省显存 | Q = Quantization |
| **LoRA vs 全参数微调** | 原权重**冻结**，只学增量 | 原权重全部更新 | 「LoRA 会改原权重」是经典错项 |
| **微调 vs 提示词** | 改模型，成本高、稳定 | 改输入，成本低、灵活 | 先提示词，后微调 |
| **质量 vs 数量**（数据） | 一致性、正确性优先 | 堆量而噪声大反而更差 | 质量 > 数量 |
| **训练集 vs 评测集** | 用来学习 | **必须独立**，用来验证 | 用训练集自评 = 分数虚高 |
| **知识问题 vs 行为问题** | 不知道 → RAG | 说不好 → 微调 | 本模块第一分水岭 |

### 6.3 判断题速记（对 / 错）

| 说法 | 判断 |
|---|---|
| 微调是在预训练模型基础上用特定数据继续训练 | ✅ |
| 微调可以改变模型的输出格式与行文风格 | ✅ |
| 微调最适合用来给模型补充最新的事实知识 | ❌ **用 RAG** |
| 微调后知识更新只需重新训练一次即可，成本很低 | ❌ 重训代价高，这是微调的主要局限 |
| 微调进权重的知识可以溯源到具体文档 | ❌ **不可追溯** |
| RAG 会修改模型权重 | ❌ RAG **不改**权重 |
| 微调会修改模型权重 | ✅ |
| 有了 RAG 就不需要微调 | ❌ 可组合：RAG 补知识 + 微调定风格 |
| 微调可以完全解决幻觉 | ❌ 只能**降低**，不能消除 |
| 微调应排在提示词优化之后考虑 | ✅ 成本顺序：提示词 < RAG < 微调 |
| LoRA 冻结原模型权重，只训练少量低秩参数 | ✅ |
| QLoRA 是在 LoRA 基础上再叠加量化以降低显存 | ✅ |
| 微调数据越多越好，质量差一点没关系 | ❌ **质量 > 数量** |
| 微调评测可以用训练集，结果同样可信 | ❌ 必须用**独立评测集** |
| 训练轮数越多效果越好 | ❌ 过多会**过拟合** |
| 微调可能导致模型原有通用能力下降（灾难性遗忘） | ✅ |
| 少样本（few-shot）示例能解决时，优先于微调 | ✅ |
