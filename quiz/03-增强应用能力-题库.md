# 一、单选题（8 题）

### Q001 [M3-K01] [A] 单选

某公司的**产品手册、报销制度和售后服务条款只存在于公司内部文档系统中，从未对外公开**，且每隔几个月就会修订一次。公司希望 AI 助手能准确回答员工关于这些内部制度的提问。按照官方的选型原则，**最合适且可持续维护**的做法是？

- A. 把这些企业资料接入知识库，采用 RAG（检索增强生成）方式，让模型回答前先检索相关资料再作答
- B. 调用工具让模型实时联网搜索这些资料，再把搜到的内容整理成回答
- C. 用这些文档对大模型做微调，把制度内容写进模型参数里
- D. 把所有制度全文写进提示词，每次提问时一并传给模型

**答案**：A
**考点**：M3-K01 RAG 的定位 —— 官方原话「**查企业资料用 RAG**」
**解析**：
- A ✅ **直接命中官方判据**。这些资料有三个典型特征：① **企业资料 / 私域知识**（不公开，模型训练数据里没有）；② **会更新**（每隔几个月修订）；③ **要可追溯**（员工要能核实依据）。RAG 恰好同时满足：文档一改即刻生效、答案可附出处、不必把知识写进模型权重。官方原话就是「**查企业资料用 RAG**」。
- B ❌ 工具调用解决的是「**实时数据 / 确定性计算 / 业务动作**」，而本题是**查企业资料**。更关键的是这些资料**从未对外公开**，联网搜索根本搜不到；即便搜到，来源也不可控、不可追溯。判据用错了对象。
- C ❌ 这是本模块**最高频的陷阱项**。微调改变的是模型的**行为、格式与风格**，不适合注入会频繁更新的事实性知识：① 制度一改就要重新训练，维护成本高；② 知识进了模型权重后**不可追溯、无法引用出处**；③ 训练完就又开始过时。知识类问题一律优先走检索。
- D ❌ 把全文塞进提示词有三个硬伤：**上下文窗口有上限**（手册往往很长）、每次请求都要重复传（成本高、延迟大）、资料更新要同步改提示词（不可持续）。RAG 的价值正是「只喂**相关**片段」。
**我错了吗**：☐

### Q002 [M3-K03] [A] 单选

企业希望大模型能够回答「我们上海仓库现在还剩多少台 XX 型号设备」，而该库存数据**每分钟都在变化**。最合适的增强手段是？

- A. 通过工具调用实时查询库存系统，再把返回的结果交给模型组织成回答
- B. 把库存清单导出成文档，接入 RAG 知识库供检索
- C. 用历史库存数据对模型做微调，让它学会报库存数量
- D. 在提示词中加入更多示例，说明库存类问题该怎么回答

**答案**：A
**考点**：M3-K03 工具的定位 —— 官方判据一「需要**实时数据**时用工具」
**解析**：
- A ✅ **命中官方判据一「实时数据」**。模型拿不到系统的当前状态，必须借助工具去调用库存接口拿当下的数据，再让模型把结构化结果组织成自然语言。判定口诀：**「给再多资料也答不出来（因为要的是『现在的值』）→ 用工具」**。
- B ❌ RAG 的知识库是**静态**的、由人工更新写入的。每分钟变化的数据一旦入库就已经是上一分钟的快照，永远答不准当前值。这是「把实时问题当成知识问题」的典型错误。
- C ❌ 微调注入的是训练时的**历史快照**，训练完数据就过时了；且数值类知识进权重后**不可追溯、不可校验**，是典型的错误用法。
- D ❌ 提示词只能规范「怎么答」，无法提供「答什么」。模型依然不知道当前库存是多少。
**我错了吗**：☐

### Q003 [M3-K03] [A] 单选

某财务场景要求 AI 根据一批订单明细（数量 × 单价，含折扣、税率与多币种换算）**计算应付总额**，业务方要求结果「一分不差」。实践中发现模型直接计算时经常算错。按照官方选型原则，最合适的做法是？

- A. 把历史订单明细接入知识库，用 RAG 检索相似订单后让模型参照估算
- B. 调用工具完成确定性计算（如计算 / 结算类接口），再让模型基于计算结果组织回答
- C. 用大量计算题数据对模型做微调，提升模型的算术能力
- D. 调高 `temperature`，让模型多算几遍后取最一致的结果

**答案**：B
**考点**：M3-K03 工具的定位 —— 官方判据二「**确定性计算**时用工具」
**解析**：
- B ✅ **命中官方判据二「确定性计算」**。大模型本质上是**按概率生成**下一个词，天然不适合要求「一分不差」的算术与换算。这类「算得准」的需求属于**工具**的活：把计算交给确定性的计算 / 结算接口，模型只负责把结果说清楚。这是官方明确列出的三条用工具判据之一。
- A ❌ 用 RAG 检索相似订单再「参照估算」，本质上还是让模型猜，且检索到的是别的订单的数据，与本次计算无关。**RAG 补的是知识，不提供计算能力**。
- C ❌ 微调稳的是**行为、格式、风格**，不是算术精度。用微调提升计算能力既成本高又不可靠，且无法保证每次结果一致。
- D ❌ 调高 `temperature` 会让输出更发散，**只会让计算结果更不稳定**；同时调参也**无法让模型获得训练数据之外的新知识**或新能力。
**我错了吗**：☐

### Q004 [M3-K03] [A] 单选

某企业希望 AI 助手完成这样的请求：**「帮我把这份周报发给项目组全体成员，并在项目管理系统中把该任务标记为已完成」**。关于实现该需求的说法，正确的是？

- A. 把周报模板和任务清单接入知识库，用 RAG 检索后模型即可自动完成发送与状态标记
- B. 通过工具调用对接邮件系统与项目管理系统，由模型判断用户意图后调用相应工具完成动作
- C. 用历史操作记录对模型做微调，让它学会发邮件和修改任务状态
- D. 在提示词中把发送和标记的步骤写得极其详细，模型就能自行执行这些步骤

**答案**：B
**考点**：M3-K03 工具的定位 —— 官方判据三「**业务动作**时用工具」
**解析**：
- B ✅ **命中官方判据三「业务动作」**。发邮件、改系统状态都是**动作**，不是**知识**。模型只能输出文字，不会真的去操作系统；必须通过工具调用把意图变成对邮件系统、项目管理系统的实际操作。官方口诀：**「做动作靠工具」**。
- A ❌ **RAG 只提供依据，不执行任何动作**。把模板接进知识库，模型最多能**写出**一封邮件的草稿，但发不出去、也改不了任务状态 —— 这正是 RAG 的能力边界。
- C ❌ 微调改变的是模型的**表达行为**，不能赋予它调用外部系统的能力。模型无论怎么训练，都只能通过输出文本来表达意图，必须有人（或系统）把意图转成真实操作。
- D ❌ 提示词写得再详细，也只是让模型把**步骤说得更清楚**，它依然没有执行能力。这是把「会说」误当成「会做」的典型错误。
**我错了吗**：☐

### Q005 [M3-K10] [A] 单选

关于 **MCP** 在大模型应用中的作用，下列说法正确的是？

- A. MCP 是一个可以替代知识库的检索引擎，负责把企业资料切分并写入向量库
- B. MCP 提供了一套标准化的连接方式，用于解决模型 / Agent 与外部数据源、工具对接时的碎片化集成问题
- C. MCP 是一种提升模型推理能力的微调方法，能让模型变得更聪明
- D. MCP 规定了模型必须使用某些指定的工具，例如只能调用官方提供的天气工具

**答案**：B
**考点**：M3-K10 MCP 的作用与定位（官方：「了解 MCP 的**作用**，**不要求掌握协议细节**」）
**解析**：
- A ❌ 切分、向量化、入库是 **RAG（知识库）** 的环节，与 MCP 无关。MCP 处在**连接层**，不负责资料的解析与索引。**补知识用 RAG，连接外部资源才谈 MCP**，两者不在同一层，也不互相替代。
- B ✅ **这就是官方要求掌握的全部内容**。没有统一标准时，N 个应用 × M 个工具需要 **N×M 个定制集成**；MCP 提供统一标准后，各方按同一套方式对接一次即可（N+M），从而解决对接的**碎片化**问题，让工具与数据源可被复用、易于扩展。
- C ❌ MCP 不是微调方法，不涉及更新模型权重；它**不提升模型本身的推理能力**，只解决「接得上、描述得清」的问题。用得好不好仍取决于模型能力与工具描述的质量。
- D ❌ MCP 是**开放的连接标准**，不限定具体用哪个工具；恰恰相反，它的价值在于让**各种**数据源与工具都能按同一标准被接入。

### Q006 [M3-K11] [B] 单选

某同学说：「我们给 Agent 接上了 MCP，所以它现在能查天气、能查库存了。」对这一说法，最恰当的评价是？

- A. 正确，MCP 本身就是一个能查天气和库存的工具
- B. 不正确，MCP 是标准化的连接协议，负责让外部数据源和工具「接得上、描述得清」；真正提供查天气、查库存能力的是被接入的**具体工具**
- C. 不正确，MCP 只能在模型内部使用，无法连接任何外部系统
- D. 无法判断，这取决于 MCP 使用哪种传输层协议与报文格式

**答案**：B
**考点**：M3-K11 MCP 与「工具」的层级关系（⛔ 只考定位，**不考协议细节**）
**解析**：
- A ❌ **这是关于 MCP 最经典的误解**。MCP 是 L3 的**连接标准**，工具才是 L1 的**能力本体**。类比：Type-C 是接口标准，U 盘和打印机才是设备 —— 你不会因为插上了 Type-C 就说「接口标准帮我打印了文件」。
- B ✅ 准确说清了层级：**MCP 管的是「怎么连」**（外部数据源与工具如何被发现、描述和对接），**工具管的才是「连上之后能干什么」**。Agent 之所以能查天气查库存，是因为通过 MCP 接进来了**天气工具和库存工具**。同时它与模型侧的 Function Calling 也不冲突：后者解决「模型怎么表达调用意图」，二者层次不同、通常共存。
- C ❌ 恰恰相反，MCP 的用途正是**连接外部**的数据源与工具；说它「只能在模型内部使用」完全说反了。
- D ❌ **这是本模块最需要注意的干扰项**。官方原文明确写着「了解 MCP 的**作用**，**不要求掌握协议细节**」，因此传输层协议、报文格式、握手流程等都**不在考试范围内**，更不可能成为判断依据。凡是选项里出现这类词，一律不是答案。
**我错了吗**：☐

### Q007 [M3-K04] [A] 单选

某企业把一批产品手册接入知识库后，用户关于**规格参数**的提问经常答不上来。排查发现：这些手册是**扫描版 PDF**，参数以**表格**形式呈现，入库后表格被拉平成一串没有结构的文字，「参数名—参数值」的对应关系丢失。该问题出在 RAG 的哪个环节，应如何改进？

- A. 检索环节 —— 应更换 embedding 模型以提升语义表征能力
- B. 解析环节 —— 应改进文件解析（扫描件做 OCR、表格按结构提取并保留行列关系）后再重新入库
- C. 切分环节 —— 应增大 chunk size，让每个片段包含更多内容
- D. 生成环节 —— 应优化提示词，要求模型只依据上下文作答

**答案**：B
**考点**：M3-K04 RAG 五环节①：**解析**（官方：「理解 RAG 的**解析**、切分、检索、重排序和评测会影响答案质量」）
**解析**：
- A ❌ 换 embedding 模型解决的是「语义表征不准、找得不对」，而本题的病根是**内容在入库前就已经丢失**（表格结构没了、扫描件没文字）。资料里根本没有可召回的内容，检索再强也无能为力。
- B ✅ **解析是 RAG 的第一道关口**：把 PDF / Word / Excel / 扫描件等原始资料提取成干净、可检索的文本，并保留标题层级、表格的行列关系与图片中的有效信息（扫描件需先做 OCR）。**解析丢内容 = 源头缺失，后面永远召不回** —— 这正是官方把「解析」列为五环节之首的原因。改进方向就是优化解析方式后再重新入库。
- C ❌ 增大 chunk size 解决的是「语义被切断」的问题，但本题的表格**结构**已经在解析阶段被破坏，块再大也是把一串无结构的文字装得更多，不会让「参数名—参数值」的对应关系自己回来。
- D ❌ 优化生成侧提示词能提升**忠实度**（不乱编），但模型面对的是丢失了结构的文本，再怎么约束也答不出没有的信息。归因时务必先看检索到了什么。
**我错了吗**：☐

### Q008 [M3-K06] [A] 单选

某 RAG 系统中，用户提问「离职手续怎么办」，而知识库文档里写的是「员工离司办理流程」。使用**关键词检索**时一个词都匹配不上、完全召不回，换成**向量检索**后却能正常召回。造成这一差异的主要原因是？

- A. 向量检索会先让大模型阅读全部文档，再凭记忆回答问题
- B. 向量检索把文本映射为向量并按语义相似度召回，能匹配字面不同但含义相近的表述
- C. 向量检索会自动把用户问题和文档都翻译成统一的规范术语后再做精确匹配
- D. 向量检索对文档做了全文逐字扫描，因此比关键词检索更全面

**答案**：B
**考点**：M3-K06 RAG 五环节③：**检索**（向量检索原理：embedding / 语义相似度 / ANN）
**解析**：
- A ❌ 让模型通读全部文档受**上下文窗口限制**、成本高且不可扩展，这不是向量检索的做法，也违背 RAG 的思路 —— RAG 恰恰是只喂**相关**片段。
- B ✅ 向量检索先用专门的 **embedding 模型**把文本变成向量，语义相近的文本在向量空间中距离更近，因此「离职手续 / 员工离司」这类**同义表述**可以被召回，突破了关键词检索「字面必须重合」的限制。
- C ❌ 向量检索**不做术语规范化翻译**，也不是精确匹配。恰恰相反，型号、订单号、专有名词这类需要精确匹配的场景，关键词检索往往比向量检索更稳（工程上因此常做**混合检索**）。
- D ❌ 向量检索依赖预先构建的索引做**近似查找**（ANN），**不会**逐字全文扫描；若真能通读全文也就不需要检索了。ANN 的价值正是「牺牲极小精度换取在海量向量上的检索速度」。
**我错了吗**：☐

# 二、多选题（3 题）

### Q009 [M3-K06] [A] 多选

关于 RAG 的**检索环节**（含向量检索与重排序），下列说法正确的有哪些？

- A. 向量检索把文本映射为向量后按语义相似度召回，能匹配字面不同但含义相近的表述
- B. 检索时用户的提问也需要用**同一个 embedding 模型**向量化，否则两者不在同一向量空间，比较无意义
- C. 关键词检索在处理型号、订单号等需要精确匹配的专有名词时往往更稳，因此常与向量检索组合成混合检索
- D. 引入重排序（rerank）可以把原本没有召回到的相关片段重新召回，从而提升召回率
- E. 调大 `temperature` 可以显著提升检索环节召回相关片段的比例

**答案**：ABC
**考点**：M3-K06 检索环节（向量检索）+ M3-K07 重排序
**解析**：
- A ✅ **向量检索的核心价值**。用 embedding 模型把文本变成向量，语义相近的文本在向量空间中距离更近，从而突破关键词检索「字面必须重合」的限制，对同义词、口语化表述更鲁棒。
- B ✅ 检索的本质是**在同一个向量空间里比距离**。文档用 A 模型向量化、提问用 B 模型向量化，得到的两组向量空间不一致，算出来的相似度没有意义。这是高频考点。
- C ✅ **两种检索各有短板**：向量检索长于语义、弱于精确；关键词检索长于精确（型号、订单号、专有名词）、弱于语义。因此工程上常采用「关键词 + 向量」多路召回后融合，即**混合检索**。
- D ❌ **本题最关键的陷阱**。rerank 只对**已经召回的候选集**重新打分排序，它提升的是**精确率**（把最相关的排到前面、避免被截断丢失），**不会扩大召回范围**。召回率不足（相关片段压根没进候选集）必须回到检索、切分、解析环节解决。
- E ❌ `temperature` 是**生成阶段**的采样参数，作用于输出随机性，对「能不能检索到相关片段」没有任何影响。这是典型的**检索侧 / 生成侧混淆陷阱**。
**我错了吗**：☐

### Q010 [M3-K09] [A] 多选

某 RAG 知识问答系统上线后答案质量不达标。关于系统的**评测与归因**，下列做法与判断正确的有哪些？

- A. 先检查召回的上下文里是否包含正确答案：包含却答错属于**生成侧**问题，不包含属于**检索侧**问题
- B. 归因顺序应「先检索侧、后生成侧」：检索侧没修好就先调生成参数，相当于对着错误资料优化措辞
- C. 建立评测集，对检索质量与答案忠实度**分别**打分，才能定位问题出在哪一环节
- D. 提高 `temperature` 让模型回答更丰富，可以同时解决检索侧与生成侧的问题
- E. 评测环节只需给最终答案打一个总分即可，无需区分环节

**答案**：ABC
**考点**：M3-K09 RAG 评测归因 + M3-K08 RAG 五环节⑤：评测
**解析**：
- A ✅ **归因口诀**：「**上下文里有却答错 → 生成侧；压根没有 → 检索侧**」。这是官方把「评测」列为影响答案质量的五个环节之一的用意所在 —— 先定位，再动手。
- B ✅ 检索侧没修好就去调生成参数，等于**垃圾进、垃圾出**：资料本身就是错的 / 没喂进去，再怎么优化措辞也答不对。正确顺序永远是**先检索、后生成**，且检索侧的优化成本相对更低。
- C ✅ 分环节打分是评测的核心方法：**检索质量**（相关片段有没有进候选集）、**上下文相关性**（噪声多不多）指向检索侧；**答案忠实度**（每句是否有上下文依据）、**答案相关性**（是否答非所问）指向生成侧。只打总分无法归因。
- D ❌ `temperature` 只是生成侧的随机性参数：调高会让输出更发散、**更容易编造**，对检索侧（能不能召回到相关资料）**完全没有作用**，更不可能「同时解决两侧」。
- E ❌ 只打总分就失去了评测的意义。**评测不是为了打分，是为了归因；归因不是为了甩锅，是为了对症下药** —— 官方单独把「评测」列为一个环节，正是要求能分环节定位问题。
**我错了吗**：☐

### Q011 [M3-K04] [A] 多选

官方指出，RAG 的**解析、切分、检索、重排序和评测**会影响答案质量。下列「问题现象 → 对应环节 → 改进方向」的匹配，正确的有哪些？

- A. 扫描版 PDF 与表格内容入库后丢失结构、相关参数怎么也召不回 → **解析环节** → 改进文件解析（扫描件做 OCR、表格按结构提取并保留行列关系）后重新入库
- B. 答案的前提与结论被切到两个片段，召回的内容总是不完整 → **切分环节** → 调整 chunk 大小，或增加相邻片段之间的 overlap
- C. 真正相关的段落排在候选集靠后位置，进入上下文前被截断丢弃 → **重排序环节** → 引入 rerank 对候选片段重新打分排序
- D. 评测环节的作用是在模型生成答案后打个总分，与解析、切分、检索等环节没有关联
- E. 检索召回率低，应通过用标注好的问答数据微调模型权重来提升

**答案**：ABC
**考点**：M3-K04 解析 / M3-K05 切分 / M3-K07 重排序 / M3-K08 评测（官方五环节整体）
**解析**：
- A ✅ **解析是五环节之首，也是最容易归因错误的一环**。解析丢内容属于**源头缺失** —— 后面检索再怎么优化也召不回。改进方式是优化文件解析（OCR、保留表格结构与标题层级）并重新入库。
- B ✅ 症状是**同一语义单元被切到两个 chunk**，导致任何单块都不完整，典型原因是 chunk size 过小 / 缺少 overlap。治本做法是让每一块自身可读：适当增大块大小，或在相邻块之间保留一段重叠文本防止跨块截断。
- C ✅ 粗召回求「全」、重排求「准」。引入 rerank 能把真正相关的片段提到靠前位置，避免它们因超出 top-n 或超出上下文窗口而被丢弃，同时过滤「只有几个词相似但其实无关」的噪声。
- D ❌ 说反了官方的用意。评测恰恰是要**与前面各环节关联起来**：分环节打分（检索质量 / 上下文相关性 / 答案忠实度 / 答案相关性）才能定位到底是哪一环出了问题。只打总分无法归因，也就无法对症下药。
- E ❌ **用标注数据更新模型权重是微调的做法，不属于 RAG 的环节**。RAG 的核心特征是**不改动模型权重** —— 这正是它知识可随时更新、答案可追溯的原因。召回率低应在检索链路上解决（改解析、调切分、查询改写、混合检索、元数据过滤、调 top-k、加 rerank 等）。二者可以组合使用，但流程上是两条独立的链路。
**我错了吗**：☐
