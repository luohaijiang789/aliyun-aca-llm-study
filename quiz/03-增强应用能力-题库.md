# 一、单选题（8 题）

### Q001 [M3-K01] [A] 单选

某公司上线了智能客服，用户问「咱们最新的退货政策是什么」时，机器人总是给出过时甚至编造的条款。公司这份退货政策**上周刚刚修订过**，且从未对外公开发布过。**成本最低且可持续维护**的解决方案是？

- A. 将最新退货政策文档接入知识库，让模型在回答前先检索相关条款再作答
- B. 把公司的历史客服对话记录整理成数据集，对大模型做领域微调
- C. 调大 `temperature` 参数，让模型的回答更有创造性
- D. 调大 `max_tokens` 参数，让模型能把条款写得更完整

**答案**：A
**考点**：M3-K01 RAG 的定义与价值定位（知识缺失 + 时效过期 + 幻觉 → RAG）
**解析**：
- A ✅ **典型 RAG 场景**。私域知识（未公开）+ 时效性强（上周修订）正是 RAG 的两大适用靶心：文档更新即刻生效，答案可附出处供用户核查，同时抑制模型「没依据就编」的幻觉。
- B ❌ 这是最经典的**陷阱项**。微调改变的是模型的**表达行为与风格**，不适合注入会频繁更新的事实性知识：① 政策一改就要重新训练，维护成本高；② 知识进了模型权重，答案**不可追溯、无法引用出处**；③ 一次改动后又会再次过时。知识类问题优先选检索。
- C ❌ `temperature` 控制**采样随机性**，调大会让输出更发散、更不稳定，只会让编造更严重，与补充知识毫无关系。
- D ❌ `max_tokens` 限制的是**输出长度上限**，只影响答案能写多长，不解决「模型不知道这件事」。
**我错了吗**：☐

### Q002 [M3-K04] [A] 单选

某 RAG 系统中，用户提问「离职手续怎么办」，而知识库文档里写的是「员工离司办理流程」。使用**关键词检索**时一个词都匹配不上、完全召不回，但换成**向量检索**后可以正常召回。造成这一差异的主要原因是？

- A. 向量检索会先让大模型阅读全部文档，再凭记忆回答问题
- B. 向量检索把文本映射为向量并按语义相似度召回，能匹配字面不同但含义相近的表述
- C. 向量检索会自动把用户问题和文档都翻译成统一的规范术语后再做精确匹配
- D. 向量检索对文档做了全文逐字扫描，因此比关键词检索更全面

**答案**：B
**考点**：M3-K04 向量检索原理（embedding / 语义相似度）⭐ V2.4 新增
**解析**：
- A ❌ 让模型通读全部文档受上下文窗口限制、成本高且不可扩展，这不是向量检索的做法，也不是 RAG 的思路（RAG 恰恰是只喂**相关**片段）。
- B ✅ 向量检索先用 embedding 模型把文本变成向量，语义相近的文本在向量空间中距离更近，因此「离职手续 / 员工离司」这类**同义表述**可以被召回，突破了关键词检索「字面必须重合」的限制。
- C ❌ 向量检索**不做术语规范化翻译**，也不是精确匹配。恰恰相反，专有名词、型号、订单号这类需要精确匹配的场景，关键词检索往往比向量检索更稳（工程上因此常做混合召回）。
- D ❌ 向量检索依赖预先构建的索引做近似查找，**不会**逐字全文扫描；若真能通读全文也就不需要检索了。
**我错了吗**：☐

### Q003 [M3-K04] [A] 单选

关于 RAG 检索环节中使用的 **ANN（近似最近邻）检索**，下列说法正确的是？

- A. ANN 是一种针对大模型的参数微调方法，用于提升模型的专业能力
- B. ANN 要求为每段文档指定唯一的编号，用户提问时按编号精确匹配
- C. ANN 的作用是先用大模型把文档压缩成摘要，再对摘要做关键词搜索
- D. ANN 通过对向量建立索引并进行近似查找，牺牲极小精度换取在海量向量上的检索速度

**答案**：D
**考点**：M3-K04 向量检索原理（ANN 近似最近邻）⭐ V2.4 新增
**解析**：
- A ❌ ANN 是**检索侧**（查找阶段）的技术，不涉及更新模型权重；更新模型权重属于**微调**（M5），两者完全不是一回事。
- B ❌ 按编号精确匹配是传统数据库 / 关键词倒排的思路，与向量的语义近似查找无关。
- C ❌ 「先用大模型压缩成摘要」既不是 ANN 的职责，也会引入额外的信息损失与成本；把文档变成向量的工作由专门的 **embedding 模型**完成，不是由生成模型完成。
- D ✅ 数据量一大，拿问题向量去和库里每一个向量逐一比对（暴力穷举）会非常慢。ANN 通过**建立索引 + 近似搜索**，在极小的精度损失下大幅提升检索速度，从而支撑在线实时问答。
**我错了吗**：☐

### Q004 [M3-K07] [A] 单选

某 RAG 客服系统的回答被判定为错误。工程师导出本次召回的上下文，发现**正确答案所在的段落排在第 2 位，并且已被完整放进模型的输入上下文里**，但模型最终给出的结论与该段落内容相矛盾。据此，最合理的归因与**优先**采取的措施是？

- A. 检索侧失败，应更换 embedding 模型以提升召回质量
- B. 知识库资料不足，应继续扩充更多文档
- C. 生成侧失败，应优先优化提示词（明确要求只依据上下文作答、无依据须回复「未找到」），并可加入答案自检环节
- D. 输出被截断了，应调大 `max_tokens` 让模型把依据写完

**答案**：C
**考点**：M3-K07 RAG 评测归因（检索侧 vs 生成侧）⭐ V2.4 新增
**解析**：
- A ❌ 归因判断错误。题干明确指出正确答案**已经出现在上下文里**，说明召回是成功的。此时换 embedding 模型属于「对着没坏的部件动刀」，成本高且不解决实际问题。归因口诀：**「上下文里有却答错 → 生成侧」**。
- B ❌ 资料已经足够（答案文档就在知识库里，否则不会被召回）。盲目加文档还可能引入噪声，进一步稀释关键信息。
- C ✅ 典型的**生成侧失败**（忠实度问题）：喂进去了但没有忠实使用。优先手段应是提示词层面的强约束 —— 限定只依据给定上下文、不得引入外部知识、找不到时须明确回答「未找到」，并可要求答案附引用出处 / 加入自检闭环便于核验。
- D ❌ 「输出被截断」通常表现为**答到一半没了**，而本题是答案**完整但与上下文矛盾**，两者症状不同；且调大长度限制不会提升忠实度。
**我错了吗**：☐

### Q005 [M3-K07] [A] 单选

对某 RAG 系统做评测时发现：一批问题的回答大量是「未找到相关资料」，但人工核对确认**这些问题的答案确实存在于知识库文档中**。按照正确的归因顺序，首先应检查并优化的是？

- A. 提高 `temperature`，让模型的回答更丰富多样
- B. 检查并优化检索环节：切片策略是否被切断、embedding 是否适配领域表述、是否需要混合召回、top-k 与元数据过滤是否合理
- C. 更换参数量更大的生成模型
- D. 收集这批问答数据，对大模型做一轮领域微调

**答案**：B
**考点**：M3-K07 RAG 评测归因（检索侧归因与对症手段）⭐ V2.4 新增
**解析**：
- A ❌ `temperature` 是生成侧参数，且提高随机性只会增加编造风险；本题症状是「答案压根没被召回」，与生成参数无关。
- B ✅ 症状「知识库里有、模型说没找到」是教科书级的**检索侧失败**（召回率不足）。对症排查应沿检索链路展开：① 切片是否把答案切断；② 领域黑话/缩写是否让 embedding 语义错位；③ 是否需要补一路关键词检索做混合召回；④ top-k 是否过小；⑤ 是否被不相关文档干扰而未做元数据过滤。
- C ❌ 换更大的生成模型成本高，且不解决「资料没喂进去」的问题 —— 再强的模型也答不出它没看到的内容。**归因顺序是先检索、后生成**。
- D ❌ 这是常见的**顺序错误**。微调属高成本手段，在 V2.4 的决策树中排在靠后位置；用它补知识还会导致不可追溯、易过时。知识缺失一律优先走检索。
**我错了吗**：☐

### Q006 [M3-K03] [B] 单选

某企业把技术手册接入 RAG 知识库后，用户反馈召回的片段经常「只有一半意思」——结论在一处、依据在另一处，答案看起来总像缺斤少两。工程师**最应该优先**调整的是？

- A. 减小 `temperature`，让模型回答更保守
- B. 增大 `max_tokens`，让模型可以输出更长的答案
- C. 适当调整切片策略：增大 chunk size 或增加相邻 chunk 之间的 overlap
- D. 提高 `top_p`，扩大候选词范围

**答案**：C
**考点**：M3-K03 文档解析与文本切片（chunk size / overlap）
**解析**：
- A ❌ `temperature` 控制生成随机性，与「片段语义被切断」无关，属于隔靴搔痒。
- B ❌ 增大输出长度只会让模型把不完整的依据写得更啰嗦，不会让缺失的内容凭空出现。
- C ✅ 症状是**同一语义单元被切到两个 chunk**，导致任何单块都不完整，这正是 chunk size 过小 / 缺少 overlap 的典型表现。治本的做法是让每一块自身可读：适当增大块大小，或在相邻块之间保留一段重叠文本（overlap）防止跨块截断。
- D ❌ `top_p` 与切片和召回毫无关系，纯生成侧参数。
**我错了吗**：☐

### Q007 [M3-K08] [B] 单选

企业希望大模型能够回答「我们上海仓库现在还剩多少台 XX 型号设备」，该库存数据**每分钟都在变化**。最合适的增强手段是？

- A. 通过插件 / 工具调用实时查询库存系统，再把结果交给模型组织回答
- B. 把库存清单导出成文档，接入 RAG 知识库供检索
- C. 用历史库存数据对模型做微调，让它学会报库存数量
- D. 在提示词中加入更多示例说明库存该怎么回答

**答案**：A
**考点**：M3-K08 插件机制与能力边界扩展
**解析**：
- A ✅ 这是**能力边界**问题：模型本身拿不到当前的系统状态。通过插件 / 工具去调用库存接口获取实时数据，再让模型把结构化结果组织成自然语言，是唯一正确的解法。判定口诀：**「给再多书也答不出来」→ 插件**。
- B ❌ RAG 的知识库是**静态**的、由人工更新写入的。每分钟变化的数据一旦入库就已经是上一分钟的快照，永远答不准当前的实时值。
- C ❌ 微调注入的是训练时的历史快照，微调完数据就过时了；且数值类知识进权重后不可追溯、不可校验，是典型的错误用法。
- D ❌ 提示词只能规范「怎么答」，无法提供「答什么」，模型依然不知道当前库存。
**我错了吗**：☐

### Q008 [M3-K10] [B] 单选

某团队需要在**夜间定时**对 5 万条历史工单批量生成摘要，且必须**拿到完整摘要文本后**才能做后续的字段抽取与统计。最合适的调用方式是？

- A. 流式生成，边生成边展示处理结果
- B. 流式生成，并把 `temperature` 调到最大以保证摘要多样性
- C. 批量生成，并把 `max_tokens` 调到极小以节省成本
- D. 批量（非流式）生成，等待全部完成后一次性获取完整结果

**答案**：D
**考点**：M3-K10 批量生成 vs 流式生成
**解析**：
- A ❌ 流式生成的核心价值是**降低等待感**（边生成边返回），服务于人在屏幕前等待的对话场景。本场景是无人值守的离线批处理，人不在等，流式没有收益。
- B ❌ 同理不适用流式；且摘要任务要求准确稳定，`temperature` 调大会损害一致性。
- C ❌ 调小 `max_tokens` 极易让摘要被**截断**，直接破坏后续的字段抽取，方向恰好相反。
- D ✅ 「让机器等的用批量」：离线批处理、必须拿到完整文本后才能做后处理，正是批量（一次性返回）的典型适用场景。

### Q009 [M3-K02] [A] 多选

下列属于 **RAG 标准流程环节**的有哪些？

- A. 对原始文档进行解析与文本切片
- B. 使用 embedding 模型将文本片段向量化并写入向量库
- C. 依据相似度从向量库中召回候选片段，并可再进行重排序
- D. 将召回片段与用户提问拼装成提示词后交给大模型生成回答
- E. 用标注好的问答数据反向更新模型权重

**答案**：ABCD
**考点**：M3-K02 RAG 完整流程与各环节作用
**解析**：
- A ✅ **离线索引环节**。先把 PDF / Word / 网页等解析成文本并切成合适粒度的片段，是所有后续步骤的基础。
- B ✅ **离线索引环节**。用 embedding 模型把片段变成向量并入库建立索引，这一步决定了后续能否被语义检索到。
- C ✅ **在线查询环节**。把用户提问同样向量化后做相似度检索取 top-k，必要时再用 rerank 对候选片段精排。
- D ✅ **在线查询环节**。把筛选出的片段作为上下文，与问题一起组装成提示词交给大模型生成，这是「检索增强生成」的落点。
- E ❌ **这是微调（M5）的做法**，不是 RAG 的环节。RAG 的核心特征是**不改动模型权重** —— 这正是它比微调更灵活、知识可随时更新且可追溯的原因。二者可以组合使用，但流程上是两条独立的链路。
**我错了吗**：☐

### Q010 [M3-K06] [B] 多选

某 RAG 系统评测后发现**检索召回质量不佳**（相关段落经常进不了候选集）。下列有助于提升召回质量的措施有哪些？

- A. 重新设计切片策略，包括调整 chunk size 与增加相邻片段的 overlap
- B. 在粗召回之后引入重排序（rerank），对候选片段重新打分排序
- C. 对用户原始提问做查询改写，或拆成多个子查询做多路召回
- D. 调高 `temperature` 以提升召回准确率
- E. 增加训练轮数对模型进行微调以提升召回准确率

**答案**：ABC
**考点**：M3-K06 召回优化思路（含 M3-K05 重排序）
**解析**：
- A ✅ 切片策略直接决定语义单元是否完整、候选块的信噪比。属于**成本最低、应最先尝试**的优化点。
- B ✅ 引入 rerank 属于两阶段检索中的精排环节（M3-K05）：粗召回求「全」，重排求「准」，能把真正相关的片段提到靠前位置，避免其因超出 top-n 而被丢弃。
- C ✅ 用户口语化的提问常与文档的书面表述不一致（如「离职」vs「离司」），通过查询改写或拆分成多路子查询扩大了命中面，是提升召回率的有效手段。
- D ❌ `temperature` 是**生成阶段**的采样参数，作用于输出随机性，对「能不能检索到相关段落」没有任何影响。这是典型的**检索侧 / 生成侧混淆陷阱**。
- E ❌ 增加训练轮数属于**微调**（M5）的范畴，改变的是模型行为，不会改变向量库的召回结果。此外训练轮数过多还会带来过拟合风险。召回问题必须在检索链路上解决。
**我错了吗**：☐

### Q011 [M3-K09] [B] 多选

关于调用大模型 API 时的常用参数 `temperature`、`top_p`、`max_tokens`，下列说法正确的有哪些？

- A. `temperature` 调低，输出会更确定、更稳定、更容易复现同一结果
- B. `top_p` 调大，可供选择的候选词范围扩大，输出更倾向于多样化
- C. `max_tokens` 限制的是**输出**的最大长度，设置过小可能导致回答被截断
- D. `temperature` 调大可以让模型获得训练数据中没有的新知识
- E. `max_tokens` 用于限制**输入**文本的长度，调大可以保证检索召回更准确

**答案**：ABC
**考点**：M3-K09 API 调用与关键参数（只考作用方向，不考默认值）
**解析**：
- A ✅ `temperature` 控制采样随机性：**调低 → 更确定、更保守**；因此事实问答、RAG 问答、数据抽取、代码生成等求准的场景应当调低。
- B ✅ `top_p` 是核采样阈值：只从累积概率达到该阈值的候选词集合中采样。**调大 → 候选集更大 → 输出更多样**；调小则更集中稳定。降低随机性时通常与 `temperature` 同向下调。
- C ✅ `max_tokens` 限定一次请求**生成结果**的长度上限；设得过小，模型「话没说完就被叫停」，表现为答案突兀中断。
- D ❌ 这是高频送命选项。无论 `temperature` 怎么调，模型都**无法凭空获得训练数据之外的新知识**；调大只会让输出更发散，反而更容易产生编造内容。要补外部知识请用 **RAG**。
- E ❌ `max_tokens` 限制的是**输出**而非输入；它与检索召回属于完全不同的阶段，调大不会让检索更准。
